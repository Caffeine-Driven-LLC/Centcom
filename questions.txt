Q025. Does it wait silently for input, or does it emit a notification first? Paste anything it prints unprompted.

A: Yes, one JSON object per line, ending in \n. Five real lines (-> sent, <- received; ids shortened):

Q027. Do messages include a "jsonrpc":"2.0" field in either direction? Does it reject requests that include it?
A: The server never includes "jsonrpc" in what it sends. It does NOT reject requests that include "jsonrpc":"2.0" (an initialize with it was answered normally).

Q028. Does it accept requests that omit "jsonrpc" (as our client sends)? Confirm by sending one by hand.
A: Yes, every request in our tests omitted "jsonrpc" and was accepted.

Q029. Are request ids numbers or strings from the server's side? Paste a server-to-client request with its id.
A: Numbers. Example: {"id":0,"method":"item/commandExecution/requestApproval","params":{...}}.

Q030. Can ids from the server collide with ids we use for our requests (we start at 1)? Did you ever see a server request with id 1?
A: Server request ids start at 0 and count up per connection (0, 1, 2, ...). They are a separate id space from ours (we start at 1): a server request with id 1 is normal and is not the response to our request 1. Centcom's rpc.ts tells them apart by the presence of `method`, which is correct.

Q031. What is the largest single line you saw (bytes) during a normal turn with a long answer? What is the largest during a turn that edited a big file?
A: Long answer (300 lines of text): small lines, each delta is a few bytes. Largest overall: 1,213,351 bytes, the `item/completed` of a command that printed `seq 1 200000` (its aggregatedOutput was capped at about 1 MiB, then JSON escaping and the other fields pushed the line past that). The large-file edit case was not measured.

Q032. Does it ever send a line over 1 MiB (our limit)? What triggered it, if so?
A: YES. A plain `seq 1 200000` produced a 1,213,351-byte line, over Centcom's MAX_RPC_LINE (1 MiB, packages/agent/src/codex/rpc.ts). Centcom would treat it as `provider_protocol_error` and SIGKILL the session. Any command with about 1 MiB of output triggers it. Suggest raising the limit to at least 4 MiB (the C103 card's figure) or skipping over-long `item/completed` command lines instead of killing.

Q033. Does it ever write a partial line or a line without a trailing newline (for example when it exits)?
A: Not seen. On stdin close it exits with code 0 after finishing its lines (no partial line was logged in any run).

Q034. Does it write non-JSON text to stdout (logs, banners)? Paste an example if so.
A: No. stdout carried only JSON in every run.

Q035. What does it write to stderr during a normal session, and how much per turn?
A: Usually nothing. On errors it writes ANSI-coloured tracing lines, e.g. `ERROR codex_core::tools::router: error=exec_command failed: CreateProcess { message: "Rejected(\"rejected by user\")" }` after a declined command, `... "TurnAborted"` after an interrupt, and `codex_app_server::bespoke_event_handling: failed to deserialize ...` when we answered an approval with a shape it does not know. A few hundred bytes per event at most.

Q036. Does stderr ever contain secrets (tokens, API keys, paths with usernames)? Describe the shape without pasting secrets.
A: Not seen in our runs: only module names and error kinds. The lines are not redacted by Codex itself, so a command line or path could appear; Centcom's redact() on the stderr tail is still a good idea.

Q037. What happens when we send invalid JSON? Does it answer with an error or silently drop it or exit?
A: Silently ignored: no error response, no notification, and the process keeps running.

Q038. What happens when we send a request with an unknown method? Paste the exact error object (code and message).
A: {"code":-32600,"message":"Invalid request: unknown variant `nope/nothing`, expected one of `initialize`, `server/diagnostics`, ... (the full method list)"}. Note: the code is -32600 (Invalid request), not -32601.

Q039. What happens when we send a request with missing or wrong-typed params? Paste the error.
A: {"code":-32600,"message":"Invalid request: invalid type: integer `42`, expected a string"} (thread/start with cwd: 42).

Q040. What happens when stdin is closed? Does the process exit by itself, and how fast? What is the exit code?
A: It exits by itself with code 0 about 3.5 s after stdin is closed.

Q041. What happens on SIGINT sent to the app-server process? Does it exit, ignore, or cancel the current turn?
A: It exits at once (13 ms) with code 0, but does NOT kill the commands it started: a running `sleep 62` (and its zsh parent) kept running after the app-server was gone.

Q042. What happens on SIGTERM? How long until it exits, and with what code?
A: An idle app-server exits in about 70 ms with code 0.

Q043. What happens on SIGKILL of the parent while it runs? Does the child exit by itself or become an orphan?
A: NOT TESTED directly (killing our node parent). After stdin closes it exits within about 3.5 s (Q040), so an orphaned app-server should follow once its stdin pipe closes.

Q044. Does the app-server spawn child processes of its own (shell commands, MCP servers, sandboxes)? Do they share its process group?
A: Yes, and NOT in its process group. `ps -g <app-server pgid>` shows only the node wrapper and the native `codex app-server`; the shell commands (`/bin/zsh -c sleep 61 && echo done` and `sleep 61`) run in a different process group (the item source is `unifiedExecStartup`). MCP servers: NOT TESTED.

Q045. If we kill the app-server's process group, do the commands it started die too? Test with a `sleep 300` command run by the agent.
A: NO. We sent SIGINT, then SIGTERM 3 s later, to the app-server's whole process group (what Centcom's ladder does) while the agent ran `sleep 63`. The app-server exited (code 0) but `sleep 63` and its zsh parent kept running. This breaks the assumption in packages/agent/src/codex/engine.ts ("The app-server leads its own process group ..., so stopping it stops the commands it started").

Q046. After the app-server dies, is anything left running (pgrep codex, pgrep sleep)? Paste the result.
A: After each kill: `pgrep -fl 'sleep 6'` still showed `/bin/zsh -c sleep 62 && echo done` and `sleep 62` (and the same for 61 and 63). No stray `codex app-server` was left.

Q047. How much memory does the app-server use idle and after a long turn (RSS in MB)?
A: Native `codex app-server` process: about 118 MB RSS right after start, about 250 MB after about 15 turns across several threads. The node wrapper itself is about 42 MB and does not grow.

Q048. How many app-server processes can run at the same time without trouble on one account?
A: Several app-servers one after another, each with several threads, worked on one ChatGPT Plus account, and two threads ran turns at the same time inside one app-server (Q157). Two app-servers running at the same moment: NOT TESTED.

Q049. Does starting a second app-server in the same directory conflict with the first (locks, sqlite, session files)?
A: No conflict seen: several app-servers ran in the same folder in turn, and threads from one could be resumed in another. ~/.codex holds sqlite files (state_5, thread_history_1, logs_2, ...) with WAL files and a `thread-writer-locks` folder, so sharing is designed in. Two app-servers writing the same thread at once: NOT TESTED.
