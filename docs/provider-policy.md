# Who pays, and which provider methods are allowed (lane C105, CT-PROVIDER)

- **Who pays** (`computeWhoPays`): in branch mode the agent's owner pays; in a command post the host pays. `shared` is true when the payer did not type the prompt. `buildSpawnClearFields` gives the only two provider fields that go in the clear part of `agent.spawn`: `runs_on` and `provider`.
- **Start gate** (`evaluateStartGate`), run before an engine starts and before a guest prompt is claimed: method flag off -> `provider_method_disabled`; command post + subscription (or unknown) login + `provider.command_post.subscription` off -> `provider_policy_blocked`; flag on but the host has not confirmed -> `needs: host_confirmation`; everything else is allowed (API key and cloud logins always). A flag turning off never stops a running session.
- **Flags**: `provider.claude_code` (true), `provider.codex` (true), `provider.command_post.subscription` (false). Defaults apply until the flags client has loaded, so a subscription command post stays blocked offline.
- **Host confirmation** (`createHostConfirmation`): per session, in memory only, audited once as `provider.cp_subscription.confirmed {engine}`; a new session asks again. The notice text (`packages/tui/src/provider/messages.ts`) needs a human sign-off before release.
- **Guest spend** (`createGuestSpendControl`): counts guests and pauses/resumes them through the injected `setGuestsPaused` (the session lanes implement it with `control.policy`).
- **Local states**: `providerStateFor` maps provider error codes to `provider-auth-required`, `provider-cap-reached`, `provider-policy-blocked`. They drive the mascot and status line only and are never sent as `agent.state`.
- **Policy table**: `packages/agent/data/provider-policy.json` equals the reference rows in `contracts/fixtures/providers/policy-reference.json`; `node tools/refresh-provider-policy.mjs` refreshes `checked_at` each release (`--check` verifies the rows). `centcom provider status --policy` prints one line per method with its flag value now.
- **Gate result**: a block carries `error`, the local `state` (`provider-policy-blocked`) and a `noticeKey` into the TUI message table; `needs: 'host_confirmation'` names the engine. Anything unreadable (unknown login kind, unknown mode, a flag that is not a boolean, an unknown path) is blocked, never allowed. `evaluatePathGate(path, input)` is the same gate for `new_session`, `host_handoff`, `failover`, `queue_approval`, `auto_approve` and `guest_prompt`: callers on each path must use it and none may skip it.
- **Confirmation API**: `requestHostConfirmation({ ui, audit, sessionId }, engine)` and `hostConfirmed(sessionId, engine)` hold a `y` from the host's own UI for one session in memory; `dropHostConfirmations()` is called when the host role moves, so the new host is asked.
- **Pause failures**: if `setGuestsPaused` rejects the control keeps its previous state, `lastError()` is true (the banner shows `provider.pause_failed`) and `held()` stays true, so guest items are not claimed. With the roster unavailable `count()` is the last known value and `stale()` is true (dimmed).
- **Wiring** (`packages/tui/src/collab/policy.ts`, `host-bridge.ts`, `share-session.ts`, `apps/desktop/src/local/collab.ts`): `HostBridge` owns a `PolicyGate`; every way new work reaches the host's login goes through `evaluatePathGate`, and anything not allowed does not run. `new_session`: `/share` and the desktop Share button refuse before a session exists (hard block) or end the session they created (host said no). `queue_approval`: `bridge.approve()`. `auto_approve`: turning it on, and each item it would approve. `guest_prompt`: checked right before a queue item is claimed (a flag that flipped while the agent was busy counts); a hard block rejects the item (code `other`) and tells the guests with a system message, a missing confirmation only holds it. `failover`: `AppController.switchEngine` asks the engine guard before it moves to another agent (and resets the login kind to unknown). `host_handoff`: accepting a handoff. Branch mode runs on each owner's own login and is allowed. The login kind is what the engine reported, else the C104 lookup, else `unknown` (a subscription).
- **What the host sees**: a block is a notice (terminal) or a red box in the Share dialog (desktop) saying what happened and the options: ask Centcom to switch on `provider.command_post.subscription`, use an API-key login, or share in branch mode. The confirmation is a pick list in the terminal (`/share confirm` asks again) and Yes/No buttons in the window. The header shows `runs on you · <provider>`; the footer shows `N guests can spend your <Provider> usage  /share pause` (or `Guests paused  /share resume`). Pausing sends `control.policy` with `locked: true` (the other required fields as the host engine's defaults when this client has not heard them) and holds unclaimed items locally even when that fails.
- **Guests** (`centcom join`, the desktop join pane) see `Your prompt will run on <host>'s account` before the first prompt; while the host is unknown nothing is sent.
- **Not wired yet**: a host change in a command post (the engine moving to another computer) has no code in the client yet; when it lands it must call `PolicyGate.drop()` and `admit()` for the new host. The web guest page (`apps/web` session page) still needs its own notice.
