## Goal
One permission policy engine and approval broker for every engine: it receives normalised `approval.requested` events from claude and codex, decides allow/deny/ask from persisted rules, modes and risk, asks the UI (C038) or a remote approver, and returns the decision to the engine. Default is ask or deny, never silent allow.

## In scope
- Rule model `{ id, engine?: 'claude-code'|'codex'|'*', tool: string, matcher?: { command?: string; path_glob?: string; mcp_server?: string }, action: 'allow'|'deny'|'ask', scope: 'session'|'project'|'user', created_at }`; precedence explicit deny > ask > allow > mode default; within a class the most specific matcher wins.
- Centcom permission modes `ask` (default), `accept-edits`, `plan`, `auto-low-risk` (allow only risk `low`), `bypass` (explicit config opt-in, visible `bypass_active` flag, hard denies still apply); mapped to CLI flags by C016, not here.
- Approval broker: `handle(req: ApprovalRequest): Promise<ApprovalDecision>` receives the normalised request from the runner (event `approval.requested`: `{aprId, agentId, tool, input summary, command?, paths?, risk?}`), evaluates rules, and when action is `ask` asks the UI (`ApprovalPrompter`, implemented by C038) and/or a remote approver; the answer `{decision:'approve'|'deny', scope:'once'|'session'|'always', reason?}` is returned to the engine as the return value of `PermissionGate.decide`, which the engine awaits (injected as `EngineStartOptions.approvalGate`) (engine bridge in C102/C103). Request id is the `apr_` id; `expires_at` defaults to now + 600 000 ms and expiry resolves as deny.
- Rule syntax and translation layer (owned here): parse and print Claude `--allowedTools` / `--disallowedTools` style entries (`Bash(git status:*)`, `Edit`, `Read(src/**)`, `mcp__server__tool`) to and from our rule model; for Codex translate to `--sandbox read-only|workspace-write|danger-full-access` plus `--ask-for-approval untrusted|on-request|never` approximations and report lossy translations as `translationNotes`. `toClaudeArgs(rules)` and `toCodexArgs(rules)` return argv fragments; C102/C103 append them.
- Hard denies no rule or mode can override: writes outside the agent worktree after `realpath` (symlink and `..` safe), writes into `.git/` internals, reads of credential locations (`~/.ssh`, `~/.aws`, `~/.claude*`, `~/.codex/*`, OS keychain files), and any request for an agent that is `stopped`. Applied in the broker even if the engine already allowed.
- Persistence: session rules in memory; project rules `.centcom/permissions.local.json` (added to `.git/info/exclude`, loaded only if `TrustStore.isTrusted('project-rules', sha256)` from C013); user rules `<config dir>/permissions.json`; atomic writes, mode 0600; schema-validated, malformed file ignored with a warning (fail closed: zero allow rules).
- Always-rules: approving with `scope:'always'` creates a conservative rule (exact command prefix up to the first flag/pipe/`;`; never `*` for shell commands; path rules use the directory glob inside the worktree only).
- Remote decisions: `resolveRemote(aprId, decision, from)` accepts only the host or members allowed by the approver policy (CT-RBAC, CT-WS-SESSION-EVENTS `approval.request.approver`); others return `{accepted:false, reason:'not_approver'}` and call `audit`. Produces the `approval.request` clear part `{approval_id, agent_id, risk, expires_at, approver}` and encrypted detail for C057-side senders; first decision wins, duplicates ignored.
- Risk comes from the classifier (`RiskClassifier`, C016); until plugged in the broker uses `medium`.

- Wire transport of `approval.request`/`approval.decision` frames: session lanes; this lane produces and consumes the payload shapes only.

## Interfaces (the only surface other lanes may use)
- `createPermissionEngine(deps: { fs: PermFs; clock: Clock; ids: IdGenerator; trust: TrustStore; classifier?: RiskClassifier; prompter: ApprovalPrompter; remote?: RemoteApprover; audit: (e: AuditEvent) => void; config: PermConfig }): PermissionEngine`
- `interface PermissionEngine { decide(req: ApprovalRequest, ctx: { agentId: AgentId; root: string; mode: PermissionMode }): Decision; handle(req: ApprovalRequest, ctx: AgentCtx): Promise<ApprovalDecision>; resolveRemote(aprId: string, d: ApprovalDecision, from: MemberRef): { accepted: boolean; reason?: string }; pending(): PendingApproval[]; rules: RuleStore }`
- `type PermissionMode = 'ask'|'accept-edits'|'plan'|'auto-low-risk'|'bypass'`; `type ApprovalDecision = { decision: 'approve'|'deny'; scope: 'once'|'session'|'always'; reason?: string }`.
- `interface ApprovalPrompter { prompt(p: PendingApproval, signal: AbortSignal): Promise<ApprovalDecision> }` implemented by C038.
- `parseClaudeRule(s: string): Rule`, `formatClaudeRule(r: Rule): string`, `toClaudeArgs(rules: Rule[], mode: PermissionMode): string[]` (e.g. `['--allowedTools','Bash(git status:*)','Read']`), `toCodexArgs(rules: Rule[], mode: PermissionMode): { argv: string[]; translationNotes: string[] }`.
- `interface PermissionGate { decide(req: ApprovalRequest): Promise<ApprovalDecision> }` implemented by the approval broker and injected into every engine as `EngineStartOptions.approvalGate` (C101); `ApprovalRequest` mirrors the normalised `approval.requested` payload.

## Acceptance criteria
1. Deny beats allow: with rules `allow Bash(git *)` and `deny Bash(git push*)`, `git push origin x` is denied and `git status` is allowed.
2. Mode `ask`: read inside root -> allow; edit -> ask; shell `ls` -> ask unless a rule allows. Mode `plan`: edit and shell -> deny with reason `plan_mode`. Mode `accept-edits`: edit inside root -> allow, shell -> ask. Mode `auto-low-risk`: risk `low` -> allow, `medium`/`high` -> ask.
3. A write to `<root>/../secrets.txt` and to a symlink inside root pointing outside root are hard-denied in every mode including `bypass`, as are reads of `~/.codex/auth.json` and `~/.claude/.credentials.json` (traversal tests, POSIX and Windows case variants).
4. An approval with no answer is denied at exactly `expires_at` (fake clock, default 600 000 ms) and `pending()` is empty afterwards; the engine receives the deny through `resolveApproval` within one tick.
5. The same `approval.requested` transcript from claude and from codex produces the same `PendingApproval` shape and the same decision (engine-independence test with both golden transcripts).
6. `resolveRemote` from a viewer or unknown member returns `{accepted:false, reason:'not_approver'}` and calls `audit`; from the host or a delegated approver returns accepted:true and unblocks the waiting request within one tick; a second decision for the same id is ignored.
7. `scope:'always'` for shell `git status` creates a rule that auto-allows `git status` next time but still asks for `git status; rm -rf x`.
8. `parseClaudeRule(formatClaudeRule(r))` round-trips for 50 fixture rules; `toClaudeArgs` of rules {allow `Read`, allow `Bash(git status:*)`, deny `Bash(rm:*)`} yields `--allowedTools Read 'Bash(git status:*)' --disallowedTools 'Bash(rm:*)'` as separate argv entries; `toCodexArgs` for mode `plan` yields `--sandbox read-only --ask-for-approval untrusted` and a non-empty `translationNotes` when a path rule cannot be expressed.
9. A corrupted permissions.json yields zero allow rules, a warning and continued asking; rule files are written 0600; a project rules file whose hash is not trusted is not loaded and listed in `needsTrust`.
10. Approval payload for the wire passes the generated `approval.request` clear-schema validator and contains no command text or paths in the clear part.

## Guardrails (MUST / MUST NOT)
- Default MUST be ask/deny; if the engine, prompter or classifier throws or times out the answer is deny; MUST NOT auto-allow a request it cannot parse.
- MUST NOT read credential files itself; the credential-path hard deny is a path match on requests only.
- A remote approval MUST come from an authorised approver (host or CT-RBAC delegated); the relay never decides. Command text and paths stay in the encrypted part.
- Hard denies MUST be applied after rule evaluation and after any engine-side allow; rules and modes cannot weaken them.
- MUST NOT vendor any SDK; rule syntax is parsed locally. Translation losses MUST be surfaced (`translationNotes`), never silently widened.

## Failure modes
- UI closed or no prompter attached -> request stays pending until `expires_at`, then deny; headless mode (`--yes` unsupported) denies immediately.
- Engine disconnects with pending approvals -> all pending for that agent are cancelled and audited.
- Rule file unreadable or schema-invalid -> warn, ignore, keep asking.
- Unknown tool kind or engine value -> treated as `ask` with risk `medium` (never allow).
