## Goal
A scrollable transcript that renders messages, tool calls, results, thinking and system notices from typed events, stays smooth with thousands of blocks via virtualisation, and follows the tail while streaming.

## In scope
- Transcript model and reducer `reduceTranscript(state, evt)` accepting decoded session events: `message.user`, `message.assistant.delta` (ordered by `index`, deduped by `(message_id,index)`), `message.assistant.done`, `message.system`, `tool.request`, `tool.result`, plus `approval.request/decision` as one-line notices and `agent.exit`; unknown kinds are ignored (CT-WS-SESSION-EVENTS rule).
- Block renderers per DESIGN §10.1.2: user `●` + `you` (or other member: gutter `▎` in member colour + `M · Maya`), assistant text with 2-column indent, tool call `● Name(arg)` (arg `text.link`, one line), tool result `└ summary`, thinking `∴` collapsible, system `※` in `status.info`; one blank row between blocks, none between a tool call and its result.
- Minimal streaming Markdown for assistant text: paragraphs, `-`/`1.` lists, fenced code blocks with a left bar, inline code, bold; no images or tables in v1.
- Virtualised viewport: measure block heights per `(blockId, width, revision)` with an LRU cache, render only blocks intersecting the viewport plus 20 rows of overscan.
- Scrolling: `pageup/pagedown` (viewport - 2 rows), `ctrl+home/ctrl+end`, wheel keys if the terminal maps them; auto-follow tail unless the user scrolled up, with an indicator row `↓ 12 new` that returns to the tail on `ctrl+end`.
- Memory cap of 5,000 in-memory blocks; older blocks collapse to a single row `⋯ 1,240 earlier messages` and can be reloaded through an injected `loadRange` (lane C026 provides it for local sessions).

## Out of scope
- Diff rendering (lane C037); this lane calls its component for `diff.share` and for edit tool results.
- Permission prompt rendering (lane C038) and the prompt box (C035).
- Producing events (runner, session client) and decryption (CT-CRYPTO is handled before events reach this lane).
- Syntax highlighting in code blocks and mouse support.

## Acceptance criteria
1. Replaying 10,000 blocks, scrolling one page renders in under 16 ms p95 and mounts at most (viewport rows + 40) rows of text (counted by a render probe).
2. Appending a streaming delta to the last block re-renders only that block: under 2 ms p95 and zero re-measurement of other blocks (cache hit counter).
3. Deltas arriving out of order (index 2 before 1) render in index order after a reorder buffer of up to 64 deltas; a duplicate `(message_id,index)` is ignored; a gap older than 2 s is rendered as-is with a `…` marker and later fills in place.
4. With the viewport scrolled up, new events do not move the viewport; the `↓ N new` indicator counts them; `ctrl+end` jumps to the tail and re-enables follow.
5. At 80x24 a user block, assistant paragraph with a 3-item list, a tool call `● Read(src/a.ts)`, its result `└ 120 lines`, a thinking block (collapsed shows `∴ Thinking… (ctrl+o)`) and a system notice produce the documented glyphs and spacing; same snapshot under `NO_COLOR` keeps all glyphs.
6. A message from member slot 2 (self slot 0) shows `▎` in red plus initial and name (`M · Maya`), never colour alone.
7. Unknown event kind `future.thing` and unknown `tool.result.status` value render nothing / a generic `done` result and do not throw.
8. Text containing `\x1b[2J` or OSC sequences from a tool result is displayed inert (escape removed) and does not clear the screen (pty test).
9. Resizing from 100 to 80 columns re-wraps and keeps the top visible block anchored.

## Guardrails (MUST / MUST NOT)
- MUST sanitise every string from events with `sanitizeForTerminal` (lane C034) before layout; remote members' names, tool arguments and results are untrusted.
- MUST NOT use arrival order for sequencing when `seq` is present; sort by `seq` and treat the relay as authoritative (CT-WS-ENVELOPE).
- MUST show member identity as initial + name, never colour alone (DESIGN §16.3).
- MUST NOT render the mascot inside tool results or code blocks (DESIGN §10.1.9).
- MUST keep memory bounded: at most 5,000 blocks and 64 buffered deltas per stream; deltas larger than 4 KiB are accepted but split for layout.
- MUST NOT log block text; log only ids and counts.

## Failure modes
- `onNeedRange` rejects -> keep the `⋯ earlier messages` row and show `Couldn't load earlier messages. Try again.` once per attempt.
- A block renderer throws -> replace that block with `※ Couldn't display this message.` and continue.
- Decrypted payload fails schema validation upstream (event dropped) -> a single notice `※ A message couldn't be read.` is added, with no content.
