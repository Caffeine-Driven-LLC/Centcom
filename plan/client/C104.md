## Goal
`centcom provider status|login|logout|doctor` tells the user, per engine, whether the vendor CLI is installed, supported, and signed in and how, hands login and logout over to the vendor's own commands in the user's terminal, and maps every provider error to one calm message with a next step. It learns everything from the tools' own reports and never touches a credential.

## In scope
- Detection library `packages/agent/src/provider/detect/`: `detectProvider(id, deps): Promise<ProviderStatus>` running, in parallel and with 5 s per probe and 15 s overall: PATH lookup (`which`-style, no shell), `<bin> --version`, signed-in probe (`codex login status`; for Claude Code `claude auth status` when `claude auth --help` exits 0, otherwise `signed_in: 'unknown'` and the answer comes from the first `system/init` at session start), results cached 30 s in memory, `--refresh` bypasses.
- `ProviderStatus` also carries `supported: 'yes'|'below'|'above'|'unknown'` from a bundled `supportedRanges` table (`ranges.ts`; initial values `claude-code >=2.0.0 <3.0.0`, `codex >=0.40.0 <1.0.0`, to be corrected when C102/C103 record transcripts) compared with a small in-house semver comparator (no dependency).
- Login kind classification `classifyLogin(text, exit): LoginKind` from the tool's own words only (`ChatGPT`/`subscription`/`Claude account` -> `subscription`; `API key` -> `api_key`; `Bedrock`/`Vertex`/`Foundry`/`cloud` -> `cloud`; anything else -> `unknown`); `effectiveKind(kind)` returns `subscription` for `unknown` (conservative default, CT-PROVIDER 4). Output is read from the first 4 KiB, redacted with the shared patterns, and only the classification is kept.
- CLI commands in `apps/cli/src/commands/provider/`: `centcom provider status [claude|codex] [--json] [--refresh] [--policy]`, `centcom provider login <claude|codex>`, `centcom provider logout <claude|codex>`, `centcom provider doctor [--json]`. Exit codes: 0 ok, 1 warnings (not signed in / unsupported version), 2 any engine missing when it was named explicitly.
- Login handoff `loginHandoff(id, deps)`: spawns the vendor's own login with `stdio: 'inherit'` in the user's terminal (`codex login` for Codex; for Claude Code `claude auth login` when detected, else `claude` interactive with a one-line hint to run `/login`), waits without a timeout for the user (Ctrl-C cancels cleanly, 130), then re-runs detection and prints the new status. Refuses when not attached to a TTY (`provider_not_signed_in` message with the manual command). Centcom does not capture, drive or screen-scrape the child's streams.
- Logout `logoutHandoff(id)` runs the vendor's own logout (`codex logout`, `claude auth logout` when detected) with inherited stdio after a `y/N` confirmation (skippable with `--yes`) and re-checks; never deletes files itself.
- Doctor checks exported for the doctor command (C097 registers them): `providerDoctorChecks: DoctorCheck[]` with ids `provider.claude.installed`, `provider.claude.version`, `provider.claude.signed_in`, `provider.codex.installed`, `provider.codex.version`, `provider.codex.signed_in`, `provider.policy.fresh` (the bundled policy `checked_at` older than 180 days warns), `provider.leak_scan` (scans the last 500 KiB of Centcom's own log files with the secret patterns; any match fails and prints the pattern id only). Missing provider is `skip`/`warn`, never `fail`, unless the user has an agent configured on it.
- Install hints per OS (`install-hints.ts`, text only, Centcom never runs an installer): macOS/Linux/Windows lines for Claude Code (`npm install -g @anthropic-ai/claude-code` or the vendor's installer from its docs page) and Codex (`npm install -g @openai/codex` or `brew install codex`), plus the vendor's docs URL; hints live in the message table so they can change without code.
- Error vocabulary and message table `packages/agent/src/provider/messages.ts`: one entry per `ProviderErrorCode` of CT-PROVIDER 9 with `title`, `body`, `next_step`, `severity`, `state` (client-local product state, if any), and a `{tool_message}` slot that shows the tool's own words verbatim in a quoted block (redacted, max 2 KiB); table in `interfaces`.
- Credential-leak guardrails: a shared `redactProviderText(s)` using `contracts/fixtures/providers/secret-patterns.json` (bundled copy generated at build by the codegen lane, checked for byte equality with the contract file in a test) applied to every string that leaves this module (logs, JSON output, messages); the detect module never calls `fs` on anything outside its own temp/cache paths (test with a fs spy).
- Claude Code login detection uses the documented `claude auth status` (JSON on stdout; exit 0 = signed in, 1 = not): `authMethod` `claude.ai` or `oauth_token` -> subscription, `api_key` or `api_key_helper` -> api_key, `third_party` -> cloud, `none` -> signed out. Only `authMethod` is read; no other field is stored or logged. `centcom provider login claude` runs `claude auth login` (adding `--console` when the user picks API billing) with inherited stdio; Centcom never runs `claude setup-token`.

## Interfaces (the only surface other lanes may use)
- ```ts
type LoginKind = 'subscription'|'api_key'|'cloud'|'unknown';
interface ProviderStatus {
  engine: 'claude-code'|'codex'; provider: 'anthropic'|'openai';
  installed: boolean; path?: string; version?: string;
  supported: 'yes'|'below'|'above'|'unknown'; supported_range: string;
  signed_in: 'yes'|'no'|'unknown'; login_kind: LoginKind; effective_kind: 'subscription'|'api_key'|'cloud';
  checked_at: string; errors: ProviderErrorCode[];
}
```
`detectProvider(id: EngineId, d: { spawn: SpawnFn; which: WhichFn; clock: Clock; log: Logger; timeoutMs?: number }): Promise<ProviderStatus>`; `detectAll(d): Promise<ProviderStatus[]>`.
- `classifyLogin(output: string, exitCode: number | null): { signedIn: boolean | null; kind: LoginKind }`; `effectiveKind(k: LoginKind): 'subscription'|'api_key'|'cloud'`; `satisfies(version: string, range: string): boolean`.
- `loginHandoff(id, d): Promise<{ exit_code: number | null; status: ProviderStatus }>`; `logoutHandoff(id, d, o?: { yes?: boolean }): Promise<{ status: ProviderStatus }>`; both take an injected `spawn` that must be called with `{ stdio: 'inherit', shell: false }` (asserted in tests).
- CLI: `centcom provider status --json` prints `{ schema_version: 1, providers: ProviderStatus[], policy?: ProviderPolicy }`; human output is two short lines per engine, e.g. `claude-code  installed 2.1.0 (supported)  signed in (subscription)`.
- Doctor: `export const providerDoctorChecks: DoctorCheck[]` (same `DoctorCheck` shape as C097) and `registerStatusSection(s: { id: string; render(ctx): string[]; json(ctx): unknown }): void` used by C105 for `--policy`.
- Message table: `providerMessage(code: ProviderErrorCode, o?: { tool_message?: string; engine?: EngineId; os?: NodeJS.Platform }): { title: string; body: string; next_step: string; severity: 'info'|'warn'|'error'; state?: 'provider-auth-required'|'provider-cap-reached'|'provider-policy-blocked' }`. Rows: `provider_not_installed` (next: install hint for this OS, then `centcom provider status`), `provider_not_signed_in` (next: `centcom provider login <name>`; state provider-auth-required), `provider_method_disabled` (next: 'This provider is switched off for now; try the other one'; state provider-policy-blocked), `provider_policy_blocked` (next: ask the owner of the CLI login or use an API-key login; state provider-policy-blocked), `provider_cap_reached` (next: wait for the reset shown by the tool or switch provider; state provider-cap-reached), `provider_rate_limited` (next: Centcom will not retry faster than the tool does), `provider_version_unsupported` (next: update or pin the CLI, shows the supported range), `provider_protocol_error` (next: run `centcom provider doctor`), `provider_capability_missing` (next: shows which feature is unavailable and that the rest still works).
- Env vars: `CENTCOM_CLAUDE_BIN`, `CENTCOM_CODEX_BIN` override the binary path (existence-checked, never executed through a shell).

## Acceptance criteria
1. With probe fakes, `centcom provider status --json` reports `installed:true, version:'2.1.0', supported:'yes'` for an in-range fake and `supported:'below'` for `1.9.0`, and completes in under 15 s even when one probe hangs (that probe is killed at 5 s and yields `errors:['provider_protocol_error']`).
2. `classifyLogin` table: 'Logged in using ChatGPT' -> subscription; 'Logged in using an API key - sk-...' -> api_key; 'Using Amazon Bedrock' -> cloud; empty output exit 1 -> signedIn false; garbled output -> kind unknown and `effectiveKind('unknown') === 'subscription'`.
3. A fake `codex login status` printing a full API key line produces status JSON, logs and error messages that contain 0 matches of `secret-patterns.json` (all 4 `must_match` strings are redacted when they are fed through `redactProviderText`, and none of the 4 `must_not_match` strings are altered).
4. `centcom provider login codex` invokes the injected spawn exactly once for the vendor login with `stdio:'inherit'` and `shell:false`, then calls detection again; without a TTY it spawns nothing and exits 1 with the manual command printed.
5. `centcom provider logout claude --yes` spawns the vendor logout once and re-checks; without `--yes` and without a TTY it exits 1 and spawns nothing.
6. A spy on `fs` shows detection and handoff read no path under `~/.claude*`, `~/.codex*`, the OS keychain locations or `auth.json`; the only reads are PATH directories (stat) and Centcom's own cache dir.
7. `providerMessage` returns a non-empty `title`, `body` and `next_step` for all 9 codes in 2 platforms, each `next_step` names a runnable command or a concrete action, and a lint test fails on any text that styles a Centcom feature with a vendor name (pattern `Centcom (Claude|Codex|ChatGPT|Anthropic|OpenAI)`); vendor names appear only as the tool being referred to (CT-PROVIDER 1.5).
8. `providerDoctorChecks` returns `warn` (not `fail`) with a next step for a missing CLI and `fail` for a leak-scan hit, and `provider.policy.fresh` warns for a `checked_at` 181 days old with the injected clock.
9. Detection results are cached: two `detectAll` calls within 30 s spawn each probe once; with `--refresh` they spawn again.
10. Given fake `claude auth status` outputs, `detectProvider('claude-code')` returns: `{authMethod:'claude.ai'}` exit 0 -> signed_in yes, kind subscription; `{authMethod:'api_key'}` -> api_key; `{authMethod:'third_party'}` -> cloud; `{authMethod:'none'}` exit 1 -> signed_in no; a non-JSON reply -> unknown (treated as subscription by `effectiveKind`).

## Guardrails (MUST / MUST NOT)
- MUST NOT read, open, stat or copy any credential or config file of the vendor tools (`~/.claude*`, `~/.codex/*`, `auth.json`, keychain entries) and MUST NOT read provider API-key environment variables to guess a login kind; the tools' own reports are the only source (CT-PROVIDER 1 and 4). Unknown means subscription.
- Login and logout MUST run the vendor's own command with inherited stdio in the user's terminal; Centcom MUST NOT capture the password, code or token, open a browser flow of its own, or screen-scrape the child.
- Every string leaving this module (stdout, JSON, logs, messages) goes through `redactProviderText`; a probe output that matches a secret pattern is replaced by `[redacted:<pattern id>]` and the raw text is dropped at once.
- Never execute through a shell and never interpolate user input into a command string; binary overrides are passed as `file` + `args`.
- Error text for the user is the calm message from the table plus the tool's own words in a quoted block; do not paraphrase the tool's error or blame the user, and never include paths, branch names or prompt text.
- Do not run any probe that could cost money or use plan quota (no `claude -p` test prompts, no `codex exec` smoke runs).

## Failure modes
- Binary found but `--version` hangs or exits non-zero -> `installed:true, version:undefined, supported:'unknown'` plus `provider_protocol_error`; doctor warns, other engine unaffected.
- `claude auth` subcommand absent in the installed version -> `signed_in:'unknown'`; status says 'will be checked when the first agent starts' and login falls back to the interactive hint.
- Login child exits 0 but the re-check still says signed out -> print the status and the manual command; exit 1, no loop.
- stdout of a probe exceeds 64 KiB -> kill the probe, keep the first 4 KiB, mark `provider_protocol_error`.
- PATH contains a relative or non-existent entry, or the binary is a directory -> skipped silently; `not installed` is reported with the OS install hint.
