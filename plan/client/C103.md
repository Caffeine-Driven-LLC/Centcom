## Goal
An `AgentEngine` that runs the user's own unmodified `codex` binary, preferring `codex app-server --listen stdio://` (JSON-RPC threads, turns, approvals, events) with a `codex exec --json` fallback, mapping everything onto the C101 normalised events and routing approvals through the C015 policy engine, with no credential access.

## In scope
- `createCodexEngine(deps)` implementing `AgentEngine` (id `codex`, provider `openai`) in `packages/agent/src/engines/codex/`; mode selection `auto | app-server | exec` (config `engines.codex.mode`, default `auto`): app-server when the probe `codex app-server --help` exits 0 within 5 s, else exec fallback; the chosen mode is logged once and reported in `session.started.tools` as a `mode:<name>` entry.
- JSON-RPC 2.0 client over the child's stdio (`rpc.ts`): newline-delimited messages, request ids as integers, per-request timeout 30 s (`initialize` 10 s), notifications and server-to-client requests supported, max line 4 MiB, unknown methods answered with `-32601`, pending requests rejected with `provider_protocol_error` on child exit. Method names live in one table `protocol.ts` (initially `initialize`/`initialized`, `thread/start`, `thread/resume`, `turn/start`, `turn/interrupt`, server requests for command and file-change approval, notifications for agent message deltas, item started/completed, token usage and turn completion), confirmed against recorded transcripts when they are made.
- Session flow: spawn `codex app-server --listen stdio://` (cwd = worktree) -> `initialize` (client name `centcom`, version) -> `thread/start` with cwd, model?, sandbox and approval policy (mapping below) -> for each `send`: `turn/start` with the text input -> map notifications until turn completion -> emit `turn.done`. The thread id is the `resumeToken()`; `start({resume})` calls `thread/resume`.
- Approvals: server requests for command execution and file changes become `ToolUseRequest`s for the C015 gate (`requestApproval`), emitting `approval.requested` and `approval.resolved`; the JSON-RPC response carries the decision (`approved` / `denied`, and for `scope:'session'` the session-scoped variant if the server version advertises it, else `once`). Unanswered after `agent.approval_timeout_ms` -> denied.
- Permission-mode mapping, one pure function `mapPermissionMode(mode): { sandbox: 'read-only'|'workspace-write'|'danger-full-access'; approval: 'untrusted'|'on-request'|'never' }`: `default` -> workspace-write + untrusted; `acceptEdits` -> workspace-write + on-request; `plan` -> read-only + on-request; `bypassPermissions` -> danger-full-access + never (only with config `agent.allow_bypass` and never in a command post). Exec fallback passes the same via `--sandbox <s> --ask-for-approval <a>`; when the exec mode cannot ask interactively, any mode that needs approvals is downgraded to `read-only` + `never` with a `message.system`-bound warning event, never to a more permissive setting.
- Exec fallback (`exec.ts`): argv `codex exec --json --sandbox <s> --ask-for-approval <a> [--model <m>] [--cd <worktree>] -` with the prompt on stdin; `resume` via `codex exec resume <SESSION_ID> --json ...` (or `--last` only when the session id is unknown and exactly one session exists in this worktree); JSONL events parsed with a table-driven mapper (`exec-map.ts`); capabilities in this mode drop `approvals` and `subagents`.
- Auth and failure mapping: not signed in (`codex login status` non-zero, or the server's auth-required error) -> `provider_not_signed_in`; usage limit text / error kind -> `provider_cap_reached`; HTTP 429 -> `provider_rate_limited`; JSON-RPC parse/shape failures -> `provider_protocol_error`. Table in `failure-table.ts`, oracle = recorded transcripts. Login kind comes from `codex login status` output via the C104 parser (`ChatGPT` -> subscription, `API key` -> api_key, otherwise unknown) and is placed in `session.started.login_kind`.
- Interrupt: app-server mode sends `turn/interrupt` for the active turn, waits 5 s for turn completion, then SIGINT to the child, then SIGTERM after another 5 s, then SIGKILL after 3 s; exec mode sends SIGINT, grace 5 s, SIGTERM. Cleanup events as in C101.
- Version handling: `codex --version` is checked against `supportedRange` (C104) before spawn -> `provider_version_unsupported`; capability set derived from the `initialize` result (server capabilities) when present, else the floor `{streaming, approvals, resume, interrupt, usage}` (exec floor: `{streaming, resume, interrupt, usage}`).
- Process hygiene as in C102: spawn timeout 10 s, first-event timeout 30 s, stderr ring buffer 64 KiB redacted, max line 4 MiB, `shell:false`, inherited environment (including `OPENAI_API_KEY` if the user set it; never read, logged or copied), no touching of `~/.codex/*`.
- Recorder and fake CLI: `tools/record-codex-transcript.mjs` (dev-only) writes `packages/agent/test/fixtures/providers/codex/<mode>-<scenario>.jsonl` (app-server frames tagged `->`/`<-`, or exec JSONL), scrubbed and scanned; `packages/agent/test/fake-cli/codex` (+ `codex.cmd`) replays them, answers `--version`, `login status`, `app-server --help`, and plays a JSON-RPC server that validates the client's requests against the recorded ones.

## Out of scope

- The interface and normalised events (C101); the Claude Code engine (C102).

## Acceptance criteria
1. Replaying `app-server-simple.jsonl` yields the golden normalised events (`session.started` with `login_kind:'subscription'` when `FAKE_CLI_LOGIN=chatgpt`, text deltas, `text.done`, `usage.report`, `turn.done{ok}`) and the same replay in exec mode yields the same events minus approvals and subagents, with the reduced capability set in `session.started`.
2. `mapPermissionMode` table test: default/acceptEdits/plan map exactly as in scope_in; `bypassPermissions` throws `provider_policy_blocked` unless `allowBypass` is true and `commandPost` is false; argv for each case contains `--sandbox` and `--ask-for-approval` with those values and never a more permissive one than requested.
3. A command approval request from the fake server surfaces as `approval.requested` within 200 ms; approve/deny answers produce the matching JSON-RPC response ids and `approval.resolved`; two concurrent approvals with ids 7 and 8 are answered to the right ids even when resolved in reverse order.
4. No approval answer within `agent.approval_timeout_ms` (1 s in test) responds with a denial and emits `approval.resolved{by:'timeout'}`.
5. Interrupt in app-server mode sends `turn/interrupt` first; with a fake that ignores it, SIGINT arrives at 5.0 s and SIGTERM at 10.0 s (+/- 200 ms fake clock); `turn.done{outcome:'canceled'}` is emitted once.
6. `FAKE_CLI_LOGIN=none` makes `start` fail with `provider_not_signed_in` before any turn; the `usage limit` transcript yields `provider_cap_reached`; a 429 transcript yields `provider_rate_limited` and no automatic retry loop.
7. `codex --version` outside the supported range -> `provider_version_unsupported` with no app-server spawned; `app-server --help` failing -> exec fallback is used and a single info log says so.
8. A JSON-RPC response that never arrives is rejected after 30 s (10 s for `initialize`) with `provider_protocol_error`; a 4 MiB + 1 byte line stops the child with `provider_protocol_error`; child exit rejects all pending requests within 100 ms.
9. Secret scan: 0 matches of `secret-patterns.json` in committed fixtures and in captured logs; the recorder refuses to write a transcript containing a match (including the masked key line of `codex login status`).

## Guardrails (MUST / MUST NOT)
- MUST NOT read, open or parse `~/.codex/auth.json`, `config.toml` or any file under `~/.codex/`; sign-in state comes only from `codex login status` and the server's own errors. Lint rule bans `.codex` path strings outside fixture names.
- MUST NOT pass `--sandbox danger-full-access` or `--ask-for-approval never` unless the user chose `bypassPermissions` AND `agent.allow_bypass` is true AND the session is not a command post; any parse failure while mapping modes falls back to the most restrictive pair (`read-only` + `untrusted`).
- Approvals fail closed: timeout, gate exception, interrupt, unknown request method and malformed params all answer deny/decline; an unknown server request that could execute something is never auto-accepted.
- `codex login status` may print a masked key: its output is parsed from the first 200 bytes only, run through the secret scanner and redactor, and never stored or logged raw.
- The user's prompt never goes into argv (stdin or JSON-RPC params only) and never into logs.
- No automatic retries on usage-limit or rate-limit errors; the CLI's own messages are shown verbatim (redacted, 2 KiB cap) by the UI.

## Failure modes
- app-server dies mid-turn -> pending requests rejected, tools `canceled`, `error{provider_protocol_error}` with stderr tail, `turn.done{error}`; the next `send` re-spawns and `thread/resume`s the same thread, once; a second crash within 60 s stops retrying.
- Server speaks an unknown protocol version (initialize error) -> fall back to exec mode when allowed by `engines.codex.mode`, else `provider_version_unsupported`.
- Notifications for unknown item types -> ignored with debug log; the turn still completes.
- Exec fallback cannot ask for approval -> run read-only with `never` and tell the user via an `error{fatal:false, code:'provider_capability_missing'}` event; never escalate silently.
- Login expires between turns -> next turn `provider_not_signed_in`; C105 shows `provider-auth-required`.
