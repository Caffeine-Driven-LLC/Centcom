## Goal
Show each agent's context and usage exactly as its engine reports it, warn near limits using the engine's own numbers, and ask the engine to compact itself through its own command when the capability exists. Centcom never counts tokens or summarises context.

## In scope
- `ContextView` per agent, updated only from normalised `usage.report` events `{ agent_id, message_id, input_tokens?, output_tokens?, cache_read_tokens?, context_used?, context_window?, cost_usd?, model? }`; every field is optional because engines differ (capability `usage`).
- Percent = `context_used / context_window` only when the engine reported both; otherwise `pct` is `undefined` and the UI shows raw counts or 'not reported'. No estimator, no tokenizer, no model-window table.
- Warning thresholds in config `context.warn_pct` (default 75) and `context.full_pct` (default 97), applied to engine-reported pct only; hysteresis: each fires once until pct drops 10 points below it. `full` raises the local product state `context-full` (CT-STATE-MAP limits category).
- `requestCompaction(agentId)`: allowed only when the engine capabilities include `compact` (a command the engine documents, e.g. Claude Code `/compact` sent as a prompt via `AgentEngine.send`); only between turns (agent status `waiting`), never during a tool call or pending approval. Where the capability is absent the call returns `{ ok:false, reason:'unsupported' }` and the UI explains it.
- Optional auto-request: when `context.auto_compact` is true (default false) and the engine reports pct >= `context.auto_pct` (default 85) while idle, call `requestCompaction` at most once per hysteresis cycle.
- Compaction progress comes from engine events (`compaction.started` / `compaction.ended` with before/after if reported) and is re-emitted as bus events `agent:compaction`; the state machine (C014) maps it to `compacting`.
- `UsageLedger` summing engine-reported usage per agent with de-duplication by `message_id` (resume replays do not double count), monotonic totals, and `agent:context` bus events at most once per second per agent.

## Out of scope
- Counting or estimating tokens, tokenizers, context-window tables, deciding what to drop from context: the engine's own job.
- Sending usage to any API or telemetry: the billing and usage client lanes.
- Rendering the context meter: TUI lanes. Mapping signals to wire states: C014.
- Cost or plan-limit enforcement: the CLIs' own limits are shown verbatim by the engine adapters (C102, C103).

## Interfaces (the only surface other lanes may use)
- `createContextView(deps: { bus: AgentBus; clock: Clock; config: ContextConfig; engines: { capabilities(id: AgentId): CapabilitySet; send(id: AgentId, prompt: string): Promise<void>; status(id: AgentId): 'starting'|'running'|'waiting'|'exited' } }): ContextView`
- `interface ContextView { onEvent(e: NormalisedEvent): void; snapshot(id: AgentId): { used?: number; window?: number; pct?: number; reported: boolean; totals: { tokens_in: number; tokens_out: number; cost_usd?: number } }; requestCompaction(id: AgentId): Promise<{ ok: true } | { ok: false; reason: 'unsupported'|'busy'|'not_idle' }> }`
- `interface ContextConfig { warn_pct: number; full_pct: number; auto_compact: boolean; auto_pct: number }`; bus events `agent:context { agent_id, used?, window?, pct? }`, `agent:compaction { agent_id, phase: 'start'|'end', before?, after? }`.
- CLI: `centcom context [agent]` prints the snapshot; TUI command `/compact` calls `requestCompaction`.

## Acceptance criteria
1. Given `usage.report {context_used:150000, context_window:200000}`, exactly one warn event fires at 75%; a second report at 151 000 fires none until pct falls below 65 then rises again.
2. A `usage.report` without `context_window` yields `snapshot.pct === undefined` and `reported:false` for the window; no warning and no `context-full` are ever raised from it.
3. `context-full` is raised once at 194 000/200 000 (97%) and cleared after a `compaction.ended` report below 87%.
4. `requestCompaction` on an engine without capability `compact` returns `{ok:false, reason:'unsupported'}` and sends nothing (engine `send` mock call count 0).
5. With capability `compact` and status `waiting`, `requestCompaction` sends exactly one prompt `/compact` for Claude Code and none while status is `running` (returns `reason:'busy'`).
6. Replaying a 1 000-message transcript twice (resume) leaves `totals.tokens_in` equal to the sum of unique `message_id`s; totals never decrease across 1 000 shuffled reports.
7. `agent:context` is emitted <= 1 per second per agent when 100 reports arrive within 1 s (fake clock).
8. The source tree contains no tokenizer or estimator: a lint test greps `packages/agent/src/context/` for `ceil(` over chars and for `tiktoken` and finds none.

## Guardrails (MUST / MUST NOT)
- MUST NOT count, estimate or tokenise anything; if the engine does not report a number, show nothing rather than a guess.
- MUST NOT request compaction during a tool call, pending approval or when the capability is absent; MUST NOT implement our own summarisation.
- MUST NOT send prompt or message text to usage or telemetry paths: the view stores counts, model names and cost only; model names are encrypted-part data on the wire and never logged.
- All timers use the injected clock and are cleared on agent exit; auto-compaction ships default off because a compaction changes what the model remembers.

## Failure modes
- Engine reports no usage at all (capability `usage` absent) -> meter hidden with an explanatory line; no warnings.
- Compaction command fails or the engine returns an error event -> show the tool's own message verbatim in a calm frame, back off 60 s, never retry automatically more than once per cycle.
- Unknown or malformed `usage.report` fields -> ignored at debug level; known fields still applied.
