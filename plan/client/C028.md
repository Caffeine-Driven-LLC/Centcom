## Goal
The user can choose and switch the Claude model for the session, per project, or per sub-agent, with context-window and price metadata available to the rest of the client.

## In scope
- Client-owned model catalog `packages/agent/src/models/catalog.json`: entries `{id, alias, label, context_window, max_output, price_per_mtok: {input, output, cache_read, cache_write}}` in USD; aliases such as `default`, `fast`, `best` resolve through it.
- Resolution order: `--model <id|alias>` flag, then session override (`/model`), then project config key `model`, then user config key `model`, then catalog default; resolved through the layered config of lane C004.
- `/model [id|alias]`: no arg prints current model and the catalog as a short list; with arg switches. A switch takes effect at the next turn boundary, never mid-stream.
- Bus events `model.changed` ({agent_id, from, to, reason}) and a `message.system` style notice for the transcript (level `info`, text from the message table).
- Unknown model ids are allowed (passthrough to the SDK) with a warning and the fallback window from config `model.unknownContextWindow`, so new models work without a client release.

## Out of scope
- Sending the model name over the wire; model names are secret payload (`agent.spawn.ct.model`) handled by the session lanes.
- Token counting and compaction triggers (lane C019) and cost calculation (lane C029); this lane only supplies catalog data.
- Authentication to the model provider and API-key management (separate auth/runner lanes).
- The picker UI overlay (lane C041 can list `catalog()`); only the text command lives here.

## Build against (no counterpart needed)
No counterpart. Catalog is a static JSON file validated by a zod/JSON-schema check in the test suite; the runner is a stub implementing the C013 `setModel(next)` call.

- `packages/agent/src/models/`

## Interfaces (the only surface other lanes may use)
- `interface ModelRegistry { catalog(): ModelInfo[]; resolve(input: string): ResolvedModel; current(agentId: string): ResolvedModel; switchTo(agentId: string, input: string, reason: 'user'|'config'|'fallback'): Promise<ResolvedModel> }`
- `type ResolvedModel = {id: string; alias?: string; known: boolean; contextWindow: number; maxOutput: number; price?: ModelInfo['price_per_mtok']}`
- `createModelRegistry(deps: {config: ConfigReader; bus: EventBus; runner: Pick<AgentRunner,'setModel'>; log: Logger}): ModelRegistry`
- Flag `--model <id|alias>`; slash `/model [id|alias]`; config keys `model`, `model.unknownContextWindow` (default 200000).

## Acceptance criteria
1. `resolve('fast')` returns the catalog entry whose `alias` is `fast`; `resolve('<id in catalog>')` returns `known: true`; `resolve('mystery-model')` returns `known: false` with `contextWindow` equal to the config fallback.
2. Precedence test: flag beats session override beats project config beats user config beats catalog default, each exercised in one table-driven test.
3. `switchTo` during a streaming turn returns immediately, the runner receives `setModel` only after the bus event `turn.ended`, and exactly one `model.changed` event is emitted.
4. Switching to the model already in use is a no-op with no event and the message `Already using <label>.`.
5. `/model` with no argument prints one line per catalog entry in at most 80 columns, current model marked with `*`.
6. catalog.json fails the validation test if any entry has a missing price field, a non-positive context window, or a duplicate id/alias.
7. The persisted session (lane C026 consumers) records the model id at each `model.changed`; resume restores the last model.

## Tests required
- models/resolve.test.ts: aliases, unknown ids, precedence table.
- models/switch.test.ts: turn-boundary application, no-op switch, failure from runner.
- models/catalog-schema.test.ts: schema and uniqueness checks.
- models/command.test.ts: `/model` output at 80 columns.

## Guardrails (MUST / MUST NOT)
- MUST NOT hard-code prices or ids in code; they live only in catalog.json so product can update them without a code change.
- MUST NOT log API keys or full prompts when logging a model switch; log only ids.
- MUST apply a switch only at a turn boundary; changing the model mid-tool-call would corrupt token accounting in lane C029.
- MUST treat catalog prices as display/estimate data and label any derived cost as an estimate in user-facing text.

## Failure modes
- Runner rejects the model id -> keep the previous model, emit a toast `Couldn't switch to <id>. Still using <previous>.`, return a typed error.
- Config contains a non-string `model` -> ignore it, log at warn with the key name only, fall back to catalog default.
