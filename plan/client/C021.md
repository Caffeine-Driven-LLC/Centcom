## Goal
Let the user configure MCP servers for Claude Code and Codex and see per-engine MCP status, by writing the engines' own documented config formats after confirmation and reading status from the engines' events. Centcom stores no secrets and does not run MCP servers itself.

## In scope
- Claude Code config: read/write the project `.mcp.json` (`{ mcpServers: { <name>: { type?: 'stdio'|'http'|'sse', command?, args?, env?, url?, headers? } } }`) and build a `--mcp-config <file-or-json>` payload for per-session servers; Codex: read/write the MCP section of `~/.codex/config.toml` or the project-scope config only where documented, via a TOML edit limited to `[mcp_servers.<name>]` tables.
- Neutral model `McpServerDef { name, transport: 'stdio'|'http'|'sse', command?, args?, url?, env_refs?: Record<string,string> /* NAME -> ENV VAR NAME */, header_refs?: Record<string,string> }`; names `^[a-z][a-z0-9_-]{0,31}$`; converters `toClaude(def)` and `toCodex(def)`.
- Secrets: values are never stored by Centcom. Only environment-variable references are written (`${GITHUB_TOKEN}` form for Claude, `env_vars = ["GITHUB_TOKEN"]`-style reference for Codex as documented); a literal value matching `looksLikeSecret` (C005) is refused with `SecretRejected`.
- Every write goes through `plan()` -> diff -> user confirmation -> `apply()` with a timestamped backup `<file>.centcom-bak`; project scope default, user scope needs extra confirmation; project `.mcp.json` servers run arbitrary commands, so the diff view labels stdio `command` lines as 'runs a program on your machine'.
- Status: per engine and per server `{ name, state: 'connected'|'needs_auth'|'failed'|'pending'|'disabled'|'unknown', tools?: number, error?: string }` taken from the engine's status event (Claude `system/init` `mcp_servers` name+status and `mcp_server_errors`; Codex status events) and refreshed on `engine.status` events; tool names shown as the engine reports them.
- Test-connection helper `testServer(def)`: validates the definition, checks the command exists on PATH (`which`-style lookup, no execution) or the URL is https/loopback, then starts a throw-away engine session through the runner with only that server (`--mcp-config`, a no-op prompt) and reports the status the engine gives; 30 s timeout; the session is stopped afterwards.
- Built-in, non-removable entry `centcom-approvals`: the small stdio MCP approval server used as `--permission-prompt-tool` by the Claude engine (owned and started by C102). It is listed with a lock icon, excluded from edits, export and `.mcp.json` writes, and shown as `connected` when the engine reports it.

## Out of scope
- Implementing the MCP protocol, running or supervising MCP servers, health pings, restarts, tool-call timeouts: the engines do all of it.
- The approval MCP server itself and the approvals bridge: C102 (Claude) and C103 (Codex); permission decisions: C015.
- Keychain access or secret storage of any kind; OAuth flows for MCP servers (the engine's own `/mcp` flow is shown, not driven).
- Skills, hooks and memory files: C020, C022, C023.

## Interfaces (the only surface other lanes may use)
- `createMcpManager(deps: { fs: McpFs; engines: { status(engine: EngineId): EngineStatus | undefined; testSession(engine: EngineId, mcpConfigJson: string, o: { timeoutMs: number }): Promise<EngineStatus> }; clock: Clock; bus: AgentBus; log: Logger }): McpManager`

- CLI: `centcom mcp list|add|remove|status|test <name> [--engine claude|codex] [--scope project|user]`.

## Acceptance criteria
1. `plan({kind:'add', engine:'claude-code', scope:'project', def:{name:'files', transport:'stdio', command:'npx', args:['-y','some-mcp']}})` produces a diff adding one `mcpServers.files` entry to `.mcp.json`, and `apply` writes it plus a `.centcom-bak` of the previous bytes; unrelated keys and ordering in the file are preserved.
2. The same definition for Codex produces exactly one `[mcp_servers.files]` TOML table; other TOML content is byte-identical after apply (golden test).
3. A literal `env` value `ghp_` + 36 chars is refused with `SecretRejected` and nothing is written; `env_refs: { GITHUB_TOKEN: 'GITHUB_TOKEN' }` writes only the variable name, never a value (grep of the written file for the test token finds none).
4. Given a recorded `system/init` with `mcp_servers:[{name:'files',status:'connected'},{name:'gh',status:'needs-auth'}]` and `mcp_server_errors:[...]`, `status()` shows `connected` and `needs_auth` with the engine's error text verbatim for failures.
5. The built-in `centcom-approvals` entry appears in `list().builtin`; `plan({kind:'remove', name:'centcom-approvals'})` throws `BuiltinServer` and it never appears in any written file.
6. `testServer` with a missing command returns `failed` with reason `command_not_found` and starts no engine session (testSession mock count 0); with a valid one it calls `testSession` once with a `--mcp-config` JSON containing only that server and resolves within 30 000 ms (fake clock), stopping the session.
7. An `http://example.com` URL is rejected; `https://example.com` and `http://127.0.0.1:8080` are accepted.
8. `apply` with a stale `planHash` (file changed after the diff) writes nothing and throws `PlanChanged`.

## Guardrails (MUST / MUST NOT)
- MUST NOT store, cache, echo or log any secret value; only env var names are persisted, and `looksLikeSecret` hits are refused without echoing the content.
- MUST NOT write any config without a diff and confirmation bound to the plan hash; a project `.mcp.json` entry is arbitrary command execution by the engine, so the UI states that before confirming.
- MUST NOT read credential files (`~/.codex/auth.json`, `~/.claude*` credentials); only the documented MCP config sections are parsed, and unknown TOML/JSON content is preserved untouched.
- MUST NOT shell-interpolate: the test helper never executes the server command itself; only the engine does.
- MUST NOT allow removal or editing of `centcom-approvals`.

## Failure modes
- Config file invalid JSON/TOML -> refuse to edit, show the parse position, leave the file untouched.
- Engine does not report MCP status (capability `mcp` absent or old version) -> show 'status not reported by this version' and still allow config edits.
- Test session times out -> report `failed: timeout`, stop the session, never leave a child process running.
## Notes
