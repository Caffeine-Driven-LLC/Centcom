## Goal
Give the rest of the client one SessionClient that creates, joins, leaves, ends and hosts relay sessions: it wires REST, the WebSocket client, reliable delivery and crypto together and exposes decrypted, validated, typed session events.

## In scope
- REST: POST /v1/sessions (Idempotency-Key, `relay` entitlement error surfaced), GET /v1/sessions, GET /v1/sessions/{id}, PATCH, POST .../end, POST .../join-token (called for every connection attempt), GET .../members, POST .../claim-host, share-link create/revoke and POST /v1/share-links/{token}/join, key-bundle PUT/GET for invites.
- Connection assembly: `getTicket` (join-token with region hint) -> RelayClient (C054) -> ReliableChannel (C055); applies decrypt-and-verify to every received `ct` frame and encrypt-and-sign on send.
- Host mode: creates epoch key `k1`, answers `control.member_joined` with `key.grant` frames (respecting `share_history`), rotates on `control.kick`/leave (publishes new grants after `control.rotate_key`), scheduled rotation, and publishes snapshots.
- Guest mode: waits in `waiting_for_key` until a grant (or invite bundle) opens; verifies the granter's signature; then decrypts history.
- Roster/member cache from `control.member_joined`, `control.member_left`, `control.roster` and GET .../members (slot, role, device id, device public keys); TOFU trust checks through C056 with a `key-changed` event.
- Resume REST side of CT-RESUME: `fetchSnapshot()` (GET .../snapshot, download pre-signed URL, verify sha256 and size, decrypt with the right epoch, require `fmt:'centcom.snapshot'`, `v:1`), `fetchHistory(afterSeq)` (paginated GET .../history), host `uploadSnapshot()` (POST .../snapshot, PUT to `upload_url`, POST .../commit `{seq, sha256, size, kid}`) every 500 frames or 5 min, and on graceful end.
- Typed event API: `on(kind, handler)` for decoded session events (validated against the C003 event schemas, hybrid p+ct merged), `sendEvent(kind, {p, secret})`, lifecycle events (`state`, `roster`, `waiting-for-key`, `ended`).

## Out of scope
- Queue semantics (C058), presence/cursors (C059), control commands (C060), approvals (C061), fleet sync (C062): thin clients that sit on this lane's `sendEvent`.
- Socket/handshake (C054), delivery guarantees (C055), crypto primitives (C056), HTTP plumbing (C051).
- LAN sessions: lanes C072, C074, C075.
- Building the snapshot content (transcript/queue/roster state): the host session engine provides a `buildSnapshot()` callback.
- CLI commands for create/join: not specified in this plan's lanes; they will call this API.

## Acceptance criteria
1. `createSession` sends one POST /v1/sessions with an `Idempotency-Key`; a forced network retry yields one session on the mock; a `relay_access:false` account gets the typed entitlement error (not a generic failure) and no socket is opened.
2. Each connection attempt performs exactly one POST .../join-token; after a forced disconnect the reconnect uses a new ticket and the mock rejects a reused jti (the client never reuses one).
3. Host+guest in-process: guest joins, `waiting_for_key` is entered, the host emits one `key.grant` within 2 s of `control.member_joined`, the guest reaches `live` and decrypts a `message.user` fixture sent by the host; the simulator's captured traffic contains no plaintext of `secret`.
4. With `share_history:false` the grant contains only the current and later epochs; the guest cannot decrypt epoch-1 history frames and reports them as `unreadable_earlier_history` instead of failing.
5. Kicking a member: after `control.kick` + `control.rotate_key {kid:'k2'}` the host's next outbound frame uses `kid:'k2'`, grants for k2 are sealed to every remaining device but not the kicked one, and no frame after rotation is encrypted under k1.
6. A frame with a bad signature or from an unknown `from` is dropped, a `protocol-warning` is emitted, and the session stays `live`; a server-only control kind (`control.roster`, `member_joined`, `host_changed`, `session_state`, `rotate_key`) whose `from` is a normal member id is ignored.
7. A changed device key for a known device raises `key-changed` and the frames from that device are held (not delivered) until the caller calls `trustDevice(deviceId)`.
8. Snapshot restore: given `sys.resumed {snapshot_required:true, snapshot_seq:900}`, the client downloads the snapshot, verifies sha256 and size (mismatch -> typed error, snapshot ignored), decrypts, rejects `fmt:'other'` or `v:2` with a clear message, then applies history after 900 in order and acks.
9. Host snapshot upload triggers after 500 frames or 5 min of activity (fake clock), whichever first, and on `end()`; sequence is POST .../snapshot -> PUT upload_url -> POST .../commit with `{seq, sha256, size, kid}`; the three calls carry Idempotency-Keys on the POSTs.
10. `end()` sends POST .../end, uploads a final snapshot, and the handle moves to `ended` on `control.session_state {state:'ended'}`; `leave()` closes with 1000 and does not end the session.
11. Event decoding validates against the C003 schemas: an unknown `k` is ignored (debug log, still acked), a known kind with a malformed `ct` secret is dropped with a warning.

## Guardrails (MUST / MUST NOT)
- MUST verify `sig` then decrypt every `ct` frame before emitting it; MUST drop failures and keep the session alive. MUST NOT emit undecoded or unverified content to subscribers.
- MUST ignore `control.member_joined/left/roster/host_changed/session_state/rotate_key` unless the frame comes from the server (CT-WS-CONTROL); MUST NOT apply role or host changes from client-originated frames.
- MUST NOT put plaintext work content (message text, paths, branch names, model names) into any `p` field, REST body, log line or error; only fields the privacy budget lists in CT-WS-SESSION-EVENTS may be cleartext.
- MUST NOT send a client-side role claim as authority; UI role checks are for hiding controls only, the server answers `forbidden` (CT-RBAC).
- MUST mint a new join-token per connection attempt and MUST NOT cache or log tickets; MUST send them only via C054's hello.
- MUST NOT grant keys to a device that is not in the roster or whose key check is `changed`; MUST seal grants only to the device's registered X25519 key.
- MUST stay usable offline for non-session work: no network call at construction; creating a LAN or local session never goes through this client.

## Failure modes
- Join-token 403 (membership revoked / not entitled) -> state `ended` with a typed error and no retries; 404 -> `ended` (session gone).
- No key holder online -> remain `waiting_for_key` with the 'Waiting for the host to let you in' state; ciphertext is retained, not discarded; resumes automatically when a grant arrives.
- Snapshot hash mismatch or decrypt failure -> discard it, fall back to full history from the earliest retained frame and surface 'earlier history unavailable'.
- Host disconnects -> state `paused` (from `control.session_state`); guests keep read access and queue UI shows held items (C058); host return resumes.
- Quota/plan notices (`sys.notice`) -> re-emitted as `notice` events for C064/C065, never interpreted here.
