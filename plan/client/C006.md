## Goal
Turn HTTP and WebSocket errors into typed client errors with correct retry behaviour and user-facing text from a single message table, following CT-ERR exactly.

## In scope
- `parseProblem(res: { status: number; headers: Headers; bodyText: string }): CentcomError` handling `application/problem+json` (fields type, title, status, code, detail, instance, request_id, retry_after_s, errors[]), and non-problem bodies (HTML from a proxy, empty body, invalid JSON) mapped to a status-class error.
- `CentcomError` class with `kind: 'api'|'network'|'timeout'|'aborted'|'protocol'`, `code`, `status`, `requestId`, `retryAfterS`, `fieldErrors: {pointer, code, detail}[]`, `detail` (sanitised), `cause`.
- Retry table from CT-ERR as pure functions: `retryDecision({status, method, hasIdempotencyKey, attempt, authRefreshed})`: 400/403/404/409/410/422 no; 401 refresh once then no; 408/425/429 retry; 500/502/503/504 retry only idempotent (GET/HEAD/PUT/DELETE, or POST with Idempotency-Key); max 5 attempts.
- `backoffDelayMs(attempt, retryAfterS, rng)`: honour `Retry-After`/`retry_after_s` if present, else full-jitter exponential, base 500 ms, cap 30 000 ms.
- WebSocket mapping `closeCodeAction(code)`: 1000/1001 -> reconnect; 4400 -> stop (protocol bug); 4401 -> refresh_token then reconnect; 4403, 4404 -> stop and tell user; 4408, 4409(superseded -> stop), 4429, 4503 -> reconnect with backoff (4503 honours `retry_after_s`); 4426 -> upgrade_required; unknown 4xxx -> reconnect with backoff.
- User message table `messages.en.ts`: `code -> { title, hint }` for every code in the generated `ErrorCode` union (compile-time exhaustive) plus status-class fallbacks (CT-ERR rule 7) and local kinds (network, timeout, aborted); `userMessage(err): { title: string; hint?: string; ref?: string }` where `ref` is `Ref: req_...` for support.
- Auth-specific handling: `token_expired` -> action `refresh`; `token_invalid`, `token_revoked`, `device_revoked`, `refresh_reuse_detected` -> action `reauthenticate`; `client_too_old` -> `upgrade`; `quota_exceeded` -> `show_quota`; `forbidden` -> `show_forbidden`. Exposed as `nextAction(err)`.

## Out of scope
- The HTTP client that performs requests and retries (consumes these helpers): net client lane.
- Generating the `ErrorCode` union: lane C003.
- Rendering errors in the TUI/web: UI lanes.

## Interfaces (the only surface other lanes may use)
- `class CentcomError extends Error { readonly kind; readonly code: ErrorCode | 'unknown'; readonly status?: number; readonly requestId?: string; readonly retryAfterS?: number; readonly fieldErrors: FieldError[] }`
- `parseProblem(res): CentcomError`; `fromWsError(p: unknown): CentcomError` (body of `sys.error`); `fromNetworkError(e: unknown): CentcomError`.
- `retryDecision(i: RetryInput): { retry: boolean; reason: string; refreshAuth?: boolean }`; `backoffDelayMs(attempt: number, retryAfterS: number | undefined, rng: () => number): number`.
- `closeCodeAction(code: number): { action: 'reconnect'|'stop'|'refresh_token'|'upgrade_required'; backoff: boolean }`.
- `userMessage(e: CentcomError, locale = 'en'): UserMessage`; `nextAction(e): 'refresh'|'reauthenticate'|'upgrade'|'show_quota'|'show_forbidden'|'retry'|'none'`.

## Acceptance criteria
1. A body `{type,title,status:429,code:'quota_exceeded',detail,request_id:'req_...',retry_after_s:3600}` yields `CentcomError{code:'quota_exceeded', retryAfterS:3600, requestId:'req_...'}`; a 502 HTML body yields `kind:'api', code:'unknown', status:502` without throwing.
2. `retryDecision` truth table matches CT-ERR for statuses 400,401,403,404,408,409,410,422,425,429,500,502,503,504 across GET/POST-with-key/POST-without-key (42 table-driven cases).
3. `backoffDelayMs(attempt=3, undefined, rng)` is within [0, 4000]; for attempts >= 7 never exceeds 30000; with `retryAfterS=7` returns >= 7000 and <= 7000 + 500.
4. A 5xx on POST without `Idempotency-Key` returns `retry:false`; with the key `retry:true` up to attempt 5, then false.
5. 401 `token_expired` returns `{retry:true, refreshAuth:true}` once; a second 401 in the same operation returns `retry:false`; 401 `token_revoked` never retries.
6. `closeCodeAction` covers every close code in CT-WS-ENVELOPE (1000, 1001, 4400, 4401, 4403, 4404, 4408, 4409, 4426, 4429, 4503) with the exact actions listed in scope.
7. Compile-time and test-time exhaustiveness: adding a code to the generated `ErrorCode` union without a message makes `tsc` fail (type test) and the runtime test enumerate and fail.
8. `userMessage` output never contains `detail` text longer than 200 chars, never contains URLs with query strings, and includes `Ref: req_...` only when a request id exists.

## Tests required
- parse-problem.test.ts (valid, missing fields, wrong content type, huge body capped at 64 KiB, UTF-8 BOM).
- retry-table.test.ts (table-driven, 42 cases) and backoff.test.ts with a seeded RNG + property test (monotone cap).
- close-codes.test.ts, messages-exhaustive.test.ts, next-action.test.ts, no-secret-leak.test.ts (detail containing a JWT is redacted).

## Guardrails (MUST / MUST NOT)
- MUST switch on `code`, never on `title` or `detail` (CT-ERR rule 1); unknown codes fall back to their HTTP status class.
- MUST NOT retry non-idempotent POSTs without an `Idempotency-Key`, and MUST NOT retry 400/403/404/409/410/422.
- MUST NOT show or log server `detail` verbatim if it matches `looksLikeSecret` (C005); user text comes from the message table.
- MUST bound parsing: ignore bodies over 64 KiB and `errors[]` beyond 100 entries.
- MUST NOT block local or LAN functionality on API/relay errors: these helpers only describe outcomes.

## Failure modes
- Body is not JSON or lacks `code` -> status-class fallback error, `request_id` taken from the `X-Request-Id` header if present.
- `Retry-After` is an HTTP-date or garbage -> parsed as HTTP-date when valid, otherwise ignored and backoff used.
- Unknown close code -> treated as reconnect-with-backoff, logged at debug.

## Definition of done
