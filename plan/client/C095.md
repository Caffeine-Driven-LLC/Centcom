## Goal
Installed copies of Centcom discover, verify and apply new versions on the stable, beta or nightly channel safely (never mid-session), with rollback, forced-update handling for too-old clients, and clear messages for npm/Homebrew installs that must not self-update.

## In scope
- CLI wiring in apps/cli/src/autoupdate/: background check on startup at most every 6 h (+/- 20 % jitter) using the update client (C068) against GET /v1/releases/{channel}/latest?platform=&arch=; result cached on disk with timestamp.
- Commands: `centcom update [--check] [--channel stable|beta|nightly] [--yes] [--allow-downgrade]`, `centcom config set update.channel <c>`, `centcom config set update.auto <true|false>`; status line / toast 'Update available: 1.4.3' (C044) when a newer version exists.
- Install-method detection (`standalone`, `npm`, `brew`, `unknown`) from the executable path and a build-time flag; non-standalone installs show the exact package-manager command and never self-replace.
- Apply protocol: download to temp, verify SHA-256 and Ed25519 signature (C068), atomically swap, run `<new> --version --json` health check (<= 5 s), roll back to the previous binary on failure, keep one previous version.
- Never apply while a session is live: apply on next start, or when the user runs `centcom update` explicitly; show 'restart to update'.
- Forced-update handling: map `client_too_old` (HTTP 426 / WS close 4426) and `/v1/status.min_client_version` to a blocking-for-hosted-features screen that still lets LAN and local use continue.
- React to `sys.notice client_update_available {version, channel}` and notification category `update_available` by showing the same toast; no auto-download triggered by a notice.

## Out of scope
- Signature/hash verification primitives and download implementation (C068).
- Installers, packages and the signing pipeline (C094, C012).
- Server-side manifest generation and staged rollout percentages.
- Release notes rendering beyond a link.

## Interfaces (the only surface other lanes may use)
- centcom update [--check] [--channel <c>] [--yes] [--allow-downgrade]; exit 0 up to date or updated, 10 update available (with --check), 11 verification failed, 12 unsupported install method
- export function detectInstallMethod(execPath: string, env: NodeJS.ProcessEnv): 'standalone'|'npm'|'brew'|'unknown'
- export function shouldCheck(now: number, lastCheck: number | null, rng: () => number): boolean
- export function applyUpdate(plan: UpdatePlan, fs: FsPort, runner: Runner): Promise<ApplyResult>  // ApplyResult = {ok: true; from: string; to: string} | {ok: false; rolledBack: boolean; code: string}
- Config keys: update.channel (default stable), update.auto (default true for standalone, false otherwise), update.check_interval_h (default 6)

## Acceptance criteria
1. With the mock serving version 1.4.3 > installed 1.4.2 on stable, `centcom update --check` exits 10 within 2 s and prints the version and channel; at equal version exits 0.
2. A tampered artifact (one byte changed) fails verification, the old binary stays in place, exit code 11 and no partial files remain in the install directory.
3. A new binary whose health check fails triggers rollback: after the command, `centcom --version` reports the old version and a `.previous` copy is kept.
4. Startup background check never delays first prompt by more than 20 ms (async, fire-and-forget; measured with fake network 2 s latency) and is skipped when `CI=true` or `update.auto=false`.
5. Installs detected as `npm`/`brew` print `npm i -g @centcom/cli@latest` / `brew upgrade centcom` and exit 12 on `centcom update` without touching files.
6. `client_too_old` from any call produces the blocking screen with the upgrade hint; `centcom --lan` and local sessions still start (test).
7. Channel switch to nightly requires `--yes` or an interactive confirm and shows a warning; switching to a lower version is refused unless `--allow-downgrade`.
8. Update is never applied while any session is live (host or guest): the apply path returns 'deferred' (test with a live fake session).

## Guardrails (MUST / MUST NOT)
- MUST verify signature (Ed25519, pinned public key(s) compiled into the binary) AND SHA-256 before swap; never trust TLS alone; MUST fail closed.
- MUST NOT execute any downloaded code before verification; health-check execution happens only after the atomic rename and only with the new binary's `--version --json`.
- MUST keep the update public key set in one file (`apps/cli/src/autoupdate/keys.ts`) with at least two key slots to allow rotation; MUST NOT fetch trusted keys from the same channel as the artifacts.
- MUST NOT auto-update on `nightly` or `beta` without the user having chosen that channel explicitly.
- MUST NOT send telemetry beyond the opt-in `update.result {from, to, ok}` event; no personal data in the update request (User-Agent per CT-VER only).
- Downgrade attacks: MUST refuse a manifest whose version is lower than the installed one unless `--allow-downgrade`.

## Failure modes
- Manifest fetch fails/offline -> silent in background, one dim line for explicit `update`; retry next interval.
- Disk full / permission denied on swap -> abort before replacing, leave current binary, explain with the path's directory name only.
- Signature valid but unknown `kid`/key slot -> treat as verification failure and instruct a manual reinstall.
- Process killed mid-swap -> next start detects `centcom.new`/`.previous` markers and restores or finishes atomically.
