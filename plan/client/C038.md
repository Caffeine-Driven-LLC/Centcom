## Goal
Show every approval request, from any engine, in one clear terminal prompt that says what, where, whose agent and which engine and account, uses the right keys, resists accidental approval, and works for both local requests and `approval.request` events from a shared session.

## In scope
- `<PermissionPrompt>` per DESIGN 10.1.4: title `Allow Cento to <verb> <object>?`, the exact command or path (6 lines, then `⋯ +N lines (v to view all)`), `in <directory> (<branch>)`, agent name with owner initial, risk chip, expiry countdown, and the key row.
- Data source: the normalised `approval.requested` event of any engine, delivered by the permission policy engine (lane C015) as an `ApprovalView`; the prompt never talks to an engine directly. Decisions go back to lane C015, which answers the engine.
- Provider/engine badge (`claude-code` / `codex` with the coarse provider word) and the 'whose account' line from CT-PROVIDER section 5: `runs on <name> · <provider>`; in a command post `Runs on <host>'s account`.
- Options per DESIGN 10.1.4: `[y]` once, `[s]` for this session, `[a]` always for this project, `[n]` deny, `[e]` edit; only the options the request allows are rendered (`allowedScopes`).
- Edit is only offered when the engine supports changing the input for this request (`editable: true` on the event, from the engine's capability); otherwise `[e]` is hidden and the footer says nothing about editing.
- Destructive/high-risk prompts use `status.danger` and require `y` then `⏎`; queue of pending prompts ordered by `expires_at` with `1 of 3` badge; the prompt gutter of lane C035 turns `status.warning` while any prompt is pending.
- Mapping to CT-WS-SESSION-EVENTS: input from `approval.request` (clear `approval_id, agent_id, risk, expires_at, approver`; secret `summary, command?, cwd?`), output `{approval_id, decision, scope, reason?}` for `approval.decision`.
- Role awareness: only the host and named approvers see action keys; others see `Waiting for <host name> to decide.`. Optional BEL on first display when `notify.bell` is true.

## Out of scope
- The permission engine, rules, always-rule storage and risk classification (lanes C015, C016) and applying the answer to the engine (lanes C102, C103).
- Detecting providers, who-pays policy and the command-post gate (lanes C104, C105); this component only displays the values it is given.
- Sending `approval.decision` over the wire and receiving `approval.request` (session client lanes).
- Desktop or push notifications; any mascot in the prompt (DESIGN 10.1.4 and 11.5).

## Interfaces (the only surface other lanes may use)
- `<PermissionPrompt request: ApprovalView; canDecide: boolean; onDecide: (d: ApprovalDecisionInput) => void; onEdit?: (cmd: string) => void; now: () => Date />`
- `type ApprovalView = {approvalId: string; agentId: string; agentLabel: string; ownerName: string; ownerSlot: number; engine: 'claude-code'|'codex'; provider: 'anthropic'|'openai'|'other'; runsOn: string; accountLine: string; risk: 'low'|'medium'|'high'; destructive: boolean; editable: boolean; allowedScopes: ('once'|'session'|'always')[]; expiresAt: string; approver: 'host'|'owner'|'any_editor'; title: string; command?: string; cwd?: string; branch?: string; summary: string}`
- `type ApprovalDecisionInput = {approvalId: string; decision: 'approve'|'deny'; scope: 'once'|'session'|'always'; editedCommand?: string; reason?: 'user'|'expired'|'interrupted'}`
- `<PermissionHost queue: ApprovalView[]; ... />`; `approvalFromEvent(ev: NormalisedApprovalRequested, ctx: {runsOn: string; accountLine: string}): ApprovalView`; `approvalFromWire(p: ApprovalRequestClear, s: ApprovalRequestSecret): ApprovalView`
- Action ids: `permission.yes`, `permission.session`, `permission.always`, `permission.no`, `permission.edit` (context `permission`).

## Acceptance criteria
1. Snapshot at 80x24 matches the DESIGN 10.1.4 anatomy: title, command, `in ~/centcom (agent/feature-retry)`, engine badge line `claude-code · anthropic · runs on Ana`, blank row, key row; box width `min(cols-2, 78)`.
2. Feeding the Claude Code and the Codex golden `approval.requested` events produces two prompts differing only in badge text and command text; both decisions return a schema-valid `ApprovalDecisionInput`.
3. For low/medium risk `y` calls `onDecide` once with `{decision:'approve', scope:'once'}`, `s` -> `session`, `a` -> `always`, `n` and `esc` -> `{decision:'deny', scope:'once'}`; keys for scopes not in `allowedScopes` are not rendered and do nothing.
4. `[e]` is rendered only when `editable` is true and `onEdit` is given; with `editable:false` the key row has no `e` and pressing `e` does nothing; an edited command returns `editedCommand` with `approve`/`once`.
5. Destructive prompt (`high` or `destructive:true`): `status.danger` border, bare `y` shows `Type y then Enter to confirm.` and does not call `onDecide`; `y` then `⏎` within 5 s approves.
6. Keystrokes within 300 ms after first render are ignored and buffered keys are cleared (test feeds `y` at 100 ms).
7. At `expires_at` the prompt auto-resolves `{decision:'deny', reason:'expired'}`, dims, shows `Expired`, and shows `expires in 4:32` updating each second.
8. With `canDecide=false` no key row appears, keys do nothing and the box reads `Waiting for <name> to decide.`; in a command post the account line reads `Runs on <host>'s account`.
9. Command text with `\u202E`, zero-width characters or ESC sequences is shown with visible escapes, so the user sees exactly what will run; under `NO_COLOR` risk is conveyed by words and the destructive border by `┏━┓`.

## Guardrails (MUST / MUST NOT)
- MUST NEVER make approval the default; `⏎` with nothing armed does nothing, focus never starts on `y`.
- MUST show what (exact command or path), where (directory and branch), whose agent, which engine and whose account in every prompt; MUST NOT hide the account line to save space.
- MUST ignore input during the 300 ms window and clear buffered keys, so text typed into the prompt box cannot approve an action.
- MUST NOT truncate silently: hidden lines are announced and `v` shows the full text before deciding.
- MUST enforce expiry locally; an expired prompt can never be approved.
- MUST NOT offer `[e]` unless the request is marked editable, and MUST NOT claim authority the user lacks (CT-RBAC is display only; the host decides).
- MUST NOT show the mascot or joke copy here (DESIGN 11.5).

## Failure modes
- `expires_at` already past on arrival -> render expired and emit the auto-deny; never flash an actionable prompt.
- Missing `command` -> show `summary` only and hide `[e]`.
- Decision callback throws or send fails -> keep the prompt open, show `Couldn't send your answer. Try again.`, re-enable keys.
- Unknown engine or provider value -> show the raw engine id and `other`, still allow decisions.
## Notes
`ApprovalView` fields `engine`, `provider`, `editable`, `allowedScopes` are populated by lane C015 from lane C101's `approval.requested`; align names at review. Scope `session` is added to the key row (it was already in the decision type).
