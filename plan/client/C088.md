## Goal
Invite links (/j/<token> and /i/<token>) work in the browser: preview without signing in, accept after signing in, hand off to the desktop app via centcom:// with a confirmation, and keep E2E key material only in the URL fragment.

## In scope
- Routes in apps/web/src/invite/: `/j/:token` (join a session) and `/i/:token` (workspace invite), calling `GET /v1/invites/{token}` for the public preview (workspace name, inviter, role, expiry).
- Fragment handling: read `#k=<base64url>` once into memory, immediately `history.replaceState` to remove the fragment; the key is never sent to any server, logged, or stored.
- Actions: 'Open in Centcom' (builds `centcom://join/<token>` or `centcom://invite/<token>`), 'Continue in browser' (sign in via C082 then `POST /v1/invites/{token}/accept`, then `GET /v1/invites/{token}/key-bundle` once and open it with the fragment key).
- Share link guests: `POST /v1/share-links/{token}/join` as limited viewer without an account (route `/g/:token` documented as web twin; see notes).
- Neutral error states for expired, revoked, used and malformed tokens; no detail leakage.
- Deep-link parser/validator `parseDeepLink(url)` for centcom:// and https://centcom.dev forms of CT-DEEPLINK (join, session, auth callback, billing, invite) used by the web app.

## Out of scope
- OS protocol-handler registration for centcom:// (C094) and CLI handling of the link.
- Workspace and member admin UI (C087), session view (C083).
- Creating invites (C087) and uploading key bundles (host client).
- Sealed-box opening primitive (C056); this lane calls it.

## Acceptance criteria
1. Loading /j/<token>#k=… calls GET /v1/invites/{token} with no fragment in the request URL (network log assertion) and `location.hash` is empty within the same tick after read.
2. Token regex: 160-bit URL-safe (>= 27 base64url chars); malformed tokens show the neutral error without any network call.
3. Expired/revoked/used invites show one neutral message ('This invite isn't valid anymore') with 'Ask for a new link'; the page text never reveals which of the three.
4. 'Open in Centcom' navigates to `centcom://join/<token>` (fragment key is not included; the desktop app asks the user to paste or receives it via the key bundle path) and the page remains usable if no handler opens within 1.5 s.
5. Accept flow: accept -> fetch key-bundle once -> open with fragment key -> proceed to /s/:id; a second visit gets a neutral error since the bundle is deleted on acceptance.
6. Unknown query parameters are ignored; `focus` accepts only `approval|queue`; invalid values are dropped, not errors.
7. No `Referrer` leakage: pages set `Referrer-Policy: no-referrer`; outbound links use rel=noopener noreferrer (header test).
8. axe 0 serious/critical on all invite states; flow works keyboard-only.

## Guardrails (MUST / MUST NOT)
- MUST NEVER send, log, store, or place in any URL/query the fragment key `k`; hold it in memory only until the bundle is opened, then zero the buffer.
- MUST show a confirmation before acting on any link ('Join <name>'s session?') and MUST NOT perform destructive actions from a link.
- MUST validate every parameter; invalid links show a neutral error, never the parse failure detail.
- MUST NOT auto-accept an invite on page load; acceptance requires an explicit click after sign-in.
- Preview content (names) is untrusted: render as text only.

## Failure modes
- Preview 404/410 -> neutral invalid-invite state.
- Key bundle missing but session joinable -> join in `waiting_for_key` state with the host-grant fallback copy.
- Accept succeeds but key-bundle fetch fails (network) -> retry up to 3 times with backoff; leave the user in the session with 'Waiting for the host to let you in'.
- 429 on share-link join -> show Retry-After countdown.
