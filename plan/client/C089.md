## Goal
Owners and billing admins can see their plan, usage and limits, upgrade, change seats with a prorated preview, open the billing portal, and view invoices, in calm, exact, mascot-free screens.

## In scope
- Routes in apps/web/src/billing/: `/billing` (overview), `/billing/plans`, `/billing/seats`, `/billing/invoices` using GET /v1/plans, GET /v1/workspaces/{id}/subscription, POST .../checkout, POST .../portal, PATCH .../seats?preview=true, GET .../invoices, GET .../usage/summary, GET .../entitlements, POST .../coupons/redeem.
- Plan badges FREE/PRO/TEAM (DESIGN.md 17), usage meters per metered limit with pixel pips for seats (`■■■□□`), persistent meter in settings, 80 % warning banner and 100 % firm banner from `warnings[]` and `usage` vs `limits` (CT-ENTITLEMENTS).
- Checkout: POST checkout with required Idempotency-Key, redirect to returned `url`; return page re-fetches entitlements until `rev` changes (poll max 30 s).
- Seat changes with proration preview (`?preview=true`) shown before confirm; total with currency, period and tax status always visible before a spend button.
- Status handling: `active`, `trialing`, `past_due` (grace until `grace_until`), `canceled` (until period end), `none`; banners and copy per CT-ENTITLEMENTS §4.
- Entitlement cache: 5 min TTL, refetch when token `ent` claim changes or on `plan_changed` notice.

## Acceptance criteria
1. Money is rendered from integer minor units via Intl.NumberFormat with the ISO currency; a test with amounts 1900 USD and 1900 EUR shows `$19.00` / `19,00 €` (locale-dependent) and no float arithmetic anywhere (lint ban on `* 0.01`).
2. A limit of `null` renders 'Unlimited', `0` renders 'None'; unknown limit keys are displayed read-only and never used to unlock anything.
3. At `warnings[].pct = 80` a warning banner with `!` glyph appears; at usage >= limit a firm banner appears; both are persistent and not dismissible until resolved; max 2 banners stacked.
4. Seat change flow: preview call shows proration amount; confirm sends PATCH without `preview` and an Idempotency-Key; cancel path takes the same number of clicks as subscribe (<= 3 each, asserted in a Playwright-less click-count test).
5. Checkout button disabled with tooltip reason for roles other than owner/billing; calling anyway returns 403 `forbidden` handled as toast.
6. After return from checkout, UI polls entitlements every 2 s up to 30 s until `rev` increases, then shows 'Plan updated'; mascot is not present on any billing route (only static `upgrade_pro` art may show after confirmed success, if at all).
7. `past_due` shows grace countdown from `grace_until` and an action 'Update payment method' opening the portal; after grace shows free behaviour.
8. Lighthouse a11y >= 95; all numbers use tabular figures and are right-aligned in tables.

## Guardrails (MUST / MUST NOT)
- MUST NOT use dark patterns: no upgrade modal over active work, prompts only on limit hit or when billing is opened (DESIGN.md 17.1).
- MUST show total, currency, period and tax status before any button that spends money.
- MUST NOT read plan names or Stripe state to gate features; gate only on entitlement keys (CT-ENTITLEMENTS).
- MUST NOT put card data or payment fields in our DOM; checkout and portal are hosted URLs only; the CSP must not be loosened for them (navigate, do not embed).
- No mascot and no jokes on payment surfaces; `payment_failed` is plain card icon, calm text, one action.
- Checkout and seat POSTs MUST carry Idempotency-Key.

## Failure modes
- Checkout 409 `idempotency_conflict` -> regenerate key only after user re-initiates; show 'Try again'.
- Entitlements fetch fails -> show last known (<= 24 h) marked 'as of <time>' for display only; actions still try the server.
- 429 `quota_exceeded` on creates elsewhere -> deep link here with the reset date from `retry_after_s`.
