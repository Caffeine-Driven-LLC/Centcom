## Goal
Pair a guest with a LAN host using a short code and a real PAKE (CPace over ristretto255), so a wrong or eavesdropped code never yields the session key, and remember trusted devices with TOFU for reconnects.

## In scope
- Pairing code: 8 characters from the alphabet `A-Z` and `2-9` without `0 O 1 I L` (shown `ABCD-EFGH`), CSPRNG-generated, valid 5 minutes, one successful use per guest, at most 5 attempts per code.
- CPace (draft-irtf-cfrg-cpace, ristretto255 + SHA-512, libsodium via the C056 wrapper) with channel identifiers = host session id and both device fingerprints; derive `ISK`; exchange key-confirmation MACs; constant-time verification.
- Wire messages `lan.pair.1`..`lan.pair.4` and `lan.pair.err {code}` exactly as in schemas/lan-pair.schema.json (guest: `cpace_msg`, device {id,x25519,ed25519,name}, fp; host: `cpace_msg`, device, fp; guest `confirm`; host `confirm`, `ok:true`, member, session {sid,name,policy}), validated at the boundary.
- Host-side `HostPairing` state machine per connection and guest-side `GuestPairing`, both transport-agnostic over a `TextChannel` interface; host implements the `PairingHandler` expected by lane C072.
- Failure policy: wrong code -> `lan.pair.err {code:'bad_code'}` then close 4403; 5 failed attempts for a code -> code invalidated; a source IP with repeated failures is banned for 10 minutes (`BanList`).
- After success: trust store entries (device id -> x25519/ed25519, fingerprint) kept for the session lifetime; a 256-bit per-session reconnect token issued in `lan.pair.4`, stored in memory and (guest side) in the keychain, validated later via `TokenValidator` so reconnects skip pairing; after confirmation, emit `paired` with the guest's keys so the engine can send the sealed `key.grant` (grant creation itself is lane C056/C057 territory).

## Out of scope
- Session key grants and encryption: lane C056 (and the host engine lane C075 sending `key.grant`).
- The WebSocket server and sequencing: lane C072. mDNS: lane C071. UI for showing/entering the code and fingerprint comparison: TUI lanes.
- Internet-scale PAKE or account-based trust: not in v1.

## Build against (no counterpart needed)
Pure library over an in-memory `TextChannel` pair; no sockets, no backend. Test vectors: the CPace draft's ristretto255 appendix vectors plus the lan.pair fixtures in contracts/fixtures/lan/ (valid run, wrong code, replayed message, truncated message); device keys from lane C056's test helpers.

## Acceptance criteria
1. Generated codes are exactly 8 characters from the 31-character alphabet, never contain 0, O, 1, I or L, and 10 000 samples show a roughly uniform distribution (chi-square p > 0.001); `normalizeCode('abcd-efgh')` returns `ABCDEFGH`; characters outside the alphabet return null.
2. Correct code: guest and host complete lan.pair.1-4 over the in-memory channel, derive equal `ISK`, both confirmations verify, host emits `paired` with the guest's device keys, and the guest receives a 256-bit (43-char base64url) reconnect token.
3. Wrong code: the host sends `lan.pair.err {code:'bad_code'}` and closes 4403; no confirmation MAC is revealed; the same ISK is never derived (assert different ISK values / failed confirmation on both sides).
4. After 5 failed attempts on one code, the 6th attempt with the CORRECT code is rejected (code invalidated); the source IP is on the BanList and `isBanned(ip)` is true for 10 minutes and false after 10 min + 1 s (fake clock).
5. A code is valid for 5 minutes: at 5 min + 1 s a correct code fails with `expired`; a second guest using an already-consumed code fails (one use per guest).
6. CPace known-answer test from the draft's ristretto255 appendix produces the expected `ISK` for the fixed inputs; replaying a recorded `lan.pair.1` against a fresh host state fails confirmation.
7. Channel binding: a MITM that relays messages between a guest and host with different fingerprints/session ids in the transcript causes confirmation failure; if `expectedFingerprint` (from mDNS) differs from the host's actual `fp`, `guestPair` rejects with `FingerprintMismatchError` before sending confirmation.
8. Reconnect: `validate(token, ip)` accepts a valid token once per connection attempt and rejects tokens after `revoke`, after session end, and tokens with one flipped bit; comparison is constant-time.
9. Messages that fail the lan-pair schema (missing `cpace_msg`, wrong lengths, extra huge field > 4 KiB) are rejected with `protocol` failure without throwing; fuzz of 10 000 random messages never crashes.
10. No log line or error contains the code, ISK, confirmation MACs or token; the trust store keeps only public keys and fingerprints.
11. The CPace implementation reproduces the IRTF draft test vectors for CPACE-RISTR255-SHA512 and rejects a wrong pairing code with `lan.pair.err bad_code` without revealing which side failed.

## Tests required
- pairing/code.test.ts: alphabet, uniformity, normalisation, expiry, attempt counting.
- pairing/cpace.test.ts: draft known-answer vectors, wrong-password divergence, invalid group element rejection (identity point, non-canonical encoding).
- pairing/flow.test.ts: full 4-message flow, wrong code, replay, reordering, truncation, timeouts.
- pairing/ban.test.ts: 5-attempt limit and 10-minute IP ban on a fake clock.
- pairing/tokens.test.ts: issue/validate/revoke, constant-time path, persistence of guest token in keychain fake.
- pairing/binding.test.ts: MITM and fingerprint-mismatch scenarios.
- pairing/redaction.test.ts: secrets never in logs or errors.

## Guardrails (MUST / MUST NOT)
- MUST use CPace (balanced PAKE) over ristretto255 with libsodium; MUST NOT send the code or a hash of it, MUST NOT implement a home-made PAKE, and MUST reject identity/low-order group elements and non-canonical encodings.
- MUST bind the exchange to the host session id and BOTH device fingerprints and MUST verify key-confirmation MACs in constant time before trusting the peer or issuing any key grant.
- MUST enforce: code TTL 5 minutes, one use per guest, 5 attempts per code, 10-minute IP ban after repeated failure; counters live on the host and survive reconnects of the same socket.
- MUST NOT log, display in errors or persist the pairing code, ISK, MACs or reconnect tokens; the code is shown only by the host UI and kept in memory.
- MUST generate codes and tokens from the platform CSPRNG and tokens as >= 256 bits; MUST store the guest-side token only in the OS keychain (and memory).
- MUST treat a changed key for an already-trusted device id as a warning result (TOFU violation), never a silent overwrite.
- MUST NOT send `key.grant` itself; it only signals `paired` after successful confirmation.
- MUST use the pinned CPace parameters in CT-LAN section 2 (suite CPACE-RISTR255-SHA512, DSI CPaceRistretto255, CI = lv(host fp) || lv(guest fp) || lv(sid), key confirmation BLAKE2b-256 keyed with ISK) and the libsodium sumo build.

## Failure modes
- Guest disconnects mid-handshake -> the half-open state is discarded after 10 s; the attempt counts as failed only if a `lan.pair.3` with a bad confirm was received.
- Clock change during code validity -> expiry uses a monotonic clock; a backwards jump never extends validity.
- Fingerprint from mDNS disagrees with the one in lan.pair.2 -> abort with FingerprintMismatchError and tell the user to verify out of band.
- Host restarted -> reconnect tokens are invalid (session ended); guests must pair again with a new code.
