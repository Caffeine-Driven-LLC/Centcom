## Goal
Performance regressions are caught automatically: the client has written budgets for startup, TUI frame time, transcript scrolling, crypto, resume and memory, a repeatable benchmark suite, and a CI job that fails on regressions.

## In scope
- Benchmark harness in tools/bench/ (tinybench + a pty-driven startup runner) writing `bench-results.json` and comparing to a committed `tools/bench/baseline.json` with per-metric budgets.
- Benchmarks: cold/warm `centcom --version`; time to first prompt in the TUI; keypress-to-paint latency; transcript scroll with 10 000 messages (virtualised, C036); mascot half-block redraw (C033); diff view render of a 5 000-line diff (C037); envelope encode/validate; XChaCha20-Poly1305 encrypt/decrypt of 4 KiB and 192 KiB payloads and Ed25519 sign/verify (C056); resume replay of 5 000 frames (C055); guest reducer throughput (C076); memory (RSS) after 10 000 messages.
- Budget document docs/perf/BUDGETS.md listing every metric, its budget, the reference machine definition (4 vCPU / 8 GB CI runner) and normalisation rule (ratio to a calibration loop).
- CI integration scripts: PR job runs the fast subset (<= 3 min) and posts a table; nightly runs the full set and tracks a trend file `perf-history.json`.
- Web budgets check (bundle gzip sizes, Lighthouse scores) imported from the web build report (C081, C093), not re-measured here.

## Out of scope
- Optimising code found slow (the owning lane fixes it).
- Load testing the backend.
- Production telemetry for perf (CT-TELEMETRY `perf.startup`/`perf.frame` are emitted by C010).
- Web e2e suite (C093).

## Build against (no counterpart needed)
All benchmarks run locally against in-process fixtures and the mock backend (lane C007); no network or real relay.

## Deliverables
- `tools/bench/`
- `docs/perf/`

## Interfaces (the only surface other lanes may use)
- pnpm bench [--fast] [--filter <name>] [--update-baseline]  // writes bench-results.json, exit 1 on any budget breach
- bench-results.json: {schema_version: 1, machine: {cpu, cores, node}, calibration_ms, results: [{id, unit: 'ms'|'ops/s'|'MB', p50, p95, max, budget, status: 'pass'|'fail'|'regressed', baseline}]}
- pnpm bench:compare <a.json> <b.json>  // prints table; used in PR comments

## Acceptance criteria
1. Budgets enforced (p95 on the reference runner): `centcom --version` cold <= 250 ms, warm <= 150 ms; time to first interactive prompt <= 600 ms; keypress-to-paint <= 50 ms; mascot redraw <= 2 ms; transcript scroll frame <= 16 ms with 10 000 messages; 5 000-line diff first paint <= 300 ms.
2. Crypto budgets: encrypt+sign a 4 KiB frame <= 1 ms, 192 KiB frame <= 8 ms; verify+decrypt equal; 1 000 frames/s sustained on one core.
3. Resume: replay 5 000 buffered frames to a reduced state <= 1.5 s; guest reducer >= 20 000 frames/s.
4. Memory: RSS <= 300 MB after loading a 10 000-message transcript with 4 agents and 8 members; no growth > 5 % over 10 000 further delta frames (leak check).
5. A synthetic 25 % slowdown injected into the transcript renderer makes `pnpm bench --fast` exit 1 and name the metric (self-test).
6. Result noise: coefficient of variation <= 10 % across 5 runs for each fast metric; benchmarks failing this are marked `unstable` and excluded from gating until fixed.
7. The PR job finishes in <= 3 min; the nightly job in <= 20 min and uploads `perf-history.json`.
8. Baseline updates require `--update-baseline` plus a justification line in the commit message (checked by a CI script).

## Tests required
- bench.compare.test.ts (regression detection logic).
- bench.normalisation.test.ts (calibration ratio).
- bench.selftest.regression.test.ts (injected slowdown).
- bench.schema.test.ts for bench-results.json.
- bench.stability.test.ts (CV calculation).

## Guardrails (MUST / MUST NOT)
- MUST measure on fixed inputs (seeded data, fixed terminal size 120x40) and report p95 over >= 30 samples after warm-up; never a single run.
- MUST NOT use production data or real credentials in benchmarks; fixtures only.
- MUST gate on normalised ratios (to a calibration loop) rather than absolute ms when running on shared CI runners, but still print absolute ms.
- Budgets MUST NOT be loosened without an entry in docs/perf/BUDGETS.md changelog and approval from the owning lane's reviewer.

## Failure modes
- Runner too noisy (calibration deviates > 30 % from baseline) -> mark run `inconclusive`, rerun once, then warn without failing.
- A benchmark target lane has not landed yet -> metric `skipped` with reason; release gate (C100) fails if any required metric is skipped.
- pty unavailable on the runner -> startup benchmarks fall back to child_process timing with a note.
