## Goal
Let the CLI log a user in with the OAuth device flow, keep the refresh token only in the OS keychain, and hand every other lane a valid 15-minute access token that refreshes itself safely, even with several centcom processes running.

## In scope
- Device authorization grant client (RFC 8628) against POST /v1/auth/device/code and POST /v1/auth/token with `client_id` `centcom-cli` (or `centcom-tui`), scope string = CLI default from CT-AUTH, `device_name`, and `device_pubkeys {x25519, ed25519}` obtained from an injected `DeviceKeyProvider`.
- Polling loop: `interval` from the response (5 s), `slow_down` adds 5 s permanently, `authorization_pending` continues, `access_denied` and `expired_token` end the flow; hard stop at `expires_in` (10 min); cancellable by AbortSignal.
- Authorization-code + PKCE (S256 only) primitives for desktop: verifier/challenge/state generation, authorize URL builder, `completeFromCallbackUrl('centcom://auth/callback?code=..&state=..')` with exact state check; used by the web lane and by an optional `--browser-pkce` CLI path. Registering the URL scheme is out of scope.
- `KeychainTokenStore` on `@napi-rs/keyring` (service `centcom`, account `refresh:<api-host>`) storing the refresh token, device id (`dev_`) and api host; access tokens in memory only.
- `TokenManager`: `getAccessToken()` single-flight refresh when the access token has < 60 s left or the API said `token_expired`; handles rotation (new refresh token on every use) and writes the rotated token to the keychain before releasing the new access token; cross-process lock around refresh.
- Decoding (not verifying) the access-token JWT for `exp`, `sub`, `dev`, `wsp`, `plan`, `ent`; emits `ent-changed` when the `ent` claim changes (consumed by C064).
- Logout: POST /v1/auth/revoke on the refresh token, then clear keychain and memory; works offline by clearing local state and reporting that server revocation was skipped.
- API-key principal: accept a `cen_live_`/`cen_test_` key from a provided secret source and expose it through the same `getAccessToken()` surface.

## Out of scope
- login/logout/whoami/devices commands and their output: lane C053.
- Device key generation and private-key storage: lane C056 (this lane only consumes a `DeviceKeyProvider` interface).
- The HTTP client itself (retry, headers): lane C051. Web-app token handling (in-memory + HttpOnly cookie): lane C082.
- Registering the centcom:// URL scheme with the OS: lane C094.

## Build against (no counterpart needed)

## Interfaces (the only surface other lanes may use)
- `interface DeviceKeyProvider { getOrCreatePublicKeys(): Promise<{ x25519: string; ed25519: string }> /* base64url, 32 bytes each */ }`
- `startDeviceLogin(opts: { http: HttpClient; deviceName: string; clientId?: 'centcom-cli'|'centcom-tui'; scopes?: string; keys: DeviceKeyProvider }): Promise<DeviceLogin>`; `DeviceLogin = { userCode: string /* ABCD-EFGH */; verificationUri: string; verificationUriComplete: string; expiresInS: number; intervalS: number; poll(signal?: AbortSignal): Promise<TokenSet> }`
- `interface TokenStore { load(): Promise<StoredAuth | null>; save(a: StoredAuth): Promise<void>; clear(): Promise<void> }` with `StoredAuth = { refreshToken: string; deviceId: string; apiHost: string }`; `createKeychainTokenStore(apiHost: string): TokenStore`
- `class TokenManager { constructor(o: { http: HttpClient; store: TokenStore; clock: Clock; lockDir: string }); getAccessToken(): Promise<string>; forceRefresh(): Promise<void>; claims(): AccessClaims | null; logout(o?: { allDevices?: false }): Promise<{ serverRevoked: boolean }>; on(ev: 'auth-required' | 'refreshed' | 'ent-changed', fn): () => void }`
- `pkceStart(o: { redirectUri: 'centcom://auth/callback'; clientId: string; scopes: string }): { url: string; state: string; verifier: string }`; `pkceComplete(callbackUrl: string, pending): Promise<TokenSet>`
- Errors: `AuthRequiredError`, `DeviceFlowDeniedError`, `DeviceFlowExpiredError`, `KeychainUnavailableError` (local classes extending the C006 base)

## Acceptance criteria
1. Against the mock configured pending x3 then success, `poll()` issues token requests at t=5, 10, 15, 20 s (fake clock) and resolves with a TokenSet; the request body carries the device-code grant type `urn:ietf:params:oauth:grant-type:device_code`.
2. When the mock answers `slow_down` once, every following poll interval is 10 s (5 + 5) and stays 10 s.
3. `access_denied` rejects with DeviceFlowDeniedError after exactly one request; `expired_token`, or reaching `expires_in` (600 s), rejects with DeviceFlowExpiredError and no request is made after the deadline.
4. The device/code request body contains `device_pubkeys.x25519` and `.ed25519` as 43-char base64url strings (32 bytes), `client_id` `centcom-cli` and the default CLI scope string.
5. After login the keychain contains the refresh token and no plaintext token file is written anywhere (test scans the temp HOME and config dir); the access token is never persisted.
6. Ten concurrent `getAccessToken()` calls with an expired token produce exactly one refresh request to the mock; the mock's rotated refresh token is saved to the store before the first caller resolves.
7. Two TokenManager instances sharing one lockDir and one store, both expired, produce exactly one refresh request in total and the second instance reads the rotated token from the store after acquiring the lock (no `refresh_reuse_detected`).
8. A refresh answered with `refresh_reuse_detected`, `token_revoked`, `token_invalid` or `device_revoked` clears the store, emits `auth-required` once and makes `getAccessToken()` throw AuthRequiredError without further requests; a network error during refresh keeps the stored token and retries on the next call.
9. Refresh is attempted when the token has < 60 s left; a token with 61 s left is returned without a request.
10. PKCE: authorize URL contains `code_challenge_method=S256`, a 43+ char challenge, and `redirect_uri=centcom://auth/callback`; `pkceComplete` rejects a callback whose `state` differs (constant-time compare) before any network call.
11. `logout()` while the mock is unreachable clears the keychain and resolves `{serverRevoked:false}`; while reachable it calls POST /v1/auth/revoke once.

## Tests required
- auth/device-flow.test.ts: pending/slow_down/denied/expired/abort timeline tests on a fake clock.
- auth/token-manager.test.ts: single-flight, rotation write-ordering, early-refresh window, terminal-error clearing, offline-error retention.
- auth/refresh-lock.test.ts: two processes (child_process) racing on a stale lock; lock auto-expires after 10 s; no deadlock.
- auth/keychain-store.test.ts: round-trip with the fake; real keyring test gated by CENTCOM_TEST_KEYCHAIN; unavailable keyring raises KeychainUnavailableError.
- auth/pkce.test.ts: RFC 7636 test vectors for S256 challenge; state mismatch; code replay.
- auth/logging.test.ts: capture logger output during a full login+refresh and assert no token, code or key substring appears.

## Guardrails (MUST / MUST NOT)
- MUST store refresh tokens only in the OS keychain; if the keychain is unavailable MUST refuse to persist (keep the session in memory for this process and tell the user) and MUST NOT fall back to a file, config or env-written plaintext.
- MUST write the rotated refresh token to the store BEFORE using the new access token; MUST NOT discard a rotated token because a later step failed (reuse detection would revoke the whole family).
- MUST serialise refresh across processes with a lock and MUST re-read the store after taking the lock; MUST NOT send the same refresh token twice.
- MUST NOT log, print or include in errors any access token, refresh token, device_code, PKCE verifier, auth code or API key; the user_code and verification URI may be printed by C053 only.
- MUST NOT trust decoded JWT claims for authorisation decisions; claims are for scheduling (`exp`) and cache invalidation (`ent`) only. The server is the authority (CT-RBAC).
- MUST use PKCE `S256` only, never `plain`; MUST compare `state` in constant time; MUST NOT accept tokens from URLs other than the one-time `code` in the callback.
- MUST NOT require the backend for LAN or local-only use: constructing a TokenManager must perform no I/O, and a missing login must surface as AuthRequiredError only on code paths that need the backend.

## Failure modes
- User never approves -> poll ends at `expires_in` with DeviceFlowExpiredError and a message telling them to rerun login; no leaked timers.
- Keychain locked or missing (headless Linux without secret service) -> KeychainUnavailableError with remediation text; login completes in memory for that process only.
- Clock skew > 60 s makes the server reject a fresh token -> one forced refresh, then AuthRequiredError rather than a loop.
- Lock holder crashed -> lock considered stale after 10 s and taken over; the refresh then proceeds.
- Server rate-limits auth endpoints (20/min/IP) -> honour Retry-After via the C051 retry layer; polling never goes below the server `interval`.
