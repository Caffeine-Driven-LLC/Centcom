## Goal
Provide the command-post queue client: guests submit, track and cancel items; the host approves, rejects, reorders, drops, claims and completes them; every client derives the same queue from sequenced frames.

## In scope
- Submit: new `que_` ULID used as the frame `id`, hybrid `queue.submit` with cleartext `p {item,size,kind:'message'|'command'}` and encrypted `{body, attachments?}`; `size` = ciphertext bytes, <= 192 KiB checked locally.
- Cancel (`queue.cancel`, own item while `queued` or `approved`).
- Host controls: `queue.approve`, `queue.reject {item, code:'not_now'|'off_topic'|'unsafe'|'duplicate'|'other'}` (+ encrypted `note`), `queue.reorder {order[]}`, `queue.drop`, `queue.claim {item, agent_id}`, `queue.done {item, outcome:'ok'|'error'|'canceled'}`.
- Queue model: a reducer over sequenced `queue.*` frames plus authoritative `queue.state {version, items}` snapshots; per-item state machine (queued, approved, running, done, failed, canceled, rejected, dropped, held), position derived from frame order, last-reorder-by-seq wins.
- Local pre-checks mirroring server rules for UX only: viewer, muted, locked session, 5 live items per member, `control.policy.queue_limit` (default 20); server error handling for `queue_full`, `queue_item_gone`, `forbidden`.
- Idempotent resubmit: submit survives reconnect through the C055 outbox with the same item id; the model treats the echo as the confirmation.

## Out of scope
- What the host does when an item is claimed (running agents): lane C075 and the agent lanes.
- Auto-approval decisions (the relay or LAN host emits the approve frame): lanes C072/C075.
- Queue UI: TUI lanes. Control frames (kick/mute/policy): lane C060.
- Encryption/signing mechanics: lane C056 via the session client (C057).

## Interfaces (the only surface other lanes may use)
- `new QueueClient(session: SessionHandle, opts?: { now?: () => Date })`
- `submit(o: { body: string; kind?: 'message'|'command'; attachments?: Attachment[] }): Promise<{ item: string; seq: number }>`; `cancel(item: string): Promise<void>`
- Host only: `approve(item)`, `reject(item, code, note?)`, `reorder(order: string[])`, `drop(item)`, `claim(item, agentId)`, `done(item, outcome)`; each rejects `NotHostError` locally when `session.me.role !== 'host'`
- `snapshot(): QueueView = { version: number; items: QueueItem[] }`, `QueueItem = { id; submitter: string; state: QueueItemState; position: number | null; size: number; kind; body?: string; ts: string }`; `on('changed', (v: QueueView) => void)`, `on('rejected', ...)`, `on('error', ...)`
- `type QueueItemState = 'queued'|'approved'|'running'|'done'|'failed'|'canceled'|'rejected'|'dropped'|'held'` (unknown values tolerated as 'queued')

## Acceptance criteria
1. `submit()` emits one `t:'queue'` frame with `k:'queue.submit'`, `id` = the returned item id (`que_` ULID), `p.size` equal to the byte length of the decoded `ct.c`, and a `ct` that decrypts to `{body}`; the relay simulator sees no body text.
2. Retrying a submit after a forced reconnect leaves exactly one item in the simulator queue (replayed `queue.submit` is a no-op) and the client model has one item.
3. A body whose ciphertext would exceed 192 KiB rejects locally with `QueueItemTooLargeError` before any frame is sent.
4. A viewer, a muted member, or a locked session gets a local `NotAllowedError` with the reason; with the pre-check bypassed the server `forbidden` is mapped to the same error class.
5. The 6th live item from one member is blocked locally, and if forced, the simulator's `queue_full` becomes `QueueFullError`.
6. Host `approve` -> `claim` -> `done` moves the item queued -> approved -> running -> done on both host and guest models with identical `version` and order after the same frames are replayed from seq 1 (deterministic reducer).
7. Two concurrent `reorder` frames: the model applies the one with the higher `seq` on both clients; `queue.state` with a higher `version` replaces local state wholesale.
8. Cancel of an item already `running` is refused locally; cancel of an item approved by the host a moment earlier but arriving later gets the `queue_item_gone` sys.error mapped to a non-fatal `ItemGoneError`, and the model stays consistent.
9. Non-host calling `approve` throws NotHostError without sending; a forged `queue.approve` from a guest observed by the host client is ignored (sender role check using the roster) and logged at warn.
10. Host disconnect: the model shows `approved`/`running` items as `held` after `control.session_state {state:'paused'}` and returns them to their states on `live`.

## Guardrails (MUST / MUST NOT)
- MUST NOT put the queue body, attachment names or reject note in cleartext `p` (privacy budget, CT-WS-SESSION-EVENTS); only `item,size,kind` are clear.
- MUST derive position only from sequenced frames and `queue.state`; MUST NOT order items by local time or arrival order of REST calls.
- MUST generate the `que_` id client-side as a monotonic ULID and reuse it on every resend (idempotency key).
- MUST NOT trust the sender role claimed in a frame: the host client applies a received host-only queue frame only if its `from` is the current host in the roster; otherwise ignore and log.
- Local pre-checks are UX only; MUST still surface the server's authoritative error and MUST NOT retry a `forbidden`/`queue_full`.
- MUST NOT show non-host items' bodies in UI-facing models to other editors when `body` is marked hidden by policy; do not rely on this for confidentiality (CT-WS-QUEUE rule 9).

## Failure modes
- Unknown queue item referenced by `queue.state` or a frame -> create a placeholder in state `queued` flagged `unknown:true` and request nothing; heal on the next `queue.state`.
- Echo never arrives for a submit -> the C055 outbox resends; after `stuck` the item is shown as `pending-send` and can be cancelled locally.
- Undecryptable item body -> item appears with `body: undefined`, state still tracked.
- Unknown future queue kind -> ignored, acked, debug-logged.
