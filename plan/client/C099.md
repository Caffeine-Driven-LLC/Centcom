## Goal
The client repository has an enforced security baseline: secret scanning, dependency and licence policy, no install scripts, pinned and provenance-signed builds, an SBOM per release artifact, and a written threat model with a review checklist for secrets, sandbox and supply chain.

## In scope
- Security scripts in tools/security/ wired as `pnpm security:check`: secret scan config (gitleaks rules incl. `cen_live_`, `cen_test_`, JWT, private key patterns), dependency audit (`pnpm audit --prod --audit-level=high`), licence allow-list check (MIT, Apache-2.0, BSD-2/3, ISC), install-script detector, exact-version pinning check, lockfile integrity check.
- SBOM generation: CycloneDX JSON per release artifact (`tools/security/sbom.ts`) including the Node runtime version embedded in the SEA binary; attached to the release; plus npm provenance flags (`--provenance`) for published packages.
- CI hardening checks: GitHub Actions pinned by full commit SHA, workflow `permissions:` least privilege, no `pull_request_target` with checkout of PR code, secrets never echoed, third-party actions allow-list.
- Threat model docs/security/client-threat-model.md (assets: device private keys, refresh tokens, session keys, decrypted transcripts; actors: malicious guest, malicious relay, compromised update channel, local malware, malicious repo content/prompt injection) with mitigations mapped to lanes.
- Review checklist docs/security/review-checklist.md and automated verification tests: keys/tokens only in OS keychain (scan config dirs after login), log redaction fuzz, agent command sandbox/permission engine review (C015, C016), update signature verification (C068, C095), crypto vector run (C056), web CSP and token storage (C081, C082).
- Dependency update policy (Renovate/Dependabot config in tools/security/) with grouped weekly PRs and a 7-day cooldown for new major versions.

## Out of scope
- Fixing findings inside other lanes (raised as issues against the owning lane).
- Backend and infrastructure security review.
- Penetration testing by third parties (scheduled separately).
- Code signing key management (ops).

## Build against (no counterpart needed)
Runs entirely locally/CI on the repo tree and built artifacts; auth/crypto behaviours exercised via the mock backend (lane C007) and fixtures/crypto vectors.

## Deliverables
- `tools/security/`
- `docs/security/`

## Interfaces (the only surface other lanes may use)
- pnpm security:check [--fast]  // exit 1 on any high finding; writes security-report.json
- pnpm sbom --artifact <path> --out <file.cdx.json>
- security-report.json: {schema_version: 1, checks: [{id, status: 'pass'|'fail'|'waived', findings: [{severity, location, message}]}], waivers: [{id, issue, expires}]}
- tools/security/waivers.json: waivers must carry an issue URL and an expiry date <= 90 days

## Acceptance criteria
1. A planted fake `cen_live_` key, JWT and PEM private key in a test branch are each detected by the secret scan (3 of 3) and fail the job; a clean tree passes.
2. `pnpm security:check` fails when any workspace package declares `install`, `preinstall` or `postinstall` scripts (planted test) and when any dependency version uses `^`, `~` or `latest`.
3. Licence check fails on a planted GPL-3.0 dependency fixture and passes on the allow-list; unknown licences fail closed.
4. SBOM for each of the 5 release artifacts validates against the CycloneDX 1.5 JSON schema and lists >= 1 component with a purl and hash for every bundled dependency; includes `node` with the exact runtime version.
5. After a scripted login against the mock, a scan of the user config/state directories finds no refresh token, access token, private key or session key (fixtures contain known markers; 0 matches).
6. Log redaction fuzz: 10 000 random strings seeded with token/key/path patterns produce 0 leaks in logger output (property test shared with C005).
7. Workflow lint rejects an action referenced by tag instead of SHA and a workflow lacking an explicit `permissions:` block.
8. Threat model lists each asset with at least one mitigation and an owning lane; checklist items are all checkable by a script or have an owner and date in `docs/security/review-log.md`.

## Guardrails (MUST / MUST NOT)
- MUST fail closed: a tool that cannot run (missing binary, network error) is a failed check, never a pass.
- MUST NOT store real secrets in fixtures; markers are synthetic and clearly labelled.
- Waivers MUST have an issue link and expire within 90 days; expired waivers fail the check.
- MUST NOT upload SBOMs, reports or source to third-party services without an explicit, documented allow-list entry.
- Review findings with severity high block the release gate (C100) until fixed or waived.

## Failure modes
- Audit service unreachable -> retry 3 times, then fail with a distinct `tool_unavailable` finding (not a pass).
- False positive in secret scan -> allow via path+rule entry in the scanner config with a comment; never by disabling the rule.
- SBOM tool lacks a component's hash -> record `unverified` and fail for runtime dependencies.
