## Goal
Run the relay's job on a LAN: a WebSocket server in the host client that accepts guests, completes the `sys.hello`/`sys.welcome` handshake with local reconnect tokens, assigns sequence numbers, fans frames out, replays history and enforces the same limits and close codes as the hosted relay.

## In scope
- `LanHostServer` on the `ws` library: subprotocol `centcom.v1`, plain `ws://`, bind all interfaces by default, `--bind <ip>` to restrict, port 7070 with random-port fallback; refuses a public bind unless `allowWan` (then logs a warning); max payload 256 KiB; max 8 members.
- Connection lifecycle: hello within 5 s (else close 4408); optional pre-hello pairing frames `lan.pair.1..4`/`lan.pair.err` handed to an injected `PairingHandler`; `sys.hello` with `ticket` = LAN reconnect token validated by an injected `TokenValidator`; `sys.welcome` with `protocol:1`, caps, `member {id,name,slot,role}`, `roster_v`, `heartbeat {ping_ms:20000, dead_ms:50000}`, `server_time`, `limits`, `resume`; supersede an older connection of the same (member, device) with `sys.bye reason=superseded` and close 4409.
- Sequencing: strictly increasing `seq` from 1 per session across `event`, `queue` and `control` frames in arrival order; stamp `from` (sender member) and `ts` (RFC 3339 ms UTC); echo to the sender with `seq`; fan out to every connected member; de-dup by `(sid, from, id)` for 24 h; ephemeral presence frames never sequenced.
- Resume: replay buffer in memory of >= 5 000 frames or 10 minutes (whichever is larger) plus an append-only local transcript file (JSONL, mode 0600); on `last_seq` inside the buffer replay then `sys.resumed {from_seq,to_seq,count}`, else `sys.resumed {snapshot_required:true, snapshot_seq}`; serve `lan.snapshot.get` through an injected `SnapshotProvider`.
- Heartbeat and limits: server `sys.ping` every 20 s, close after 50 s silence; sequenced 30/s sustained burst 100 and presence 10/s per member; `sys.slow_down` when over rate; 2 MiB outbound buffer per connection then close 4429; schema-validate every inbound frame (`invalid_frame`, repeated > 10/min -> close 4400); presence coalescing to the latest per member every 500 ms and cursor throttling every 100 ms; typing auto-clear after 5 s.
- Extension hook `FrameInterceptor` called before sequencing so the host engine (lane C075) can authorise, reject or rewrite frames; in-process `createLoopbackLink()` so the host's own member uses the same path without a socket.
- IP-ban check at accept time through the injected `BanList` (filled by pairing failures).

## Out of scope
- mDNS: lane C071. Pairing protocol and token issuing: lane C073. Transport selection: lane C074.
- Queue, control, approval and policy semantics (who may do what): lane C075 via `FrameInterceptor`.
- Client-side connection logic: lane C054 (reused by guests). Crypto: lane C056.
- Hosted-relay features: entitlements, billing, audit, failover (CT-LAN §3 says none apply).

## Acceptance criteria
1. A guest RelayClient with a valid reconnect token completes hello/welcome; `welcome` has `protocol:1`, `heartbeat {ping_ms:20000, dead_ms:50000}`, `limits.max_frame` 262144, `slot` = lowest free, and validates against the envelope schema.
2. No `sys.hello` within 5 s -> the server closes with 4408; an invalid token -> `sys.error` then close 4401; a token for a revoked member -> close 4403; a second connection for the same member/device gets the first closed with `sys.bye superseded` and 4409.
3. Three guests send 100 sequenced frames each concurrently: every connection receives the same ordered `seq` 1..300 with no gaps or duplicates, each sender's echo carries its `seq`, and `from` equals the sender (a client-supplied `from`/`seq`/`ts` is ignored).
4. Re-sending a frame with the same `id` (after a simulated reconnect) yields no second sequence number; the echo returns the original `seq`.
5. A guest reconnecting with `last_seq` 250 while head is 300 receives 251..300 in order followed by `sys.resumed {from_seq:251,to_seq:300,count:50}`; with a buffer trimmed to 10 frames it receives `sys.resumed {snapshot_required:true, snapshot_seq}` and `lan.snapshot.get` returns the provider's bytes.
6. Rate limiting: 101 sequenced frames in 1 s from one member trigger `sys.slow_down`; sustained 31 frames/s for 5 s does the same; a consumer that never reads and exceeds 2 MiB queued is closed with 4429.
7. Malformed frames: 11 invalid frames in one minute -> `sys.error {code: invalid_frame}` each and then close 4400; a frame of 262 145 bytes is rejected without being routed; an unknown `k` is sequenced and forwarded.
8. The 9th member is refused (max 8) with a `sys.error` and close; hosts never exceed 8 live connections.
9. `allowWan` unset and `bind` = a public address -> `start()` rejects `PublicBindRefusedError`; with `allowWan` it starts and logs one warning.
10. Pings: the server sends `sys.ping` every 20 s and closes a silent connection after 50 s (fake clock); pongs are matched on `p.t`.
11. The transcript file contains every sequenced frame in JSONL with mode 0600 and contains only what was on the wire (ciphertext stays ciphertext).
12. Presence from 5 members at 10 frames/s each fans out at most once per 500 ms per member; a typing indicator not refreshed disappears after 5 s.

## Guardrails (MUST / MUST NOT)
- MUST assign `seq` and `from`/`ts` itself and MUST ignore any client-supplied values (CT-WS-ENVELOPE); `seq` is a single space for event, queue and control frames.
- MUST NOT read, decrypt or log `ct` or the cleartext `p` of events beyond kind, sizes and ids; the host process acting as relay applies the same privacy budget as the hosted relay.
- MUST NOT bind to a public interface unless `allowWan` is set (CT-LAN §4) and MUST NOT accept connections from banned IPs.
- MUST validate every inbound frame against the C003 schema before routing and drop invalid ones; MUST NOT crash on any input.
- MUST enforce the same limits and close codes as the hosted relay (frame 256 KiB, 30/s burst 100, 2 MiB buffer, 8 members) even though LAN has no billing.
- MUST never call the backend or require network access beyond the LAN socket.
- MUST create the transcript file with mode 0600 and MUST NOT grow memory unboundedly (replay buffer cap = max(5 000 frames, 10 min), per-connection buffer 2 MiB).

## Failure modes
- Port 7070 busy -> pick a random free port and report it; the advertiser (lane C071) publishes the actual port.
- Transcript file unwritable -> keep serving from memory, warn the host UI that history beyond the buffer is unavailable.
- Host process exits -> all guests see a dead connection; on graceful stop send `sys.bye` and close 1001/1000 so guests end the session (no failover in LAN, CT-LAN §3).
- Guest on a flaky link -> its 2 MiB outbound budget is exhausted only for that guest; others are unaffected.
