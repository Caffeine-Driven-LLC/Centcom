## Goal
A host on any relay plan can invite a person who has an account into one session as editor or viewer without making them a workspace member, so "the host pays, collaborators join free" works and Pro (one seat) can share.

## In scope
- `POST /v1/sessions/{id}/invites` (host, idempotent) and `GET /v1/sessions/{id}/invites`: email or link invites with role editor or viewer, expiry up to 7 days; needs the workspace's `relay_access`; no seat check.
- Reuse of B029's invite token, preview (`GET /v1/invites/{token}` with `session_name`), revoke (also by the host), key bundle storage and fetch; `invites` gains `session_id` and the session roles (migration).
- Accepting a session invite records a session grant (new table) and creates no membership and uses no seat; answer `SessionInviteAcceptance {session, role, workspace}`.
- B054's join-token admits a grant holder at the invited role, counting against `max_session_members` and a slot like any member; revoking the invite withdraws the grant; a removed member cannot rejoin.

## Out of scope
- Workspace-level invites (B029 as is).
- Billing or seat changes.

## Build against (no counterpart needed)
The in-memory invite, session and slot stores of the B029 and B054 tests.

## Acceptance criteria
1. A Pro-plan host (one seat) invites a signed-in user by e-mail; the user accepts and joins through the relay as editor; the workspace still has one seat used and one member (test).
2. Accepting uses no seat and creates no workspace membership; the invitee cannot read the workspace, its members or another session.
3. The invitee counts against `max_session_members` (the next join after the cap is `member_limit_reached`).
4. Revoking an accepted invite withdraws the right to join; a member removed by the host cannot rejoin by the same invite.
5. An invite for another e-mail address cannot be accepted by someone else; a used, expired or revoked token gives the same answers as workspace invites.
6. The sealed key bundle path works for a session invite (upload by the host, one fetch by the invitee).
7. A workspace without `relay_access` cannot create session invites (`entitlement_required`).

## Tests required
- session-invites.test.ts: create, preview, accept, join, member cap
- session-invites.test.ts: revoke, kick, wrong address, used and expired tokens
- session-invites.test.ts: the Pro host with one seat and an outside invitee
- two-accounts step: a Pro host invites an outside account

## Guardrails (MUST / MUST NOT)
- MUST NOT put tokens, tickets, invite or link secrets, key material or e-mail addresses in logs.
- MUST keep contracts/ as it is: this lane builds against the contract text and fails closed where the contract is silent.
- MUST NOT create a workspace membership or use a seat for a session invite.
- MUST check the session's host role on create and revoke, from the records, never from token claims.

## Failure modes
- Session ended or expired -> invite create 410 `session_ended`; accept of an invite for an ended session -> `session_ended`.
- Cap reached between accept and join -> join is `member_limit_reached`, the grant stays.
