## Goal
Define the three environments (dev, stage, prod) as Terraform plus Fly configuration so any environment can be created or rebuilt from the repo with one reviewed command and no manual console steps.

## In scope
- Terraform root modules per environment (`envs/dev`, `envs/stage`, `envs/prod`) using shared modules for: Fly apps (api, relay, worker, admin-internal), Postgres 16 (HA primary + replica in prod), Redis 7 with AOF persistence, Cloudflare R2 buckets (`history`, `snapshots`, `exports`, `releases`, `backups`), DNS and TLS for `api`, `relay-<region>` and `releases` hostnames.
- Fly configuration per service and environment (`fly.<service>.<env>.toml`): regions, machine sizes, min/max machines, health checks (`/healthz`, `/readyz`), `kill_timeout` for graceful relay drain, internal-only admin app.
- Remote Terraform state in an S3-compatible bucket with locking, one state per environment, and per-environment secrets references (names only, values set through the secret manager at deploy time).
- Environment sizing table: dev (1 machine per service, shared-cpu-1x 512 MB), stage (prod topology at ~25 % size), prod (api >= 3 machines in 2 regions, relay >= 2 per region in 2 regions, worker >= 2, Postgres HA).
- Naming/tagging convention (`centcom-<env>-<service>`), cost tags, and an `infra/README` documenting bootstrap order and break-glass.
- Static checks: `terraform fmt`, `validate`, `tflint`, and a policy scan (checkov or tfsec) wired as `pnpm infra:check`.

## Out of scope
- CI/CD deployment steps, blue/green and migration safety (B092).
- Backups, PITR and DR drills (B099) and the WAF module (B097); this lane leaves clearly named extension points for them.
- Dashboards and alert rules (B093, B094).
- Application config schema (B004) and secret values.

## Build against (no counterpart needed)
`terraform validate` and `terraform plan` against a local backend with provider mocks (`-refresh=false`, `tflint` rules) and `localstack`-free dry checks; the only real apply happens by the owner in `dev` after review. No other lane's code is needed.

## Interfaces (the only surface other lanes may use)
- Terraform outputs per env: `api_url`, `relay_urls` (map region -> URL), `database_url_secret_name`, `redis_url_secret_name`, `bucket_names` (map), `fly_app_names` (map).
- Variables per env file (`terraform.tfvars` committed, no secrets): `region_primary`, `regions_relay`, `machine_sizes`, `domain`.
- Commands: `pnpm infra:check`, `pnpm infra:plan -- <env>`, `pnpm infra:apply -- <env>` (apply refuses `prod` unless `CI=true` and a plan file is supplied).
- Fly app names `centcom-<env>-api|relay|worker|admin`; Fly secrets names listed in `infra/fly/SECRETS.md` (names only).

## Acceptance criteria
1. `pnpm infra:check` passes on a clean checkout: fmt, validate, tflint and policy scan report zero errors for all three env roots.
2. A second `terraform plan` immediately after an apply in dev shows `No changes` (idempotent), verified by the owner and recorded in the PR.
3. Prod config declares >= 2 regions for api and relay, >= 3 api machines, Postgres with a replica and automated failover, Redis with persistence on, and every R2 bucket with public access disabled; a policy test asserts each of these properties from the plan JSON.
4. No secret value or credential appears in any committed file: gitleaks over `infra/` reports 0 findings and every sensitive variable is marked `sensitive = true`.
5. Each Fly service defines HTTP checks on `/healthz` (liveness) and `/readyz` (readiness) and, for relay, `kill_timeout >= 60s`; the policy test asserts it.
6. Stage and prod use separate state, buckets, databases and credentials: a test asserts no resource name or identifier is shared between environments.
7. Teardown of dev (`terraform destroy`) followed by apply recreates it end-to-end in <= 30 min without manual steps (owner-verified, documented).

## Tests required
- CI job `infra-check`: fmt, validate, tflint, checkov for each env root.
- plan-JSON policy tests (Rego/OPA or a Node script) for the prod properties listed in acceptance.
- secret scan test (gitleaks) restricted to `infra/`.
- naming-convention lint script.
- documentation test: `infra/fly/SECRETS.md` lists every secret referenced by a `fly.*.toml`.

## Guardrails (MUST / MUST NOT)
- MUST NOT commit secrets, tokens, state files or `.tfvars` containing credentials; state backend credentials come from the environment.
- MUST make R2 buckets private, encrypted, with versioning on `backups` and lifecycle rules defined; no public ACLs.
- MUST NOT let `apply` run for `prod` from a laptop: apply is CI-only with a saved plan and human approval.
- MUST keep the admin app on the private network only; no public IP or hostname.
- MUST pin provider and module versions exactly; no `latest`.
- MUST NOT share data stores across environments.

## Failure modes
- State lock held after a crash -> documented `force-unlock` procedure restricted to the owner; CI never force-unlocks.
- Provider API rate-limited during apply -> retry with backoff; partial apply is safe to re-run (idempotent resources).
- Region unavailable -> variables allow moving relay regions without recreating the data layer.
