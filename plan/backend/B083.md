## Goal
Serve per-caller feature flags and remote config at `GET /v1/flags`, with deterministic percentage rollouts, plan and client-version targeting, kill switches, and ETag-based caching.

## In scope
- `GET /v1/flags` (anonymous or authenticated) returning `{flags: {key: value}, rev, ttl_s}` with `ETag` and 304 handling.
- Flag store: table `feature_flags` with typed values (bool, string, number, small JSON), rules (percent rollout, plans, workspace allow-list, min/max client version, kill switch) and a monotonically increasing global `rev`.
- Evaluator `evaluateFlags(ctx): FlagSet` that is pure and deterministic: stable hash of `(flag_key, user_id)` for percentage buckets; anonymous callers only receive flags marked `public` with no per-user rules.
- In-process cache refreshed on `rev` change via Redis pub/sub `flags:inv` and polling every 15 s as backstop.
- Service API used by internal admin tooling (B087): `setFlag`, `deleteFlag`, `listFlags` with audit events.
- Client version parsing from `User-Agent: centcom-cli/1.4.2 (contract/1.0.0; ...)` (CT-VER) for version targeting.

## Out of scope
- Admin UI and admin endpoints that call `setFlag` (B087, B088).
- Using flags to gate backend code paths in other lanes (they import `isEnabled`).
- Experimentation analytics and exposure logging.
- Token issuance (B017); this lane only reads the authenticated principal.

## Build against (no counterpart needed)
In-memory repository plus Redis in-memory pub/sub from B009; token validation via the test token minter from B017's test helpers; golden evaluation vectors stored with the tests.

## Interfaces (the only surface other lanes may use)
- HTTP `GET /v1/flags` -> `{flags: Record<string, boolean|string|number|object>, rev: number, ttl_s: number}`; headers `ETag`, `Cache-Control` (`private, max-age=<ttl_s>` when authenticated, `public, max-age=30` when anonymous).
- `evaluateFlags(ctx: {userId?: string; workspaceId?: string; plan?: 'free'|'pro'|'team'; clientVersion?: string; now: Date}, defs: FlagDef[]): Record<string, FlagValue>`.
- `isEnabled(key: string, ctx: EvalContext): boolean` for server code.
- Admin service: `setFlag(def: FlagDef, actor: Actor): Promise<{rev: number}>`, `deleteFlag(key, actor)`, `listFlags()`.
- Config: `FLAGS_TTL_S=60`, `FLAGS_MAX_COUNT=500`, `FLAGS_MAX_VALUE_BYTES=2048`.

## Acceptance criteria
1. The same user id always lands in the same bucket for a given flag; at 30 % rollout over 100 000 synthetic ids the enabled share is between 29 % and 31 %; changing the flag key changes the bucket assignment.
2. A request with `If-None-Match` equal to the current ETag returns 304 with no body; after any flag change `rev` increases by exactly 1 and the next request returns 200 with a new ETag.
3. An anonymous request receives only `public` flags and never a per-user percentage result; the same request with a valid token receives the personalised set.
4. A kill-switch flag overrides every other rule and is reflected in responses within 15 s on all API instances (pub/sub within 1 s).
5. A `min_client_version: 1.2.0` rule hides the flag from `centcom-cli/1.1.9` and shows it for `centcom-cli/1.2.0`; an unparsable User-Agent is treated as 'unknown' and only receives flags without version rules.
6. p95 latency of `GET /v1/flags` <= 20 ms with 500 flags (cache hit); body size <= 64 KiB.
7. Flag definitions or targeting rules are never present in the response; `server_only` flags are never returned.
8. Attempting to store a value larger than 2 048 bytes or the 501st flag is rejected by the service with a validation error.

## Tests required
- unit: bucket function golden vectors; rule precedence (kill switch, plan, workspace, version, percent).
- integration: ETag/304 flow and cache invalidation via pub/sub across two app instances.
- property: evaluation is deterministic and independent of definition order.
- authz: anonymous vs authenticated vs API key principal.
- failure-path: DB down -> serves last good flag set up to 5 min with unchanged ETag, then 503 `retry_after_s`.
- contract: response shape and headers vs CT-API-FLAGS.

## Guardrails (MUST / MUST NOT)
- MUST NOT expose targeting rules, other users' membership in rollouts, or workspace ids in the response.
- MUST NOT use flags to bypass entitlements or RBAC; flags never grant paid features (CT-ENTITLEMENTS is the only gate).
- MUST make anonymous responses cacheable and free of per-user data; MUST add `Vary: Authorization`.
- MUST audit every flag mutation with actor and previous value hash.
- MUST NOT put secrets or PII into flag values (documented and validated by a denylist on key names such as `secret`, `token`, `key`).

## Failure modes
- Unknown rule type in a stored definition -> flag evaluates to its default and an error metric is incremented; response still succeeds.
- Cache and DB disagree on rev -> cache is discarded and reloaded; clients may see a 15 s stale value at most.
- Corrupt `User-Agent` header -> treated as unknown version.
