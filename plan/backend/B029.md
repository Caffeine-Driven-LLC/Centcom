## Goal
Implement invites end to end: create (email or link), preview, accept, revoke, expiry, plus storage and one-time delivery of the sealed invite key bundle, so a newly accepted member can obtain session keys even if the host is offline.

## In scope
- POST /v1/workspaces/{id}/invites (Idempotency-Key required), GET /v1/workspaces/{id}/invites, DELETE /v1/invites/{id}, GET /v1/invites/{token} (public preview), POST /v1/invites/{token}/accept (Idempotency-Key accepted).
- PUT /v1/invites/{id}/key-bundle (host uploads sealed bundle) and GET /v1/invites/{token}/key-bundle (invitee fetches once).
- 160-bit URL-safe tokens from the platform CSPRNG; only `sha256` of the token is stored; expiry 7 days; email invites bound to the lower-cased invitee email.
- Invite emails queued through B032 (template `workspace_invite`); link built through an injected `InviteUrlBuilder`.
- Expiry sweeper job that marks invites `expired` and deletes their key bundles.
- Fail-closed seat check through the Fastify decorator `seatGate` (provided by B030).

## Out of scope
- Seat counting logic (B030), URL/deeplink formats (B033), email provider and templates (B032).
- Generating or opening key bundles - all cryptography is client-side (CT-CRYPTO); the server stores opaque bytes.
- Share links and viewer guest join (B068).
- Webhook delivery of invite events (later lane).

## Build against (no counterpart needed)
Fastify app built with the B006 error handler and the B010 test harness (Postgres/Redis containers, factories). Call routes with app.inject() and an HMAC-free test access token minted by the B017 test signer; authorisation uses the B021 RBAC engine; no client is involved. Email goes to the in-memory provider from B032; the `seatGate` decorator is a test double (allow/deny) in tests; key bundles are random bytes since the server never decrypts.

- Job `invite-expiry` runs every 5 min.

## Acceptance criteria
1. Create without `Idempotency-Key` returns 400-class `idempotency_key_required`; same key + same body returns the stored response with `Idempotency-Replayed: true`; same key + different body returns 409 `idempotency_conflict`.
2. The plaintext token appears only in the create response (link invites) and in the email body; neither the DB, the audit event, the logs nor GET /invites list contains it (grep test on captured logs and DB dump).
3. Preview of a valid token returns workspace name, inviter display name, role and `expires_at` and nothing else; unknown token -> 404; expired or revoked or used -> 410; the endpoint is limited to the anonymous bucket (30/min/IP) and returns 429 with `Retry-After` on the 31st call in a minute.
4. Accept by an authenticated user creates one membership with the invite's role; a second accept of the same token returns the same membership if by the same user (idempotent) and 410 for another user; an email-bound invite accepted by a user with a different verified email returns 403.
5. Accepting when `seatGate` rejects returns 403 with an `entitlement_*` family code and creates no membership; two concurrent accepts for the last free seat produce exactly one membership.
6. Invite expires exactly at `expires_at` (7 d default); at +1 s accept returns 410; the sweeper deletes the key bundle within 5 min of expiry.
7. PUT key-bundle by the session host stores <= 16 KiB of base64url (>= 48 bytes decoded); a larger bundle returns 413; by a non-host returns 403; GET key-bundle returns the bytes once to the accepting user and the next GET returns 410; bundle also deleted 15 min after acceptance if never fetched.
8. Revoke returns 204, preview then returns 410, key bundle is deleted; revoke by a `member` returns 403.

- invites.token-secrecy.test.ts: log and DB capture contains no plaintext token or `#k=` fragment.
- invites.seat-race.test.ts: 10 parallel accepts, 1 seat left.

## Guardrails (MUST / MUST NOT)
- The server MUST store key bundles as opaque ciphertext and MUST NOT log, parse or return them anywhere except the one GET; the invite link fragment `#k=` never reaches the server and MUST NOT be accepted as a query parameter.
- Tokens MUST be compared by hash lookup (constant-time on the hash), generated with the CSPRNG, and never written to logs; log the route template `/v1/invites/:token`, not the raw URL.
- Accept MUST lock the invite row and run the seat check in the same transaction as the membership insert.
- MUST NOT reveal whether an email is already a user or member in preview or error bodies.
- If the `seatGate` decorator is missing at boot the API MUST fail to start (fail closed), not skip the check.
- Key-bundle GET MUST require the authenticated user who accepted the invite; the token alone is not enough.

## Failure modes
- Email provider down -> the invite is still created; the send job retries (5 attempts, backoff + jitter); the response includes no delivery claim.
- Upload of a bundle for an invite that is expired/revoked/accepted-and-fetched -> 410.
- Invitee loses the GET response after the bundle was consumed -> 410; the client falls back to a WS `key.grant` from an online key holder (CT-CRYPTO section 4).
- Duplicate pending invite for the same email in a workspace -> 409; the existing invite id is not leaked to non-admins.
