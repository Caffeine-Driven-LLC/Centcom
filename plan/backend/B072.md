## Goal
Ingest Stripe webhooks safely: verify the signature on the raw body, persist each event once, process asynchronously and idempotently in any order, and apply resulting plan changes to entitlements.

## In scope
- POST /internal/stripe/webhook (not part of the public contract) with raw-body access, signature verification (Stripe-Signature, 300 s tolerance) and a 2xx only after the event is durably stored.
- stripe_event table unique on Stripe event id, with status received|processing|processed|failed|ignored and attempts; duplicate events return 200 without reprocessing.
- BullMQ job `stripe.event.process` handling customer.subscription.created|updated|deleted, checkout.session.completed, invoice.paid, invoice.payment_failed and ignoring others.
- Out-of-order safety: on processing, re-fetch the current subscription from Stripe and apply it through B070 upsertFromStripe (stale guard) and B069 applySubscriptionState.
- Emit domain events for outgoing webhooks (billing.subscription.updated, billing.invoice.paid, billing.invoice.payment_failed) via an outbox table, and publish a billing_issue notification request on payment failure through NotifyPort.
- Replay tooling: an internal function replayEvent(eventId) that reprocesses a stored event.

## Out of scope
- Delivering outgoing webhooks to customers: B081. Notification delivery: B063.
- Dunning/grace state machine rules: B078 (this lane records past_due_since only).
- Seat sync and invoices listing: B073, B077.
- Public contract: Stripe webhooks are explicitly internal.

## Build against (no counterpart needed)
Stripe CLI-style signed fixtures generated in tests with the test webhook secret, StripeGateway fake (B070) returning scripted subscription objects, in-memory BullMQ, fake NotifyPort and EntitlementService.

## Acceptance criteria
1. A body with a wrong signature, a timestamp older than 300 s, or a modified body returns 400 and stores nothing; a valid one returns 200 in < 200 ms (median) after one DB insert.
2. Delivering the same event id 5 times yields one stripe_event row, one processing run and 200 for each delivery.
3. Events arriving out of order (subscription.updated with created=T2 before created=T1) end with the subscription state equal to what Stripe's current object says, and entitlements rev increments once per real change.
4. invoice.payment_failed sets past_due_since once (second failure does not move it), calls NotifyPort billing_issue exactly once per invoice id, and enqueues a billing.invoice.payment_failed outbox row.
5. customer.subscription.deleted moves the workspace to status canceled/none per mapping and applies entitlements through B069; subscription.updated with seat/plan change updates plan and seats.
6. A handler failure retries 8 times with exponential backoff and jitter, then marks the event failed and moves it to the DLQ; replayEvent on it reprocesses it successfully after a fix.
7. Unknown event types are stored with status ignored and return 200; an event for an unknown customer is marked failed with reason `unknown_customer` without crashing.
8. With two webhook secrets configured, signatures from either verify (rotation test).
9. No log line or stored column contains card data, the signature header or the webhook secret.

## Guardrails (MUST / MUST NOT)
- MUST verify the signature against the exact raw bytes before parsing JSON; MUST use Stripe's constant-time verification.
- MUST NOT return 2xx before the event row is committed; MUST return 2xx quickly and do work in the job.
- MUST NOT trust event payload ordering; always reconcile against the current Stripe object.
- MUST exempt this route from user auth but NOT from size limits (max body 1 MiB) and request logging redaction.
- MUST NOT change entitlements except through B069 applySubscriptionState.
- Handlers MUST be idempotent: replaying any event any number of times yields the same final state.

## Failure modes
- DB down at ingest -> 500 so Stripe retries; nothing is acknowledged that is not stored.
- Stripe API down during processing -> job retries with backoff; events remain `received`/`processing`; alert if oldest unprocessed > 10 min.
- Entitlement service error -> event marked failed for retry, subscription row already updated is safe because upsert is idempotent.
