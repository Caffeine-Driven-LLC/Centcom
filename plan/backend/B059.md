## Goal
An advisory file-lock service that arbitrates acquire/release/expire of locks by path_hmac with TTLs and first-come fairness, without ever seeing a path.

## In scope
- Handler for file.lock frames (action acquire|release from clients; deny|expire emitted by the server) keyed by (sid, path_hmac).
- TTL locks: default ttl_ms 60 000, min 1 000, max 600 000; renewal by re-acquire from the same agent extends the TTL.
- Fairness: FIFO wait queue per path_hmac (max 10 waiters); on release or expiry the next waiter is granted and a server file.lock acquire is sequenced for it.
- Lock table in Redis with atomic Lua/SET-NX semantics and expiry sweep emitting file.lock {action:'expire'}; locks released automatically when the owning agent exits or its member leaves/is kicked.
- Per-session cap (500 locks) and per-agent cap (100 locks).
- conflict hints: when a deny occurs, offer holder agent id to the conflict signaller (B061) through a port.

## Out of scope
- Computing path_hmac (client; BLAKE2b-MAC with the epoch path key).
- Conflict.detected and branch signalling: B061.
- Enforcing locks on the file system (locks are advisory).
- Agent registry: B057.

## Interfaces (the only surface other lanes may use)
- LockService.handle(ctx, frame: FileLockFrameIn): Promise<LockOutcome>  // outcome: granted | denied{holder: agt_} | queued{position} | released | ignored
- LockService.releaseAllForAgent(sid, agentId) / releaseAllForMember(sid, memberId)

- Metric: relay_locks_held, relay_lock_denials_total, relay_lock_wait_ms

## Acceptance criteria
1. Two agents acquire the same path_hmac concurrently (100 trials, interleaved): exactly one gets acquire, the other gets a sequenced deny with the holder's agent_id in no field beyond agent_id.
2. A lock with ttl_ms 5 000 expires at 5 000 ms (fake clock): sweep emits exactly one file.lock expire frame and the path is free; ttl_ms 999 or 600 001 is clamped to 1 000 / 600 000.
3. Release by a non-owner is ignored and does not free the lock; release by owner frees it and grants the first waiter within the same sequencing step.
4. Waiters are granted FIFO; the 11th waiter for a path receives deny; the 501st lock in a session is denied.
5. When agent.exit arrives for an agent holding 3 locks, all 3 are released and 3 expire/release frames are sequenced; same on member kick.
6. Re-acquire by the holder extends the expiry and emits no deny; re-acquire by the holder of an already-held lock is idempotent for the same frame id.
7. Only path_hmac matching ^[A-Za-z0-9_-]+$ and length <= 64 is accepted; the service never receives or stores p.path (inside ct), verified by a test that scans Redis keys and values.

## Guardrails (MUST / MUST NOT)
- MUST arbitrate on the hash only; MUST NOT read, derive or log `ct.path`.
- MUST make acquire atomic (single Redis script or SET NX PX) so no two holders can exist.
- MUST NOT block any frame processing waiting for a lock; denial is immediate.
- Locks are advisory: MUST NOT reject non-lock frames because of lock state.
- A lock MUST be released when its owner can no longer act (agent exit, member left, session ended).

## Failure modes
- Redis down -> acquire returns deny-by-unavailable (503-class sys.error) rather than granting unsynchronised locks.
- Sweep missed (process pause) -> lock TTL in Redis still expires keys; next sweep reconciles by emitting expire for locks it can still see in the index.
- Duplicate file.lock frame (same sid, from, id) -> same outcome replayed, no double waiter entry.
