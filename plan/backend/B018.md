## Goal
The web app can sign in with authorization code + PKCE, keep a refresh cookie scoped to the token endpoint, and is protected against CSRF and open redirects.

## In scope
- `GET /v1/auth/authorize`: params `response_type=code`, `client_id` (`centcom-web`, `centcom-cli`, `centcom-tui`), `redirect_uri`, `code_challenge`, `code_challenge_method=S256` (only), `state`, `scope?`; requires a browser login session, else redirects to the configured login page with a signed `return_to`.
- `redirect_uri` exact-match against a configured allow-list per client (incl. `centcom://auth/callback` for desktop); any mismatch renders an error page and NEVER redirects.
- Authorization code: 256-bit random, stored hashed in Redis with {client_id, redirect_uri, code_challenge, user, scopes}, single use, TTL 60 s.
- `authorization_code` grant handler registered with B017's `/v1/auth/token`: verifies `code_verifier` (43-128 chars) against the stored S256 challenge in constant time, then issues tokens bound to a device or web session record.
- Web refresh cookie: `Secure; HttpOnly; SameSite=Lax; Path=/v1/auth/token`; refresh via cookie requires header `X-Centcom-Client: web` plus an Origin check against the allow-list; the JSON body never contains the refresh token for `centcom-web`.
- Minimal browser login-session store (cookie `centcom_sid`, Redis-backed, 30 d sliding, id rotated on login) exposing `establishLoginSession(reply, userId)` for the login lanes to call.

## Out of scope
- Login methods and the login page UI (login lanes).
- Token minting/refresh/JWKS internals (B017).
- The device-code flow (B016).
- Rate limiting implementation (B023); this lane declares the `auth` bucket on its routes.

## Interfaces (the only surface other lanes may use)
- `GET /v1/auth/authorize?...` -> 302 to `redirect_uri?code=...&state=...` or 302 to login.
- `POST /v1/auth/token` with `grant_type=authorization_code`, `code`, `code_verifier`, `redirect_uri`, `client_id` (header `X-Centcom-Client: web` for the web client).
- `establishLoginSession(reply: FastifyReply, userId: string): Promise<void>` and `getLoginSession(request): Promise<{userId: string}|null>`.
- `verifyS256(verifier: string, challenge: string): boolean`.
- Config: `AUTH_REDIRECT_URIS` (JSON map client_id -> string[]), `WEB_LOGIN_URL`, `WEB_ALLOWED_ORIGINS`.

## Acceptance criteria
1. `code_challenge_method=plain` or a missing method yields an error response and no code is issued.
2. A `redirect_uri` that differs by one character, a trailing slash, or an added query from the allow-list is rejected with no redirect; `centcom://auth/callback` is accepted only for clients that list it.
3. The authorization code works exactly once: a second exchange returns an invalid-grant-class error and revokes tokens already issued from that code.
4. A code older than 60 s (fake clock) is rejected; a code exchanged with a different `redirect_uri` or `client_id` is rejected.
5. A wrong `code_verifier` (one char flipped) is rejected; the happy path passes the RFC 7636 Appendix B test vector.
6. A token request for `centcom-web` without header `X-Centcom-Client: web`, or with an `Origin` not in the allow-list, returns 403 `forbidden` and sets no cookie.
7. A successful web exchange sets `Set-Cookie` with `HttpOnly; Secure; SameSite=Lax; Path=/v1/auth/token`; the JSON has `access_token` but no `refresh_token`; a refresh using the cookie succeeds and rotates the cookie.
8. An unauthenticated authorize redirects to login with a signed `return_to`; a tampered return_to is rejected and never used as a redirect.
9. `state` is echoed unchanged; requests missing `state` are rejected.

## Tests required
- pkce.test.ts: RFC 7636 vectors, constant-time compare, verifier length bounds.
- authorize.test.ts: allow-list matrix, missing params, login redirect, return_to tampering.
- code-store.test.ts: single use, TTL, binding to client/redirect.
- web-cookie.test.ts: attributes, CSRF header/Origin checks, rotation, logout clears cookie.
- session-store.test.ts: sliding expiry, fixation (new sid after login).

## Guardrails (MUST / MUST NOT)
- MUST only support S256; MUST NOT implement implicit flow or `plain`.
- MUST exact-match redirect URIs and MUST NOT redirect to an unvalidated URI on any error path.
- MUST NOT put tokens in URLs; the only secret in a URL is the one-time `code` in the PKCE redirect.
- MUST rotate the login-session id on login (session fixation) and set cookies `Secure; HttpOnly`.
- MUST apply uniform error bodies and the auth-endpoint rate bucket (20/min/IP).

## Failure modes
- Redis unavailable -> authorize/token return 503 with `retry_after_s`; no in-process fallback in production.
- Login session expired mid-flow -> redirect to login again preserving a signed return_to.
- Allow-list config invalid -> API refuses to start.
