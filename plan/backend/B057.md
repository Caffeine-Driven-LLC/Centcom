## Goal
The relay keeps an authoritative registry of agents per session (id, owner, mode, current state), built from agent.spawn, agent.state and agent.exit frames, so late joiners and quota checks never depend on replay of the client.

## In scope
- Hooks on sequenced agent.spawn, agent.state and agent.exit frames after they receive their seq; registry updated from their cleartext p only.
- Registry entity {agent_id, owner member, mode command_post|branch, state, since, spawned_seq, exited_seq?, outcome?}.
- Authorisation: in command_post mode only the host may emit agent.* frames; in branch mode only the agent's owner (or host) may emit for their own agent id; others get `forbidden`.
- max_parallel_agents check on agent.spawn using the session's cached entitlements (relay checks spawn per CT-ENTITLEMENTS).
- Rate limit: at most 2 agent.state frames per agent per second (excess dropped, identical consecutive states dropped).
- Registry snapshot API for roster/join flows and Redis-backed storage with Postgres write-through for audit/history of agent lifetimes.

## Out of scope
- Validating the state name against the state map: B058 (called as a validator hook).
- File locks, branch/conflict signalling, approvals: B059, B061, B060.
- Running agents or reading agent content (label, branch, worktree stay in ct, never seen).
- Usage metering of agent minutes: B074/B075.

## Acceptance criteria
1. agent.spawn from the host in a command_post session creates a record; the same frame id replayed creates no second record.
2. In command_post mode an editor's agent.spawn returns sys.error `forbidden`; in branch mode an editor may spawn an agent with owner = self but not with owner = another member.
3. When countLive == max_parallel_agents (e.g. 8 for pro fixture) the next agent.spawn is rejected `forbidden` with quota-class detail and is not sequenced.
4. agent.state for an unknown agent id is ignored with sys.error `invalid_frame` to the sender; for an exited agent it is ignored silently.
5. Sending 5 agent.state frames for one agent within 1 s results in at most 2 being sequenced; two identical consecutive states result in 1.
6. agent.exit sets the record exited, decrements countLive, and a later agent.state for that agent does not resurrect it.
7. After restart the registry rebuilds from the agent table and returns the same list() as before for 100 random agents.
8. Registry never stores or logs label/branch/worktree/model (a test asserts these keys are absent from the table and from log output captured during the suite).

## Guardrails (MUST / MUST NOT)
- MUST read only the cleartext p of hybrid agent.* frames; MUST NOT attempt to read ct.
- MUST enforce the spawn limit server-side even though the host client also enforces it.
- MUST treat unknown agent ids and unknown future fields as tolerated input (ignore), never close the connection.
- MUST NOT let an editor spoof the owner field: owner must equal the frame's server-stamped `from` unless sender is host.
- State rate-limit drops MUST NOT be sequenced and MUST NOT be audited per frame (log counter only).

## Failure modes
- Redis unavailable -> registry falls back to Postgres reads and rejects new spawns with 503-class sys.error until Redis returns (fail closed for limits).
- Out-of-order agent.state after agent.exit (race) -> ignored, counter incremented.
- Entitlements cache stale during downgrade -> spawn uses the entitlement rev at that time; mismatch resolved by the next invalidation (<= 30 s).
