## Goal
Persist reactions (cleartext) and comments (ciphertext) as queryable per-target records so late joiners and the history API can show them, without the server reading comment text.

## In scope
- Sequenced-frame hook storing reaction {target msg_, code, op add|remove, member} and comment.add {target, ciphertext ref seq} after sequencing.
- Reaction aggregate: current set of (target, code, member) with add/remove idempotent semantics; counts per target and code.
- Tables reaction and comment_ref (comment text is NOT stored; only seq, id, member, target, size, kid pointing to the history blob).
- Limits: reaction codes limited to thumbs, heart, party, laugh, eyes, check; at most 200 reaction ops per member per minute; comment ct <= 192 KiB; 100 comments per target.
- Authorisation: host, editor and viewer may react and comment, muted members may not.
- Read API used by relay join flow: reactionsFor(sid, targets[]): aggregates (internal function, not a new endpoint).

## Out of scope
- History retrieval of comment ciphertext: B055.
- Mention notifications (category mention needs plaintext; clients send explicit mention signals in a future contract).
- Rendering or moderation of comment text (client, encrypted).

## Interfaces (the only surface other lanes may use)
- ReactionStore.apply(sid, frame:{seq, from, target, code, op}): Promise<{changed:boolean}>
- ReactionStore.aggregate(sid, targets: string[]): Promise<Record<string, Record<string, number>>>

## Acceptance criteria
1. reaction add then add again by the same member for the same (target, code) leaves one row; remove deletes it; remove of a missing reaction is a no-op that is still sequenced.
2. aggregate for 50 targets with 6 codes and 20 members returns correct counts in under 50 ms on the Postgres container.
3. A reaction with code 'skull' is rejected `invalid_frame`; target not matching ^msg_ pattern is rejected.
4. Muted member reaction and comment frames are dropped with `forbidden`; viewers' frames succeed.
5. comment.add stores no text: the comment_ref table has no text column (schema test) and a 100-comment-per-target cap rejects the 101st with `forbidden`.
6. Replaying the same frame id (sid, from, id) produces one row.
7. Deleting a session's history (B055 purge) can call ReactionStore.purge(sid) and CommentIndex.purge(sid), both removing all rows.

## Guardrails (MUST / MUST NOT)
- MUST NOT store or log comment text or ct; only pointers (seq, size, kid).
- MUST validate reaction `code` against the contract enum; unknown codes are rejected, not stored.
- MUST apply reaction state from sequenced frames only (so replay reproduces state).
- MUST NOT let a client delete another member's reaction.

## Failure modes
- DB write fails after sequencing -> frame stays in the log; a repair job rebuilds the reaction table from the durable log on restart (idempotent).
- Target msg_ id not present in history -> still stored (late joiners may not have it); no error.
