## Goal
One token service issues EdDSA access tokens, rotating refresh tokens with reuse detection, publishes the JWKS and handles revocation, and the API authenticates every request through it.

## In scope
- JWT access tokens (RFC 9068 profile) signed Ed25519 with `jose`, `kid` header, 15 min lifetime, claims `iss=https://api.centcom.dev`, `sub`, `aud=centcom-api`, `exp`, `iat`, `jti`, `scp`, `dev`, `wsp`, `plan`, `ent` per CT-AUTH; +/-60 s skew tolerated on verify.
- Signing key set from config (active kid + previous kid(s)); `GET /.well-known/jwks.json` publishing public keys only; rotation procedure (new key published before it becomes active, old key kept for the overlap; rotation at least every 90 days).
- Refresh tokens: opaque 256-bit CSPRNG base64url, stored as sha256 hash in `refresh_tokens` (family_id, device_id, parent, used_at, expires_at 30 d sliding, absolute_expires_at 180 d, revoked_at); rotation on every use in one transaction; reuse of a spent token revokes the entire family and returns `refresh_reuse_detected`.
- `POST /v1/auth/token` dispatcher with grant-handler registry (`registerGrantHandler`) and built-in `refresh_token` grant; `POST /v1/auth/revoke` (RFC 7009) revoking a refresh-token family or device; always 200 for unknown tokens.
- Access-token revocation: Redis set `revoked:jti` (TTL 16 min) and `revoked:dev` flags checked on verify; 401 codes `token_expired`, `token_invalid`, `token_revoked`, `device_revoked`.
- Fastify auth plugin (apps/api/src/plugins/auth.ts): parses `Authorization: Bearer`, verifies, attaches `request.principal`; pluggable `PrincipalResolver` so API keys (B019) register for `cen_` prefixed bearers.
- `mintRelayTicket(claims)`: JWT aud `centcom-relay`, 60 s, unique `jti`, claims `sid`, `mid`, `role`, `dev`, `caps` (used by the sessions lane's join-token endpoint).
- Migration for `refresh_tokens` and typed DB definitions; `EntitlementsLookup` interface for `plan`/`ent` claims (default `{plan:'free', ent:0}`).

## Out of scope
- Device-code grant (B016) and authorization-code grant/cookies (B018) which register themselves as grant handlers.
- API-key authentication (B019) and device list/revoke endpoints (B020) beyond exposing `revokeDevice(deviceId)`.
- The join-token HTTP endpoint and single-use jti enforcement for relay tickets (sessions lane / relay handshake lane).
- Entitlement computation (billing lanes).

## Acceptance criteria
1. An issued access token has header `alg=EdDSA` and `kid`; decoded claims include all CT-AUTH claims; `exp - iat` equals 900; `aud` is `centcom-api`.
2. JWKS contains only OKP/Ed25519 public keys (no `d`), at least 2 keys during an overlap, and a token signed by the previous key still verifies.
3. A refresh grant returns a new refresh token and spends the old one; presenting the old one again returns 401 `refresh_reuse_detected` AND the newly issued token from that family stops working (family revoked).
4. 100 parallel refreshes with one token produce exactly one success; the rest fail without issuing extra tokens.
5. Refresh slides 30 days on use but is refused after 180 days absolute (fake clock test at day 181).
6. Expired access token -> 401 `token_expired`; tampered signature or wrong aud -> 401 `token_invalid`; revoked jti -> 401 `token_revoked`; token of a revoked device -> 401 `device_revoked` within 1 s of revocation.
7. `POST /v1/auth/revoke` with an unknown token returns 200 and reveals nothing; with a valid refresh token it revokes its family.
8. A relay ticket decodes to `aud=centcom-relay`, `exp - iat = 60`, a unique `jti` across 10 000 mints, role and caps as given.
9. Refresh tokens appear in the database only as hashes; no log line from a full flow contains a token (log-capture test).

## Tests required
- jwt.test.ts: claims, skew 60 s, alg confusion (`none`, HS256) rejected, wrong kid.
- refresh.test.ts: rotation, reuse detection, concurrency, sliding/absolute expiry.
- jwks.test.ts: rotation overlap, no private material.
- revocation.test.ts: jti, device, family.
- auth-plugin.test.ts: missing/malformed header, principal attached, resolver registry.
- relay-ticket.test.ts.
- errors.test.ts: uniform bodies for invalid tokens.

## Guardrails (MUST / MUST NOT)
- MUST accept only `alg=EdDSA`; MUST reject `none` and any HMAC algorithm to prevent algorithm confusion.
- MUST store refresh tokens hashed and rotate inside a single transaction with row locking; reuse detection MUST revoke the whole family.
- MUST NOT put tokens in URLs or logs; MUST NOT return refresh tokens in any response other than the token endpoint.
- MUST read signing keys only from config secrets (B004 `Secret`), never from the repo; private keys never appear in the JWKS.
- MUST apply the 60 s skew tolerance only, not more.
- MUST keep error bodies uniform for unknown vs malformed vs expired refresh tokens to avoid oracle behaviour.

## Failure modes
- Redis unavailable -> revocation lookups fail closed for tokens carrying the `admin` scope and fail open (with metric + alert) for normal tokens for at most their 15 min life; refresh still works via the database.
- Signing key missing at boot -> API refuses to start.
- Clock jump beyond skew -> tokens rejected with `token_invalid`/`token_expired`, logged with ids only.
