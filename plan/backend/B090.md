## Goal
Enforce data retention: nightly idempotent purge jobs for history, snapshots, audit rows, expired tokens and codes, webhook delivery logs and exports, driven by entitlements and the rules in the contracts, with dry-run, safety brakes and downgrade notices.

## In scope
- Retention policy registry `RetentionPolicy[]` (one entry per dataset: id, owner, ttl resolver, batch size, purge function) and a runner job `retention.run` scheduled 03:00 UTC with a Redis lock per policy.
- History and snapshots: after session end, purge durable log blobs and snapshot blobs older than the workspace's effective `history_days` (CT-RESUME, CT-ENTITLEMENTS) through the history store interface of B055; workspace deletion purges immediately via `purgeWorkspace(workspaceId)`.
- Downgrade handling: on `history_days` decrease, record a `retention_pending(workspace_id, new_days, notice_sent_at, effective_at = +7 days)` row, send `sys.notice history_retention_changed {days}` to live sessions and an email to owners, then purge after the 7 days.
- Other datasets: audit events beyond `audit_log_days`, webhook delivery log (30 days), idempotency keys (24 h), expired/used invites and share links, device-flow codes, expired relay-ticket `jti` records, refresh-token families past 180 days absolute, export files and audit-export objects (24 h to 7 days per type), notification inbox beyond 90 days read.
- Safety brakes: batch size 1 000 rows / 500 blobs, per-run time budget 30 min, abort when a policy would delete > 20 % of a table's rows in one run unless `RETENTION_FORCE=true`.
- Dry-run mode (`RETENTION_DRY_RUN=true`, default true outside production), metrics and a run report table.

## Out of scope
- Telemetry retention (owned by B085; reported here read-only).
- Account deletion 30-day grace and data export flow (B026); the runner only calls its finaliser if registered.
- Storage-level lifecycle rules and backups (B091, B099).
- Entitlement values (B069) and plan changes (B078).

## Interfaces (the only surface other lanes may use)
- `interface RetentionPolicy { id: string; owner: string; run(ctx: {now: Date; dryRun: boolean; budgetMs: number}): Promise<{scanned: number; purged: number; skipped: number}> }`.
- BullMQ jobs `retention.run {policy?: string}` (cron 03:00 UTC) and `retention.purge-workspace {workspaceId}`.
- `purgeWorkspace(workspaceId: string): Promise<{blobs: number; rows: number}>` used by workspace deletion.
- Tables `retention_runs(id, policy, started_at, finished_at, scanned, purged, dry_run, aborted_reason)` and `retention_pending`.
- Metrics `retention_purged_total{policy}`, `retention_run_duration_seconds{policy}`; config `RETENTION_DRY_RUN`, `RETENTION_FORCE`, `RETENTION_MAX_DELETE_FRACTION=0.2`.

## Acceptance criteria
1. For a Pro workspace (`history_days:7`) with a session ended 8 days ago, one run deletes its durable-log blobs and snapshots and the DB metadata rows; a session ended 6 days ago is untouched; a live or paused session is never purged regardless of age.
2. Running the whole job twice in a row yields zero deletions on the second run (idempotent) and no errors; killing the process mid-run and restarting completes the remaining work.
3. Downgrade from `history_days:30` to `7` creates one `retention_pending` row, sends exactly one `history_retention_changed {days:7}` notice and one email, and purges nothing for 7 days (+/- 5 min), then purges data older than 7 days.
4. The workspace-level `retention override` (settings) can only shorten retention: an override of 30 days on a 7-day plan yields 7; an override of 3 days yields 3.
5. Dry-run mode logs counts and deletes nothing (verified by row/blob counts); the report row has `dry_run=true`.
6. A run that would delete more than 20 % of a table aborts with `aborted_reason='fraction_exceeded'`, pages via metric `retention_aborted_total`, and deletes nothing from that policy.
7. Idempotency keys older than 24 h, device codes older than 10 min past expiry, share links past expiry and refresh-token families past 180 days absolute are deleted; none of the unexpired rows are.
8. Deleting a workspace calls `purgeWorkspace` and removes all of its blobs and rows within 5 min for a 10 000-frame history, and writes an audit event with counts.

## Tests required
- unit: effective retention resolution (plan, override, free = 0) with fake clock.
- integration: seeded matrix of session states x ages x plans against MinIO + Postgres.
- idempotency and crash-restart tests.
- downgrade-notice scenario test including cancellation on re-upgrade within 7 days.
- failure-path: blob store errors on 10 % of deletes -> run completes, failures retried next run, no DB metadata removed for undeleted blobs.
- brake test: fraction guard triggers with a corrupted `history_days=0` fixture.

## Guardrails (MUST / MUST NOT)
- MUST delete blobs before metadata rows and MUST NOT delete metadata whose blob delete failed (no orphaned unreachable blobs).
- MUST NOT purge sessions in `live`, `paused` state, and MUST NOT purge anything newer than the retention horizon computed from the session end time.
- MUST apply the 7-day notice on downgrades; MUST NOT shorten retention retroactively without it.
- MUST NOT read, decrypt or log blob contents; operate on keys and sizes only.
- MUST run dry-run by default in non-production and MUST log counts only (never ids of users' content).

## Failure modes
- Entitlement lookup fails for a workspace -> skip that workspace this run (never assume 0 days), log warn.
- Run exceeds the 30 min budget -> stops cleanly, continues next night; metric `retention_backlog` exposed.
- Storage returns throttling -> adaptive concurrency drop and retry with backoff, job not failed.
