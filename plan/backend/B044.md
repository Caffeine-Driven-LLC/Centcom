## Goal
Deliver each accepted, sequenced frame to every member connection of the session in strict `seq` order as opaque bytes, including the sender's echo, without ever reading or altering ciphertext.

## In scope
- Fan-out stage (order 50): after sequencing, build the outbound frame (server fields added, content fields untouched) and deliver to all local connections of the room.
- Per-room `OrderedRelease`: releases frames to connections strictly in contiguous `seq` order (buffers out-of-order offers up to 2 000 frames or 250 ms, then reports a gap); on a single node offers arrive in order.
- Per-connection send queue (FIFO) abstraction used by B046 for backpressure; the sender receives its own frame with `seq` as echo.
- `RemoteDispatcher` port (default no-op) that B045 implements to publish to other nodes.
- Server-originated sequenced frames (`control.*` by server, `queue.state`) enter through `fanout.emitServer(sid, kind, p)` so they share the same seq space.
- Metrics for frames delivered, fan-out latency (receive to last local write), and per-room member count.

## Out of scope
- Sequencing and the hot buffer (B041), room membership and authorisation (B043), multi-node transport (B045), slow-consumer policy (B046), presence fan-out (B047).
- Interpreting any event kind (queue, control semantics: B051, B052).
- Key grant validation (B049).

## Acceptance criteria
1. With 5 connected members, a frame from member A is delivered to all 5 (including A as echo) with the same `seq`; per-connection delivered `seq` sequences are strictly increasing in a 10 000-frame run with 8 concurrent senders.
2. The delivered `ct`, `sig`, `p` and `id` fields are byte-identical to the sender's (compared as raw JSON substrings of the original frame) and `from`/`ts`/`seq` are the server-stamped values.
3. A server-emitted `control.member_joined` via `emitServer` receives the next `seq` and is delivered in order relative to client frames.
4. Offering seq 12 before 11 to `OrderedRelease` delivers 11 then 12; if 11 never arrives within 250 ms `onGap` fires with (11,11) and no frame >= 12 is delivered before the gap is resolved.
5. A closed or `closed`-state connection is skipped without affecting others; one throwing connection send does not prevent delivery to the rest.
6. Fan-out of one frame to 50 connections takes < 5 ms p95 (local, in-memory sockets); throughput >= 5 000 deliveries/s on one core in the benchmark.
7. Unknown event kinds are sequenced and delivered unchanged (no close).

## Tests required
- fanout.order.test.ts: property test over random sender interleavings; per-connection monotonicity.
- fanout.opaque.test.ts: byte-identical ct/sig/p, random-byte payloads, no JSON re-serialisation of ct.
- fanout.release.test.ts: OrderedRelease reorder, gap callback, bounded buffer.
- fanout.server-frames.test.ts: emitServer shares seq space.
- fanout.isolation.test.ts: faulty connection, closed connection.
- fanout.bench.ts: 50-member room throughput.

## Guardrails (MUST / MUST NOT)
- The relay MUST route `ct` as opaque; the fan-out path MUST NOT `JSON.parse` then re-stringify `ct` (use the raw substring or an immutable object reference) and MUST NOT log `p` of cleartext frames beyond the kind (CT-WS-ENVELOPE security notes).
- Delivery order per connection MUST equal `seq` order; never skip ahead past a gap.
- Frames MUST only be delivered to connections in the frame's own room; the room lookup is by the connection's authenticated `sid`, never by the frame's `sid` field alone.
- A slow or failing connection MUST NOT block or delay other connections (no shared await across recipients).
- Server-emitted frames MUST carry `from` = the server principal and clients MUST be able to tell; do not stamp a member id on them.

## Failure modes
- Gap that never fills (lost offer) -> after 250 ms fetch the missing range from the hot buffer via `SeqStore.range`; if still missing, close the room's connections with 1001 so clients resume.
- Send queue full for a connection -> delegated to B046; this lane never drops sequenced frames silently.
- Room unexpectedly absent -> frame is still sequenced and buffered; delivery is skipped and logged at warn.
## Notes
`from` for server-originated frames is not specified as a concrete id in the contract (catalogue says 'server'); this card uses the literal string `server` and flags it.
