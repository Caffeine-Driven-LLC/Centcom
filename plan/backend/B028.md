## Goal
Implement workspace membership management: list members, change workspace roles, remove or leave, and transfer ownership, enforcing the CT-RBAC matrix and the single-owner invariant, and telling the relay about changes so live sessions react.

## In scope
- GET /v1/workspaces/{id}/members (paginated; emails visible to admin+ only), PATCH /v1/workspaces/{id}/members/{mem}, DELETE /v1/workspaces/{id}/members/{mem} (remove or self-leave), POST /v1/workspaces/{id}/transfer-ownership (Idempotency-Key accepted).
- `MembershipService` used by other lanes (invite accept in B029, session joins in B043).
- Redis pub/sub channel `centcom:membership` events `{type: 'role_changed'|'removed'|'left', wsp, mem, user, role?, at}` consumed by the relay.
- Audit events for every change via B036 and denied-attempt audit per CT-RBAC rule 6.

## Out of scope
- Seat counting and limits (B030); invites (B029).
- Session-level roles and kicks (B051, B043).
- Webhook delivery for member events (a later webhook lane); this lane only publishes the pub/sub event and audit row.
- Device or token revocation for a removed user beyond emitting the event.

## Build against (no counterpart needed)
Fastify app built with the B006 error handler and the B010 test harness (Postgres/Redis containers, factories). Call routes with app.inject() and an HMAC-free test access token minted by the B017 test signer; authorisation uses the B021 RBAC engine; no client is involved.

## Interfaces (the only surface other lanes may use)
- HTTP: the four routes above.
- TS: `interface MembershipService { list(wspId: string, viewer: Actor, page: PageRequest): Promise<Page<MemberView>>; add(trx: Trx, wspId: string, userId: string, role: WorkspaceRole): Promise<Membership>; changeRole(wspId: string, memId: string, role: WorkspaceRole, actor: Actor): Promise<Membership>; remove(wspId: string, memId: string, actor: Actor): Promise<void>; transferOwnership(wspId: string, toMemId: string, actor: Actor): Promise<void>; getLive(wspId: string, userId: string): Promise<Membership | null>; }`
- Pub/sub channel `centcom:membership` (JSON payload above).
- DB: `memberships.role` check constraint over `owner|admin|member|billing|guest`; partial unique index `one_owner_per_workspace`.

## Acceptance criteria
1. Role changes follow CT-RBAC: owner may set admin/member/billing/guest; admin may set member/billing/guest only and gets 403 trying to touch an owner or promote to admin; `owner` can never be set via PATCH (400-class), only via transfer.
2. DELETE of self by a non-owner returns 204 and the membership is gone; DELETE of self by the owner returns 409 until ownership is transferred.
3. Admin removing another admin or the owner returns 403; admin removing a member returns 204.
4. transfer-ownership to an `admin` member succeeds atomically (old owner becomes `admin`, target becomes `owner`) and a concurrent second transfer returns 409; transfer to a `member` returns 422.
5. Replaying transfer-ownership with the same Idempotency-Key returns the stored response with `Idempotency-Replayed: true`.
6. After each successful change a message appears on `centcom:membership` within 100 ms and an audit event with the actor, target mem and outcome exists; every rejected privileged attempt also writes an audit event with outcome `denied`.
7. GET members as `guest` returns names and roles but no emails; as `admin` includes emails; list of 120 members paginates with limit=50 into 3 pages.
8. `getLive` returns the new role within 1 s of a change (no cache older than 2 s, per CT-RBAC rule 2).

## Tests required
- members.rbac.matrix.test.ts: table-driven (actor role x target role x action) against the CT-RBAC matrix.
- members.owner-invariant.test.ts: concurrent transfers and removals never leave 0 or 2 owners (run 50 parallel attempts).
- members.events.test.ts: pub/sub payloads and audit rows for each mutation, including denied.
- members.list.test.ts: pagination, email visibility by viewer role.
- Contract: responses validate against CT-API-WORKSPACES validators.

## Guardrails (MUST / MUST NOT)
- Authorisation MUST come from the live membership row, never from token claims or client-sent roles.
- The single-owner invariant MUST be enforced by the database, and transfer MUST be one transaction with a row lock on the workspace.
- Emails MUST NOT be returned to `member`, `billing` or `guest` viewers.
- Removing a member MUST publish the pub/sub event after commit only, never before.
- MUST NOT delete the user's other workspaces' memberships or the user itself.

## Failure modes
- Pub/sub publish fails after commit -> retry 3 times with jitter, then log error and increment `membership_event_publish_failed_total`; relay still converges via its <= 2 s live membership re-check.
- Target membership already removed concurrently -> 404, no audit success event.
- Transaction deadlock on transfer -> retry once, then 409.
