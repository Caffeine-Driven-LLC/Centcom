## Goal
All list endpoints share one cursor-pagination and filtering library that produces the CT-PAGE response shape, with opaque, filter-bound, expiring cursors.

## In scope
- Query parsing: `limit` 1..200 (default 50), `cursor`, optional `sort` from an endpoint allow-list; invalid values give a validation problem with `errors[]` pointers.
- Cursor codec: base64url of JSON `{v:1, k:<keyset values>, f:<filter hash>, s:<sort>, exp:<unix>}` plus HMAC-SHA256 signature (keys from config `CURSOR_SIGNING_KEYS`, newest signs, all verify); URL-safe; expires after 24 h; bound to the same filters and sort.
- Kysely keyset helper `paginate(query, spec, params)` fetching `limit + 1` rows, building `(sort_col, id)` tuple comparisons for asc/desc, always tie-breaking on id; returns `{data, next_cursor, has_more}`.
- Filter helper: declared filter fields with types (string, enum, id, timestamp range) parsed from query, unknown filters ignored, hashed into the cursor.
- Response builder `page(data, next_cursor)` and Fastify decorator `reply.page(...)`; helper for in-memory arrays used by non-SQL lists.

## Out of scope
- Endpoint-specific queries (each lane writes its list query using this library).
- Offset pagination (forbidden by CT-PAGE).
- Sparse field selection `?fields=` (not supported in v1).

## Interfaces (the only surface other lanes may use)
- `parsePageQuery(q: unknown, spec:{sorts: readonly string[]; defaultSort: string}): {limit: number; cursor?: string; sort: string}`.
- `encodeCursor(payload: CursorPayload, keys: SigningKeys, now: number): string`; `decodeCursor(c: string, keys: SigningKeys, now: number, expect:{filterHash: string; sort: string}): CursorPayload`.
- `paginate<DB, TB, O>(qb: SelectQueryBuilder<DB, TB, O>, spec: KeysetSpec, params: PageParams): Promise<Page<O>>` where `Page<T> = {data: T[]; next_cursor: string|null; has_more: boolean}`.
- `defineFilters({status: enumFilter([...]), created_at: rangeFilter()})` -> parser + `hash(filters)`.
- `reply.page(data, nextCursor)`.

## Acceptance criteria
1. Listing 1 000 rows with limit 200 returns 5 pages, `has_more` true on the first 4 and false on the last, `next_cursor` null on the last, with no row duplicated or skipped, in stable order.
2. Default limit is 50; `limit=0`, `limit=201`, `limit=abc` return a validation problem pointing at `/limit`.
3. Rows inserted between page fetches never cause duplicates or skips in the already-fetched ordering (keyset test with concurrent inserts).
4. Changing a filter or sort while reusing a cursor is rejected (filter-hash mismatch); a cursor older than 24 h (fake clock) is rejected; a cursor with one flipped byte is rejected.
5. Cursors cannot be forged without the key (HMAC checked in constant time) and carry no row data beyond keyset values.
6. Key rotation: a cursor signed with the previous key still verifies; an unknown key id is rejected.
7. Sorting by a non-unique column (created_at with 100 identical timestamps) is stable thanks to the id tie-breaker.
8. Generated SQL uses parameter placeholders only (query-log assertion) and EXPLAIN on a 100k-row table with a matching index shows no sequential scan.

## Tests required
- cursor.test.ts: codec, tamper, expiry, key rotation.
- query.test.ts: limit and sort validation.
- keyset.test.ts: asc/desc, ties, concurrent inserts on real Postgres.
- filters.test.ts: hash stability and unknown filters.
- plugin.test.ts and fuzz.test.ts: response shape, reply.page, decodeCursor never throws untyped errors.

## Guardrails (MUST / MUST NOT)
- MUST NOT implement or accept offsets, page numbers or `skip`.
- MUST sign cursors and bind them to filters and sort so a client cannot read other scopes by editing a cursor.
- MUST NOT include secrets, emails or content in cursor payloads (keyset values only).
- MUST always add the unique id as the final sort key; MUST NOT expose total counts.
- MUST clamp `limit` server-side to 200 even if a caller passes a higher spec maximum.

## Failure modes
- Invalid/expired/tampered cursor -> 400-class validation problem on `/cursor`, never 500.
- Signing key missing -> service refuses to start.
- Empty result -> `{data: [], next_cursor: null, has_more: false}`.
