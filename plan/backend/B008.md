## Goal
The first migration creates the core tables every identity, workspace and session lane builds on, with typed Kysely table definitions.

## In scope
- Migration `20260101000000_core_schema.sql` creating: users, devices, workspaces, memberships, sessions, session_members, with id-prefix CHECK constraints (`id ~ '^usr_[0-9A-HJKMNP-TV-Z]{26}$'` etc.).
- users: id, email (citext, unique, <=254), display_name (1-40), locale (default 'en'), avatar_slot smallint, telemetry_opt_in bool default false, status ('active'|'pending_deletion'|'deleted'), deletion_requested_at, created_at, updated_at.
- devices: id, user_id, name, platform, x25519_pub, ed25519_pub (32-byte base64url text, 43 chars), fingerprint, last_seen_at, revoked_at, created_at.
- workspaces: id, name (1-60), slug (unique, `[a-z0-9-]{3,40}`), settings jsonb, version int (for ETag), created_by, created_at, updated_at, deleted_at. memberships: id, workspace_id, user_id, role ('owner'|'admin'|'member'|'billing'|'guest'), unique(workspace_id,user_id), created_at.
- sessions: id, workspace_id (nullable FK), name (1-80), state text, region, created_by, created_at, ended_at. session_members: id (mem_), session_id, user_id, device_id, role ('host'|'editor'|'viewer'), slot int >=0, joined_at, left_at, unique(session_id, slot).
- Kysely `Database` table interfaces in packages/db/src/schema/core.ts plus indexes (users.email, memberships.user_id, memberships.workspace_id, devices.user_id, sessions.workspace_id).

## Out of scope
- Token, refresh, device-grant, api-key, invite, audit, billing and usage tables (each feature lane adds its own migration).
- Repositories and business logic (B013 and later).
- Row-level security policies (not used in v1; authorisation is in the service layer, B021).

## Build against (no counterpart needed)
Run against a real Postgres 16 via B007's runner in tests; no other service needed.

## Deliverables
- `packages/db/migrations/20260101000000_core_schema.sql`
- `packages/db/src/schema/core.ts`
- `packages/db/test/schema/core.test.ts`

## Interfaces (the only surface other lanes may use)
- Tables: users, devices, workspaces, memberships, sessions, session_members (columns above).
- `export interface UsersTable`, `DevicesTable`, `WorkspacesTable`, `MembershipsTable`, `SessionsTable`, `SessionMembersTable` and `CoreDatabase` in @centcom/db.
- Unique/FK constraints: devices.user_id -> users(id), memberships.(workspace_id,user_id) unique, session_members.(session_id,slot) unique.

## Acceptance criteria
1. Migration applies to an empty DB with B007's runner and produces exactly the six tables.
2. Inserting a user with id `ses_...` fails the id CHECK; inserting two users whose emails differ only by case fails the unique constraint.
3. Inserting a membership with role `owner2` fails; inserting the same (workspace,user) twice fails.
4. A display_name of 41 chars or an empty string fails; a workspace slug `ab` or `A-B-C` fails.
5. Two session_members with the same (session_id, slot) fail; a slot of -1 fails.
6. Deleting a user is blocked while devices or memberships reference it (no ON DELETE CASCADE from users in v1; deletion is a job, B026).
7. `tsc` type-checks a sample Kysely query against CoreDatabase, and the table interfaces match information_schema columns (test compares names and nullability).

## Tests required
- core-schema.test.ts: constraint matrix above against real Postgres.
- types-match.test.ts: Kysely types vs information_schema.
- idempotent-apply.test.ts: re-run is a no-op.

## Guardrails (MUST / MUST NOT)
- MUST store no plaintext session content, message text, paths or branch names in any column; session rows hold metadata only.
- MUST NOT use ON DELETE CASCADE from users or workspaces to history/audit tables (retention jobs own deletion).
- MUST keep the migration purely additive and end it with a `-- rollback note:` comment.
- MUST NOT store passwords or secrets in users; email is the only PII besides display_name.

## Failure modes
- citext extension missing -> migration runs `CREATE EXTENSION IF NOT EXISTS citext` and fails clearly if the role lacks permission.
- Partial failure -> whole migration rolls back (single transaction).
- Later lane needs another column -> add via its own migration, never edit this file (checksum guard).

## Definition of done
Everything in [GUIDELINES §8](../GUIDELINES.md) plus every acceptance item above covered by a test.
