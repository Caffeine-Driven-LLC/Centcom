## Goal
Implement the payment-failure lifecycle: past_due with a 7-day grace window, reminders, recovery on payment, and the drop to `none` entitlements with a 10-minute wind-down of live hosted sessions.

## In scope
- State machine `active -> past_due -> (active | none)` and `canceled -> none at period end`, driven by billing events and a scheduler, with `grace_until = first_failed_at + 7 days`.
- `applyBillingEvent(ev)` handler called by the Stripe webhook ingestion (B072) for `invoice.payment_failed`, `invoice.paid`, `customer.subscription.updated`, `customer.subscription.deleted`.
- Scheduled job `dunning.expire` (every 5 min) that moves workspaces with `grace_until < now` to `none`, plus `canceled` workspaces with `period.end < now`.
- Reminder schedule: transactional email through B032 and `billing_issue` notification to owner and billing members at grace day 0, 3 and 6.
- On transition to `none`: bump entitlement rev, publish `sys.notice plan_changed {plan:'free'}` on `relay:notice:{wsp}`, and enqueue a delayed (10 min) job that ends live hosted sessions through a `SessionEnder` port.
- Emit audit events and `billing.subscription.updated` / `billing.invoice.payment_failed` webhook events.

## Out of scope
- Receiving, verifying and de-duplicating Stripe webhooks (B072).
- Entitlement cache, enforcement and the 7-day grace read path in middleware (B080 reads status and `grace_until`).
- Retry timing of card payments (configured in Stripe Smart Retries, not here).
- Quota signals (B076) and checkout/portal (B071).
- Downgrade data handling such as history purge after 7 days notice (B090).

## Build against (no counterpart needed)
Feed recorded Stripe event fixtures into `applyBillingEvent` with an injected fake clock; the `SessionEnder` port is a fake that records calls; emails and notifications go to in-memory test doubles from B032/B063.

## Interfaces (the only surface other lanes may use)
- `applyBillingEvent(ev: BillingEvent, now: Date): Promise<StatusTransition | null>` where `StatusTransition = {workspace: string; from: Status; to: Status; grace_until: string|null}` and `Status = 'active'|'trialing'|'past_due'|'canceled'|'none'`.
- `interface SessionEnder { endLiveHostedSessions(workspaceId: string, reason: 'plan_changed'): Promise<number> }` (port; adapter wired in the worker composition root to the session lifecycle service).
- BullMQ queue `dunning` with jobs `expire {}`, `remind {workspaceId, day: 0|3|6}`, `wind-down {workspaceId}`; DLQ `dunning:dead`.
- Table `subscription_dunning(workspace_id PK, state, failed_invoice, first_failed_at, grace_until, reminders_sent smallint, updated_at)`.
- Config: `DUNNING_GRACE_DAYS=7` (contract value, validated 7), `DUNNING_WINDDOWN_MIN=10`.

## Acceptance criteria
1. A first `invoice.payment_failed` sets status `past_due` and `grace_until` exactly 7 days after the failure time; a second failure for the same subscription does not move `grace_until`.
2. During grace the entitlements object is unchanged except `status:'past_due'` and `grace_until` populated; `rev` is bumped once.
3. `invoice.paid` within grace returns status to `active`, clears `grace_until`, cancels pending reminders and bumps `rev`.
4. At `grace_until` + <= 5 min the workspace becomes `none`: `rev` bumped, a `plan_changed` notice is published once, and exactly one `wind-down` job is scheduled for +10 min (+/- 5 s) which calls `endLiveHostedSessions` once.
5. `canceled` keeps full entitlements until `period.end` and flips to `none` within 5 min after it.
6. Reminders go out on grace day 0, 3 and 6 only (3 emails, 3 notifications), never twice for the same day, and not after recovery.
7. Replaying the same Stripe event 5 times yields one transition, one audit event, one webhook event.
8. Out-of-order events (`paid` arrives before an older `payment_failed`) never leave the workspace in `past_due` (event time comparison).

## Tests required
- unit: transition table for every (state, event) pair, driven by a fake clock.
- integration: failure -> day 3 reminder -> payment -> back to active (Postgres container).
- integration: failure -> grace expiry -> none -> wind-down job; the cancelled job does nothing if the workspace re-activated within the 10 minutes.
- idempotency test with duplicate and reordered Stripe events.
- contract: emitted `plan_changed` notice and `billing.*` webhook events match CT-WS-SESSION-EVENTS and CT-WEBHOOKS shapes.
- failure-path: SessionEnder throws -> retried with backoff, job lands in DLQ after 5 attempts, alert metric increments.

## Guardrails (MUST / MUST NOT)
- MUST NOT delete any data on transition to `none`; downgrade handling is non-destructive (CT-ENTITLEMENTS §7).
- MUST NOT shorten or extend the 7-day grace window except through the config value validated to 7 (contract).
- MUST re-check status at wind-down execution time and skip if the workspace is no longer `none`.
- MUST NEVER block LAN or local use; only hosted features change.
- MUST make every transition a single DB transaction with the rev bump so clients never see a status without the new rev.
- MUST NOT include card, amount-due text or Stripe ids in notifications; `params` carry ids and enums only.

## Failure modes
- Scheduler down for hours -> next run processes all overdue workspaces in batches of 200, oldest first; no workspace stays past_due beyond grace + 5 min after recovery.
- Email provider down -> reminder job retries; notification and email are independent so one failing does not suppress the other.
- Missing workspace mapping for a Stripe event -> DLQ with the event id; no state change.
