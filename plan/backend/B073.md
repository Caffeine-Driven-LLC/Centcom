## Goal
Seat quantity management for Team workspaces: change seats via PATCH /seats, return a Stripe-computed proration preview with ?preview=true, and keep Stripe quantity, billing records and max_seats in agreement with seat accounting.

## In scope
- PATCH /v1/workspaces/{id}/seats {seats} (billing:write; owner/billing; Idempotency-Key accepted): updates the add-on seat item quantity (seats minus included 5) on the Stripe subscription with proration.
- ?preview=true: calls Stripe invoice preview and returns amounts without changing anything.
- Lower bound: seats may not drop below seats in use (members + pending invites) from B030 seat accounting; upper bound configurable (default 500).
- Applying the result immediately through B070 upsertFromStripe and B069 applySubscriptionState (idempotent with the later webhook).
- Reconciliation job `billing.seats.reconcile` (daily) comparing Stripe quantity with the stored seats and seats in use, repairing drift and logging mismatches.
- Audit event billing.seats_changed.

## Out of scope
- Seat accounting and enforcement on invites: B030.
- Checkout and portal: B071. Webhook ingestion: B072. Entitlement derivation: B069.
- Pro plan (fixed at 1 seat; seat changes return 409).
- Invoices: B077.

## Build against (no counterpart needed)
StripeGateway fake with scripted previewInvoice/updateSubscriptionItems (B070 interface), SeatAccountingPort fake returning seats in use, Postgres container for subscription rows.

## Acceptance criteria
1. preview=true returns amounts as {amount:int, currency} Money objects, performs zero Stripe write calls (fake records none) and leaves DB rows unchanged.
2. Increase from 5 to 8 seats on Team calls Stripe once with quantity 3 on the add-on item and proration_behavior create_prorations; response max_seats = 8 and entitlements rev increments by 1.
3. seats below seats-in-use (e.g. 4 with 6 members) returns 409 with a stable conflict code and no Stripe call; seats 501 returns 422; non-integer returns 422.
4. On Pro or free workspaces PATCH returns 409 (single-seat plans); on a canceled or none status returns 409.
5. Same Idempotency-Key + body replayed returns the same response (Idempotency-Replayed: true) and one Stripe update; different body with the same key -> 409 `idempotency_conflict`.
6. Roles: owner and billing succeed; admin/member/guest get 403 (CT-RBAC: change seats is owner/billing only).
7. Reconcile detects Stripe quantity 10 vs stored 8, updates stored seats and entitlements, and reports drift; running again reports no drift.
8. Stripe failure leaves stored seats unchanged and returns 503 with retry_after_s; no partial entitlement change.

## Tests required

## Guardrails (MUST / MUST NOT)
- MUST NOT reduce seats below members plus pending invites; check and Stripe update MUST be serialised per workspace (advisory lock) to avoid racing invites.
- MUST NOT apply a seat change locally before Stripe accepts it.
- MUST send an idempotency key to Stripe derived from the request Idempotency-Key.
- Preview MUST NOT mutate Stripe or DB state under any circumstances.
- Money MUST be integer minor units; no floating point arithmetic on amounts (use Stripe's values).

## Failure modes
- Stripe accepted the update but the response was lost -> retry with same idempotency key returns the same result; reconcile also heals.
- Invite accepted concurrently while decreasing seats -> lock makes one of them win; loser gets 409.
- B030 port unavailable -> fail closed (503), never assume zero seats in use.
