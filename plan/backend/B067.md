## Goal
Server-side presence history: record connection-derived join/leave timestamps per member and expose last-seen lookups internally, without storing presence payloads or adding a REST endpoint.

## In scope
- Consume connection events from the presence service (B047): member_connected, member_disconnected (after the 10 s grace) with timestamps, and write them to a compact log table.
- Maintain last_seen_at per (session, member) and per device, updated at most once per 60 s per connection.
- lastSeen(sid, memberId) and recentSessions(deviceId, limit) functions for other backend lanes (admin API, search, members listing).
- Retention: log rows kept 30 days then deleted by an in-lane purge function that B090 schedules; last_seen rows live as long as the membership.
- Metrics for connect/disconnect rates.

## Out of scope
- Live presence, typing, cursors and coalescing: B047/B048.
- Any new REST endpoint or field (the contracts expose no last-seen API; the members endpoint is B054).
- Storing presence status/activity values or cursor data.
- Retention scheduling: B090.

## Build against (no counterpart needed)
Fake PresenceEventSource emitting scripted connect/disconnect events with a fake clock; Postgres container for the tables.

## Interfaces (the only surface other lanes may use)
- PresenceHistoryRecorder.onConnected(e:{sid, memberId, deviceId, at: Date}) / onDisconnected(e:{..., reason:'closed'|'timeout'|'kicked'})
- PresenceHistory.lastSeen(sid, memberId): Promise<Date|null>
- PresenceHistory.recentSessions(deviceId, limit<=50): Promise<{sid, lastSeen: Date}[]>
- PresenceHistory.purgeOlderThan(cutoff: Date): Promise<number>
- Tables presence_log(session_id, member_id, device_id, event 'connected'|'disconnected', reason, at) ; member_last_seen(session_id, member_id, device_id, last_seen_at, pk(session_id, member_id))

## Acceptance criteria
1. A reconnect inside the 10 s grace window writes no disconnected/connected pair for the user (matching the presence service's own suppression) in a replayed scripted scenario.
2. lastSeen returns the disconnect time of the latest connection, or the current time bucket if the member is connected now; null for a member who never connected.
3. 1 000 heartbeat-driven touches within a minute for one connection produce at most 1 write to member_last_seen per 60 s (verified by write counter).
4. purgeOlderThan(30 days ago) deletes only presence_log rows older than the cutoff and leaves member_last_seen untouched; returns the exact deleted count.
5. The tables contain no column for status, activity, cursor, path or name (schema allow-list test).
6. Kicked members' last_seen remains queryable for audit but recentSessions excludes sessions the device no longer belongs to.

## Tests required

## Guardrails (MUST / MUST NOT)
- MUST NOT persist presence payloads (status, activity, cursor); CT-WS-PRESENCE says presence is never stored durably, so only connection facts are recorded.
- MUST NOT expose lastSeen outside the backend process boundary; no route is added by this lane.
- MUST NOT write on the hot path synchronously; recorder buffers and flushes every 1 s or 200 events.
- MUST apply the 30-day retention to presence_log (PII minimisation).

## Failure modes
- DB unavailable -> buffer up to 10 000 events in memory, then drop oldest with a counter; relay behaviour is unaffected.
- Out-of-order events (disconnect before connect) -> ignored with debug log, last_seen only moves forward.
