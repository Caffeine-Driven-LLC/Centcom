## Goal
Make data recoverable: continuous Postgres backup with point-in-time recovery, durable object and Redis recovery paths, monthly automated restore drills with measured RPO/RTO, and DR runbooks, including re-application of account deletions after a restore.

## In scope
- Targets: Postgres RPO <= 5 min and RTO <= 60 min; object storage (history, snapshots, exports) RPO <= 24 h via versioning plus daily replication of the `backups` bucket to a second provider, RTO <= 4 h; Redis treated as rebuildable (AOF, RPO <= 1 s best effort), RTO <= 30 min including queue replay from the outbox tables.
- Terraform module `infra/terraform/modules/backup/`: WAL archiving and daily base backups to the `backups` bucket (encrypted with `age`/KMS key, versioned, 35-day retention), second-provider replication job, bucket lifecycle rules, restricted IAM.
- Restore tooling `infra/dr/`: `restore-postgres.sh --to <timestamp>` (PITR into an isolated instance), `restore-verify.mjs` (migration version, row-count sanity against the manifest, checksum sample, smoke queries), `replay-deletions.mjs` (re-apply the deletion log so deleted accounts do not reappear), `restore-drill.sh`.
- Monthly automated drill in stage: restore latest backup to a throwaway instance, run verification, measure time, write `dr-drill-report.json` and fail if RTO exceeds the target.
- Worker job `backup-verify` (every 15 min) exporting metrics `backup_age_seconds`, `wal_archive_lag_seconds`, `last_drill_age_days`.
- DR runbooks under `infra/runbooks/dr/`: region loss, database corruption, accidental deletion (PITR), bucket compromise, key loss, full rebuild order, communications template.

## Out of scope
- Base infrastructure (B091) and alert rules (B094; this lane exports the metrics they use).
- The deletion mechanism itself (account deletion lane B026); this lane reads its durable deletion log.
- Client-side recovery (device keys are client-held and not backed up by the server).
- Retention purge logic (B090).

## Build against (no counterpart needed)
Run backup/restore against the compose Postgres and MinIO with `pg_basebackup` + WAL files; drills in CI use a small dataset (10 000 rows) and a throwaway container; no cloud account is required for tests.

## Interfaces (the only surface other lanes may use)
- Commands: `pnpm dr:drill --env stage`, `pnpm dr:restore --to <ISO timestamp> --target <instance>`, `pnpm dr:verify --target <instance>`.
- Report `dr-drill-report.json` `{started_at, restore_point, rpo_seconds, rto_seconds, verified: boolean, checks: [{name, ok}]}`.
- Metrics `centcom_backup_age_seconds`, `centcom_wal_archive_lag_seconds`, `centcom_dr_drill_age_days`.
- BullMQ job `backup-verify.check` (repeat 15 min); config `BACKUP_MAX_AGE_S=93600`, `DR_RTO_TARGET_S=3600`, `DR_RPO_TARGET_S=300`.

## Acceptance criteria
1. In the CI drill, a PITR restore to a timestamp 2 minutes before a destructive statement recovers the dropped table, and the measured recovery point differs from the requested one by <= 5 min (RPO assertion).
2. The stage drill restores a full backup to an isolated instance and `restore-verify` passes within 60 min (RTO); the report records `rto_seconds` and the drill job fails if it exceeds `DR_RTO_TARGET_S`.
3. After a restore, `replay-deletions` removes every account listed in the deletion log with a deletion time after the backup base time; a test restores a backup taken before an account deletion and asserts the user, devices and memberships are gone before the restored instance accepts traffic.
4. Backups are encrypted: object inspection shows ciphertext (no plaintext SQL header), the decryption key is not stored in the same bucket or repo, and a restore with the wrong key fails cleanly.
5. `backup-verify` exposes `backup_age_seconds` and `wal_archive_lag_seconds`; with the newest backup artificially aged to 27 h the metric crosses the `BackupStale` threshold (26 h) in the alert test.
6. Object versioning is on for `backups` and history buckets: deleting an object and restoring the previous version works and is covered by a runbook step that was executed in stage.
7. Each DR runbook has explicit RTO/RPO, step commands, verification, and who to notify; a tabletop of the 'region loss' runbook is recorded with date and participants.

## Tests required
- CI drill: base backup + WAL + PITR on containers with a seeded dataset.
- replay-deletions test with a pre-deletion backup.
- encryption/negative-key test.
- backup-verify job unit tests with fake clock and storage listing.
- runbook lint: required sections and commands present.
- metric emission test.

## Guardrails (MUST / MUST NOT)
- MUST encrypt every backup at rest and in transit and keep decryption keys outside the backup storage account (offline copy held by two named people).
- MUST re-apply the deletion log after any restore before the restored database receives traffic; a restore without it is a privacy incident.
- MUST NOT restore into the production database in drills; drills use isolated instances with no network route to production.
- MUST NOT copy backups to unapproved locations or developer machines; production data never flows to dev/stage (stage drills use stage backups).
- MUST keep backup retention at <= 35 days so deleted-data persistence is bounded and documented in the privacy notes.

## Failure modes
- WAL archive gap detected -> alert, force a new base backup within 15 min, mark PITR window boundary.
- Second-provider replication fails -> alert after 24 h; primary backups unaffected.
- Drill exceeds RTO -> drill fails, issue filed with timing breakdown; launch gate G6 fails if the last drill is older than 35 days or failed.
