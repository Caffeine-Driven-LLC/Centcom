## Goal
The API runs as a service: one entrypoint reads the configuration once, opens the database and Redis, builds the token service and serves the login routes, and a person can approve a terminal sign-in in the browser, so `centcom login` works against a real backend.

## In scope
- `apps/api/src/main.ts`: parse and validate the config once (B004, exit non-zero before opening any port), open Kysely/Postgres (B007) and Redis (B009), build the app with `buildApp(deps)`, listen, and shut down on SIGTERM/SIGINT by draining in-flight requests (30 s limit) before closing the pools; the only place besides config that reads `process.env`.
- `apps/api/src/app.ts`: `buildApp(deps)` registers the plugins in the order the lanes require (request-context, error handler, telemetry, rate limit, idempotency, auth, rbac, entitlements) and then the route modules from one explicit list `apps/api/src/modules.ts`, so a later lane adds its routes there; a module whose dependencies are not configured is skipped with one logged line instead of failing the boot.
- The login slice wired first: `GET /v1/status`, `GET /healthz` and `GET /readyz` (database and Redis checked, 503 until both answer), `GET /.well-known/jwks.json`, `POST /v1/auth/token`, `POST /v1/auth/revoke`, `POST /v1/auth/device/code`, the PKCE authorize routes and magic-link pages (B018), `GET /v1/me`, and the device list and revoke routes (B020), all using the services of their own lanes.
- The device approval pages (CT-PAGE): `GET /device` (a form for the user code, prefilled from `?user_code=`), `POST /device` (looks the code up with `lookupUserCode`, shows who is asking for access: device name, platform and fingerprint), `POST /device/approve` and `POST /device/deny` calling `approveDeviceGrant` / `denyDeviceGrant`; a visitor who is not signed in is sent to the magic-link page with `return_to` set to the same page, and comes back to it after signing in; pages are server-rendered HTML with a CSRF token, no inline script, and the CSP and cache headers of CT-PAGE.
- `pnpm dev:api` (documented in `docs/api-service.md`, with a pointer from `docs/dev-environment.md`): starts the entrypoint against the `pnpm dev:up` stack with `.env.local`, generating a signing key on first run in `.env.local` only (never committed), with magic-link mail going to the Mailpit catcher.
- An end-to-end test that plays the terminal client with scripted HTTP calls and the browser with a cookie jar: request a code, open the page, sign in with a magic link read from the mail catcher, approve, and poll to receive tokens; then use the access token on `GET /v1/me`, refresh it, and revoke the device.

## Out of scope
- Wiring the other route modules (billing, sessions, webhooks, usage, admin and the rest): they join through `modules.ts` in their own lanes or a follow-up; this lane wires only the login slice and the mechanism.
- New token, grant or login logic: B016, B017 and B018 own them, and this lane only calls their services.
- Deployment, containers for the API and the cloud environments (B091, B092).
- The relay and worker entrypoints.
- A real mail provider and social-login credentials: the mailer and providers are chosen by configuration, and the dev stack uses the mail catcher.

## Build against (no counterpart needed)
The B012 dev stack (Postgres, Redis, Mailpit) for `pnpm dev:api`, and the B010 testkit containers for the tests; the terminal client is scripted HTTP calls and the browser is a scripted cookie jar, so no client or web app is needed.

## Interfaces (the only surface other lanes may use)
- `buildApp(deps: AppDeps): Promise<FastifyInstance>`; `AppDeps` holds the parsed config, the Kysely handle, the Redis handle, the logger, the metrics and the clock, so tests build the app without a process or a port.
- `pnpm dev:api`; env `PORT` (default 8787) and `HOST` (default 127.0.0.1) from the config loader.
- HTTP: `GET /healthz`, `GET /readyz`, `GET /device`, `POST /device`, `POST /device/approve`, `POST /device/deny`, plus the routes of B016, B017, B018, B020 and the status route.
- `registerModule({ name, enabled(deps), register(app, deps) })` entries in `apps/api/src/modules.ts`.

## Acceptance criteria
1. Starting `main.ts` with an invalid or missing config exits non-zero with the config error before any port is opened (test spawns the process with an unused port and checks nothing listens).
2. `GET /readyz` is 200 only while both Postgres and Redis answer and 503 within 2 s of either going away; `GET /healthz` stays 200 while the process runs.
3. SIGTERM lets a request already in flight finish (a 1 s route), refuses new connections, closes the pools and exits 0 within 30 s (process test).
4. `buildApp` registers the plugins in the required order and every route listed under Interfaces answers; a module whose dependencies are missing is skipped with one log line and the rest of the app still boots (test removes the mail config).
5. End to end: code request -> `GET /device?user_code=` while signed out redirects to the magic-link page with `return_to` -> the link from the mail catcher signs the visitor in and returns to `/device` -> the page shows the device name and fingerprint -> approve -> the next poll returns an access token whose `dev` claim is the new device and a refresh token, and `GET /v1/me` with it returns the user.
6. Denying shows a neutral page and the next poll returns `access_denied`; approving a code that expired, was already used or was approved by another user returns the same neutral page as an unknown code, with no detail.
7. The pages carry a CSRF token that a forged cross-site POST cannot supply (403), set `Cache-Control: no-store`, the CT-PAGE security headers and a CSP without `unsafe-inline`; no user code, device code or token appears in any log line of the full flow (log-capture test).
8. After 10 wrong user codes from one user within 10 minutes the lookup is locked and the page says so identically for wrong and expired codes (reuses the B016 limiter; test goes through the page).

## Guardrails (MUST / MUST NOT)
- MUST read `process.env` only in `main.ts` and the config loader; everything else gets its configuration injected.
- MUST NOT start listening before the config is valid and the signing keys are loaded; a missing signing key refuses to start (B017).
- MUST NOT put the user code, device code, tokens, magic-link secrets or cookies in logs, URLs of redirects other than the documented `user_code` prefill, or error pages.
- MUST render every page with the CT-PAGE headers and escape every value that came from a request or a device (device names are untrusted).
- MUST keep unknown, expired, used and wrong-user codes indistinguishable on the page and in timing as far as B016 makes them.
- MUST NOT commit generated keys: `pnpm dev:api` writes them to `.env.local` only.

## Failure modes
- Postgres or Redis unreachable at start -> exit 1 after 3 tries with a clear line; unreachable later -> `/readyz` 503 and requests that need it get a 503 problem with `retry_after_s`.
- Mail cannot be sent -> the magic-link page says the mail could not be sent and offers retry, and the failure is logged without the address.
- A route module throws while registering -> the boot fails with that module's name, unless it declared itself optional.
- The signed-in visitor's session is for a user who was deleted or locked -> the approval page refuses with the same neutral page.
