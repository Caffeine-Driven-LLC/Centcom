## Goal
Users can sign in with GitHub or Google through the standard OAuth flow, with verified-email account matching and no provider tokens retained.

## In scope
- Browser-facing routes (outside the /v1 contract): `GET /login/github`, `GET /login/github/callback`, `GET /login/google`, `GET /login/google/callback`.
- Authorization-code flow as a client of the provider with PKCE (S256), `state` and (Google) `nonce`, stored in a signed, short-lived (10 min), HttpOnly cookie; `return_to` allow-list as in B014.
- GitHub: scopes `read:user user:email`; take identity from `GET /user` and the primary verified address from `GET /user/emails`. Google: scopes `openid email profile`; verify the ID token (signature via Google JWKS, `iss`, `aud`, `exp`, `nonce`) and require `email_verified=true`.
- Account matching: table `identities(provider, subject, user_id, created_at)`; existing identity -> that user; else a verified email matching an existing user -> link; else create user via B013 `getOrCreateByEmail`. Unverified provider emails are never used for matching.
- Provider tokens (access/ID/refresh) are used in memory only and discarded; nothing persisted but `(provider, subject)`.
- Injected `LoginCompleter.complete(reply, userId, returnTo)` shared with B014; provider HTTP calls with 5 s timeouts and an injected fetch for tests.

## Out of scope
- Login-session cookie and PKCE authorize endpoint for Centcom clients (B018).
- Magic-link login (B014).
- Unlinking or managing identities from account settings (not in the contracts).
- Token issuance (B017).

## Build against (no counterpart needed)
A fake GitHub/Google provider server (local HTTP stub with canned JSON and a test JWKS) injected as `fetch`; no real provider credentials; B013 service and B010 stack.

## Interfaces (the only surface other lanes may use)
- `GET /login/{github|google}?return_to=` -> 302 to the provider authorize URL.
- `GET /login/{github|google}/callback?code=&state=` -> 303 to `return_to` after `LoginCompleter.complete`, or an error page.
- `SocialLoginService { begin(provider: 'github'|'google', returnTo: string): Promise<{redirect: string; stateCookie: string}>; complete(provider, query: {code: string; state: string}, stateCookie: string): Promise<{userId: string; returnTo: string}> }`.
- Config: `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `SOCIAL_REDIRECT_BASE_URL`.

## Acceptance criteria
1. `begin` produces an authorize URL containing `code_challenge_method=S256`, a random `state`, and for Google a `nonce`; two calls give different values.
2. A callback with a missing, mismatched or expired (>10 min) state is rejected with a generic error and no user is created.
3. Google ID token with wrong `aud`, wrong `iss`, expired `exp`, bad signature, wrong `nonce` or `email_verified=false` is rejected (one test per case).
4. GitHub account whose only emails are unverified is rejected; a verified primary email logs in.
5. The same GitHub `subject` returns to the same user even if the email changed at the provider; a verified email equal to an existing user's email links to that user and writes one identities row.
6. Two concurrent first logins for one subject create exactly one identity and one user.
7. The database contains no provider access/ID/refresh tokens (schema inspection + dump test); logs contain no codes, tokens or emails.
8. A provider call exceeding 5 s results in a generic error page and a `502`-class log entry, with no partial user created.

## Tests required
- state.test.ts: signature, expiry, tamper.
- google.test.ts: ID token verification matrix with test JWKS.
- github.test.ts: email selection rules with canned responses.
- linking.test.ts: identity/user matching and concurrency.
- redirect.test.ts: return_to allow-list.
- leak.test.ts: no secrets in DB or logs.

## Guardrails (MUST / MUST NOT)
- MUST NOT match or link accounts on an unverified provider email (account takeover vector).
- MUST validate `state` and PKCE on every callback and MUST tie `state` to the initiating browser via the signed cookie.
- MUST NOT persist or log provider tokens, authorization codes or client secrets.
- MUST verify Google ID tokens fully (signature, iss, aud, exp, nonce); MUST NOT trust the userinfo of an unverified token.
- MUST restrict `return_to` to the allow-list.

## Failure modes
- Provider outage or timeout -> user sees a generic retry page; no account changes.
- Provider returns no email -> login rejected with a clear page (we require an email).
- Client secret missing for a provider -> that provider's routes return 404 and the provider is omitted from login pages; startup logs a warning.
