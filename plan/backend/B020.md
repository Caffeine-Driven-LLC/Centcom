## Goal
Users can list, inspect and revoke their devices, and session peers can fetch each other's public keys, with revocation immediately killing the device's tokens.

## In scope
- Endpoints: `GET /v1/devices`, `GET /v1/devices/{id}`, `DELETE /v1/devices/{id}`, `GET /v1/devices/{id}/keys`, plus the CT-AUTH aliases `GET /v1/auth/devices` and `DELETE /v1/auth/devices/{id}` sharing the same service.
- Device view: `{id, name, platform, last_seen_at, fingerprint, created_at, revoked_at}` (no secrets); fingerprint per CT-CRYPTO (`BLAKE2b-128(Dx||Ds)`, base32, `ABCD-EFGH-IJKL`).
- `GET /v1/devices/{id}/keys` returns `{device, x25519, ed25519, fingerprint, revoked}` only to the owner or to a caller who shares a session (a row in `session_members` for both users); otherwise 404.
- Revoke: set `revoked_at`, call B017 `revokeDevice` (kills refresh families and marks access tokens `device_revoked`), mark keys revoked in the keys response, publish on Redis pub/sub channel `devices:revoked` for the relay, emit an audit event.
- `registerDevice(input)` service function (validate pubkeys: 32 bytes base64url, not all-zero; compute fingerprint; insert) and `touchDevice(id)` (throttled `last_seen_at` update, at most once per 5 min).

## Out of scope
- Device creation during login (B016 inserts through its own transaction for now).
- Token internals (B017).
- Relay-side disconnect on revocation (relay lanes subscribe to the pub/sub channel).
- Key bundles and crypto (client side, CT-CRYPTO).

## Build against (no counterpart needed)
B017 token service, B008 schema, B010 stack with factories for users/devices/sessions; relay consumers are simulated by subscribing to the pub/sub channel in tests.

## Interfaces (the only surface other lanes may use)
- `GET /v1/devices` -> `{data: Device[], next_cursor, has_more}`; `GET /v1/devices/{id}` -> Device; `DELETE /v1/devices/{id}` -> 204; `GET /v1/devices/{id}/keys` -> keys object.
- `registerDevice(i:{userId: string; name: string; platform: string; x25519: string; ed25519: string}): Promise<Device>`.
- `deviceFingerprint(x25519: Uint8Array, ed25519: Uint8Array): string` returning `XXXX-XXXX-XXXX`.
- `revokeDevice(actorUserId: string, deviceId: string): Promise<void>`.
- Pub/sub: channel `devices:revoked`, message JSON `{device: string, user: string}` (ids only).

## Acceptance criteria
1. User A listing devices sees only their own; requesting user B's device id returns 404 (not 403).
2. A fingerprint of fixed key bytes matches `^[A-Z2-7]{4}-[A-Z2-7]{4}-[A-Z2-7]{4}$` and is stable across runs.
3. After DELETE, the device's refresh token fails with 401 `device_revoked` and its access token fails within 1 s; DELETE twice returns 204 both times.
4. `registerDevice` rejects 31-byte, 33-byte, non-base64url and all-zero keys, naming the offending field in `errors[].pointer`.
5. `GET /v1/devices/{id}/keys` returns 200 for a peer sharing a session, 404 for a stranger, and still returns keys for a revoked device with `revoked:true` so history verification keeps working.
6. `last_seen_at` is written at most once per 5 minutes per device under 10 000 touches.
7. A message appears on `devices:revoked` exactly once per revocation; revoking an already-revoked device publishes nothing.
8. An API-key principal calling `GET /v1/devices` gets 403 (machine principals have no devices).

## Tests required
- fingerprint.test.ts and pubkeys.test.ts: table-driven key validation, stable fingerprint.
- service.test.ts: ownership, idempotent revoke, throttled touch.
- keys-access.test.ts: shared-session access matrix (self, peer, stranger, revoked).
- revoke-integration.test.ts: B017 tokens fail with device_revoked after DELETE; pub/sub message once.
- routes.test.ts: pagination and the /v1/auth/devices aliases.

## Guardrails (MUST / MUST NOT)
- MUST return 404 rather than 403 for devices of other users to avoid enumeration.
- MUST NOT return private or secret material; public keys only, and only to self or session peers.
- MUST complete token revocation and the pub/sub publish even if the audit write fails (audit failure is logged and retried, not blocking).
- MUST treat public keys of an existing device as immutable; a changed key requires a new device (CT-CRYPTO trust-on-first-use).
- MUST authorise through B021 `can()`.

## Failure modes
- Redis publish fails -> revocation stays committed; a retry loop re-publishes (at least once) and the relay re-checks `revoked_at` on its next membership check.
- DB failure mid-revoke -> transaction rolled back; client gets 503 and may retry (idempotent).
- Peer lookup query slow -> bounded by statement timeout, returns 503 not 500.
## Notes
Overlap: B016 currently inserts devices itself; adopt `registerDevice` there in a follow-up. The DELETE alias paths appear in CT-AUTH while canonical ones are in CT-API-ACCOUNTS; both are served. The pub/sub channel name `devices:revoked` is an internal convention (no contract).
