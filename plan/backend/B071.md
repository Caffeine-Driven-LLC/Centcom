## Goal
Create hosted Stripe Checkout and Customer Portal sessions for a workspace, with server-controlled redirect URLs, mandatory idempotency and strict role checks, so no client can choose where money or users are sent.

## In scope
- POST /v1/workspaces/{id}/checkout (Idempotency-Key required): validates plan, interval, currency, seats; creates a Stripe Checkout Session in subscription mode and returns {url}.
- POST /v1/workspaces/{id}/portal (Idempotency-Key accepted): creates a billing portal session and returns {url}; requires an existing Stripe customer.
- Server-fixed success/cancel/return URLs built from config (https://centcom.dev/billing, with centcom://billing deep link variants per CT-DEEPLINK); the request cannot supply URLs.
- Metadata on the Checkout Session and subscription carrying workspace id (for B072) and automatic tax; plan->price mapping from the B070 catalogue.
- Refusals: already-active paid subscription on checkout (409, direct to portal), plan 'free', seats outside the plan's range.
- Audit events billing.checkout_created and billing.portal_created via the B036 emitter.

## Out of scope
- Gateway, customers and subscription persistence: B070. Webhook processing that activates the plan: B072.
- Seat changes after purchase and proration: B073.
- Coupons/promotion codes and trials: B079.
- Any card collection UI (Stripe hosted pages do it).

## Acceptance criteria
1. checkout without an Idempotency-Key returns 400/422 `idempotency_key_required`; the same key + body twice returns the identical body with Idempotency-Replayed: true and creates exactly one Stripe session; same key with a different body returns 409 `idempotency_conflict`.
2. checkout by owner or billing role returns 200; by admin, member or guest returns 403 `forbidden`; scope billing:write is required (token with billing:read only gets 403).
3. Body containing success_url, cancel_url or return_url is ignored (not forwarded); the recorded Stripe call uses only the configured URLs (test asserts equality).
4. plan 'free', interval 'week', currency 'GBP', or team seats below 5 / above the configured max (default 500) return 422 with errors[].pointer.
5. A workspace with status active/trialing on a paid plan gets 409 on checkout; a workspace with past_due may still reach the portal.
6. The Stripe call includes metadata.workspace_id, automatic_tax.enabled=true, mode 'subscription', client_reference_id = workspace id, and customer = ensureCustomer result.
7. portal for a workspace without a Stripe customer returns 404/409 (no customer is created by portal); with a customer returns {url} and the return URL is the configured billing URL.
8. Both endpoints write one audit event with actor, workspace and plan (no URL, no Stripe ids in the audit payload).

## Guardrails (MUST / MUST NOT)
- MUST NOT accept redirect URLs from the client (open-redirect and phishing risk).
- MUST require Idempotency-Key on checkout creation (CT-PAGE) and forward a deterministic Stripe idempotency key.
- MUST NOT log the returned Stripe URL (it grants a session) or the Stripe session id with user data.
- MUST NOT grant any entitlement on checkout creation; only B072 webhook processing may change the plan.
- Plan, price and currency MUST come from the server catalogue; the client cannot send price ids or amounts.

## Failure modes
- Stripe error 4xx (invalid price) -> 502 with generic detail and alert (config bug), never leak Stripe messages.
- Stripe timeout -> 503 with retry_after_s; the client retries with the same Idempotency-Key and gets the same session.
- Customer creation succeeded but session failed -> customer reused on retry (B070).
