## Goal
POST endpoints accept an Idempotency-Key and replay stored responses for 24 hours, with required-key enforcement on the endpoints the contract names.

## In scope
- Fastify plugin handling `Idempotency-Key` (ULID or UUID, <= 64 chars) on POST; per-route config `idempotency: 'accepted' | 'required'`.
- Store (B009 KeyValue) key -> {fingerprint, status, headers subset, body, created_at} with 24 h TTL, scope = (principal id, method, route template, key).
- Request fingerprint = sha256 over method + route template + path params + canonicalised JSON body (sorted keys).
- Replay: same key + same fingerprint -> stored status/body with header `Idempotency-Replayed: true`; same key + different fingerprint -> 409 `idempotency_conflict`; in-flight duplicate (lock key TTL 30 s) -> 409 `idempotency_conflict` with `Retry-After: 1`.
- Missing key on `required` routes -> `idempotency_key_required`. Required set (route config set by the owning lanes): checkout creation, invite creation, usage event ingest, webhook endpoint creation.
- Optional response encryption (AES-256-GCM, key from `IDEMPOTENCY_ENCRYPTION_KEY`) for routes flagged `sensitiveResponse` (e.g. API key creation) so secrets do not rest in Redis in plaintext.

## Out of scope
- Rate limiting (B023) and pagination (B025).
- Declaring `required` on specific endpoints (each endpoint's lane sets route config).
- Message-level dedup on WebSocket frames (relay lanes; `(sid, from, id)` for 24 h).

## Build against (no counterpart needed)
B009 in-memory KeyValue with a fake clock and Fastify inject() with test routes that count handler invocations.

## Interfaces (the only surface other lanes may use)
- Route config: `{ config: { idempotency: 'required' | 'accepted', sensitiveResponse?: boolean, maxStoredBytes?: number } }`.
- `idempotencyPlugin: FastifyPluginAsync<{kv: KeyValue; clock?: () => number; encryptionKey?: Secret<Uint8Array>}>`.
- `fingerprintRequest(method: string, route: string, params: object, body: unknown): string` (`sha256:<hex>`).
- Response header: `Idempotency-Replayed: true` on replays.

## Acceptance criteria
1. Calling a `required` route without the header returns a 400-class problem `idempotency_key_required` and runs no handler code.
2. Two POSTs with the same key and body invoke the handler once; the second returns identical status and body plus `Idempotency-Replayed: true`.
3. The same key with a body differing by one field returns 409 `idempotency_conflict`; the handler is not invoked.
4. Keys longer than 64 chars or not ULID/UUID-shaped are rejected with a validation problem pointing at the header.
5. 20 concurrent identical requests produce exactly one handler invocation and one stored 2xx; the others get 409 (in-flight) or a replay.
6. Stored entries expire after 24 h (fake clock +24 h: the same key is treated as new); replay at +23 h 59 m still works.
7. Responses with status >= 500 are not stored (a retry re-executes); 2xx and 4xx are stored.
8. Different principals using the same key string do not collide.
9. With `sensitiveResponse`, the Redis value does not contain the response secret in plaintext (grep test), and replay still returns the original body.

## Tests required
- plugin.test.ts: required, accepted, replay, conflict, in-flight.
- fingerprint.test.ts: key-order independence.
- concurrency.test.ts: 20 parallel identical requests, one handler run.
- expiry.test.ts: 24 h TTL with fake clock.
- crypto.test.ts and principal-isolation.test.ts: encrypted replay round-trip, tamper detection, no cross-principal replay.

## Guardrails (MUST / MUST NOT)
- MUST scope keys by principal so one user's key can never replay another user's response.
- MUST NOT store `Set-Cookie`, `Authorization` or other secret-bearing headers; MUST encrypt bodies of routes flagged `sensitiveResponse`.
- MUST NOT store 5xx responses or responses larger than 256 KiB (1 MiB for usage ingest); oversized responses are served normally but not stored, with a metric.
- MUST acquire the in-flight lock atomically (`setIfAbsent`) before running the handler.
- MUST compare fingerprints in constant time.

## Failure modes
- KeyValue store down -> `required` routes fail with 503 and `retry_after_s` (never run unprotected); `accepted` routes run without protection and increment a warning metric.
- Handler throws -> in-flight lock released; nothing stored for 5xx; 4xx AppErrors are stored.
- Process crash mid-request -> the lock expires after 30 s and the client retry re-executes.
