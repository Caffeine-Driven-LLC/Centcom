## Goal
A person can create a session in `branch` mode (every member runs their own agents, on their own computer) and the relay applies the branch-mode rules to it, so several computers can each run their own agents in one shared session. Until now nothing could create one: the API stored no mode and the relay's mode port answered `command_post` for every session.

## In scope
- Migration: `sessions.mode` (`command_post` default, or `branch`), set once at creation and never changed; existing rows are `command_post`.
- `POST /v1/sessions` accepts `mode` (CT-API-SESSIONS); `GET /v1/sessions/{id}` and the list return it; an unknown value is `validation_failed`; the `session.create` audit event carries it.
- The relay's `SessionModePort` (B057) reads the stored mode (cached for the session's life, since it never changes) instead of answering `command_post`; `welcome.p.session.mode` reports it to every client; B057's agent rules, B061's branch handler and conflict signal and the kind policy apply it as their cards already describe.
- `pnpm dev:branch-check` (tools/dev): two fresh accounts in one branch session, each spawning and running their own agent through the real client libraries: `agent.spawn` (owner, `runs_on`), `agent.state`, `agent.exit`, `branch.update`, `message.*` from the owner, `approval.request` and `approval.decision` with approver `owner`, `file.lock` and the relay's `conflict.detected` on the same `path_hmac`, `presence.update` with `agent_count`, `agent.handoff`, late-joiner replay; and the refusals (a member emitting for an agent they do not own, a viewer emitting anything but presence and comments).
- The command-post gate (`agents/mode-gate.ts`): in a `command_post` session an editor's `message.*`, `tool.*`, `approval.request`, `diff.share`, `file.lock` and `agent.handoff` are refused `forbidden` (the catalogue's `editor*`); in a `branch` session an `agent.handoff` offer must come from the agent's owner, and a `file.lock` names an agent the sender owns (B059's service checks it against B057's registry).

## Out of scope
- Changing a session's mode after creation (the contract fixes it).
- Client changes: the apps choose the mode and publish their agents in their own lanes.
- New event kinds (B111).

- `pnpm dev:branch-check` exits 1 when a step fails.

## Acceptance criteria
1. Creating a session with `mode: 'branch'` returns `mode: 'branch'` on create, get and list; omitting it gives `command_post`; any other value is `validation_failed`; the mode cannot be changed by `PATCH`.
2. In a branch session an editor can `agent.spawn` with `owner` equal to its own member id, send `agent.state` and `agent.exit` for it and `message.*`; it cannot spawn with another member's id as owner, nor update, exit or `agent.handoff` another member's agent (`forbidden`); the host may act on any agent.
3. In a command-post session only the host may spawn, update or exit agents (unchanged), and an editor's `message.*` or `branch.update` is refused `forbidden` (the contract's `*` rule), while a viewer's are refused as before.
4. Two members' agents locking the same `path_hmac` make the relay emit `conflict.detected` naming both agents; each member sees only the other's agent ids and the hash, never the path.
5. A late joiner to a branch session receives the agents and their latest states from the registry and the sequenced events from history.
6. `pnpm dev:branch-check` ends OK against the live stack and fails (exit 1) if any listed refusal is not refused.
7. In a command-post session an editor's `message.user`, `file.lock` and `approval.request` are refused `forbidden`; in a branch session a lock or handoff offer naming another member's agent is refused `forbidden`; the relay cannot check the owner of an encrypted `message.*` (the agent id is in `ct`), which is documented, and receiving clients check it.

## Tests required
- session.mode.test.ts (API: create, get, list, validation, PATCH refuses).
- branch-mode.relay.test.ts (welcome carries the mode; the registry, handler and kind policy apply it).
- branch-mode.e2e.test.ts (two members, their own agents, the refusals) on the testkit containers.

## Guardrails (MUST / MUST NOT)
- MUST NOT read or store anything from `ct` (the relay checks only the clear part).
- MUST fail closed: a session whose mode cannot be read is treated as `command_post`.
- MUST NOT change the mode of an existing session.
- MUST keep every existing command-post behaviour unchanged.

## Failure modes
- The mode lookup fails (database down) -> the frame is answered `service_unavailable` with `retry_after_s`, never accepted under the wrong mode.
- A client built before the field existed creates sessions without `mode` -> `command_post`.
## Notes
Added because the contract describes branch mode but nothing could create a branch session, so the cross-computer case (several people each running their own agents on one project) could not work. See plan/adr/0003. The existing files (routes/sessions/list-create.ts, agents/ports.ts, handshake) are edited in place; they stay owned by their lanes.
