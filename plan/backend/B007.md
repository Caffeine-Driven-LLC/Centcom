## Goal
A shared database package gives every lane a pooled Postgres client, a forward-only migration runner and agreed conventions, so schema work is uniform and safe.

## In scope
- Kysely + `pg` client factory with pool settings (max 10, idle 30 s, connect timeout 5 s, statement_timeout 10 s, idle_in_transaction_session_timeout 15 s) read from config.
- Migration runner: plain SQL files in packages/db/migrations named `<yyyymmddhhmmss>_<snake_name>.sql`, applied in order inside a transaction, tracked in table `schema_migrations(version, name, checksum, applied_at)`, advisory-lock guarded so two instances never migrate at once.
- CLI `centcom-db migrate | status | new <name>` (no down migrations; each file ends with a `-- rollback note:` comment).
- Helpers: `withTransaction(db, fn)` with serialization-failure retry (max 3), `expectedMigrationVersion()` for /readyz, `healthCheck(db)`.
- packages/db/CONVENTIONS.md: table/column naming, text ids with prefix CHECK constraints, `created_at/updated_at timestamptz`, soft delete rules, expand-migrate-contract policy, index naming.

## Out of scope
- Any application table (B008 and later feature lanes).
- Test containers and factories (B010).
- Backups, PITR, replicas (infra lanes).

## Build against (no counterpart needed)
Integration tests use a real Postgres 16 started by the CI service container or local compose; the pure parts (file ordering, checksum) run without a database.

## Interfaces (the only surface other lanes may use)
- `createDb(cfg:{url:string; poolMax?:number}): Kysely<Database>` and `closeDb(db)`.
- `migrate(db, dir: string, opts?:{target?: string}): Promise<{applied: string[]}>`; `migrationStatus(db, dir)`.
- `withTransaction<T>(db, fn:(trx)=>Promise<T>, opts?:{isolation?: 'read committed'|'repeatable read'|'serializable'}): Promise<T>`.
- `expectedMigrationVersion(dir: string): string` (latest file version) and `healthCheck(db): Promise<{ok: boolean; migrationsAtExpected: boolean}>`.
- CLI: `pnpm --filter @centcom/db migrate`.

## Acceptance criteria
1. Applying 3 sample migrations to an empty database creates them in version order; running again applies none and exits 0.
2. Editing an already-applied migration file makes `migrate` fail with a checksum-mismatch error and apply nothing.
3. Two concurrent `migrate` processes: exactly one applies, the other waits on the advisory lock and then applies nothing.
4. A migration failing midway leaves no partial changes and no row in schema_migrations.
5. `withTransaction` retries a forced serialization failure (SQLSTATE 40001) up to 3 times and then rethrows.
6. `healthCheck` returns `migrationsAtExpected:false` when the DB is one migration behind.
7. A query exceeding the statement timeout is cancelled (test sets 1 s and runs `pg_sleep(2)`).

## Tests required
- runner.test.ts: ordering, checksum, atomicity, lock (real Postgres).
- tx.test.ts: retry on 40001, rollback on error, nested use rejected.
- health.test.ts: behind/ahead/unreachable.
- conventions.test.ts: lints migration files for the `-- rollback note:` footer and forbids DROP TABLE/COLUMN outside a `-- contract` phase marker.

## Guardrails (MUST / MUST NOT)
- MUST use parameterised queries only; MUST NOT expose a raw string-SQL helper outside migrations.
- MUST keep migrations forward-only and backward compatible with the previous release (expand -> migrate -> contract); destructive statements need an explicit `-- contract` marker.
- MUST never log SQL parameters or connection strings.
- MUST run migrations as a separate deploy step (CLI), not on API/relay boot.

## Failure modes
- Database unreachable -> createDb succeeds lazily, healthCheck reports ok:false, callers get a typed unavailable error (not a raw pg error).
- Lock not acquired within 60 s -> migrate exits non-zero with a message naming the lock.
- Pool exhausted -> queries wait at most 5 s then fail with an unavailable error; pool saturation metric exposed.
