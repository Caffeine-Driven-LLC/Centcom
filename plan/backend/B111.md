## Goal
Agents on different computers share what they learn: the relay accepts, validates, rate-limits, sequences and stores the three board event kinds of the shared context board, so every member's agents can receive each other's decisions, warnings and findings and a late joiner gets them from history.

## In scope
- Kind policy (B043): `board.note` and `board.pin` from the host and editors, `board.remove` from the host or the author of the note; a viewer sending any of them is `forbidden`; a muted member's are dropped like other events.
- A relay stage (`apps/relay/src/board/`, order beside B057): validates the clear part against the schema (`type`, `supersedes`, `note`, `pinned`), keeps a small document of the session's notes (note id = the `msg_` id of the `board.note` frame, author, type, pinned, removed, sequence) so it can refuse a `board.pin` or `board.remove` naming an unknown or already removed note (`invalid_frame`) and a `board.remove` from anyone but the host or the author (`forbidden`), and a `supersedes` that names a note by someone else (unless host).
- Limits: at most 20 `board.note` per member per hour and 500 live notes per session; over the limit the frame is refused `frame_rate_exceeded` with a detail naming the limit and is not sequenced (a sliding window in Redis, like B057's state limiter); metrics `relay_board_notes_total{type}`, `relay_board_refused_total{reason}`.
- State: one Redis document per session (`relay:board:<sid>`, 48 h after its last change, under a mutex), holding only note id, author, type, pinned and removed; history and replay carry the sequenced frames as for every kind; the purge of a session deletes the document; never any text or refs (those stay in `ct`).
- `tools/dev/branch-check-board.ts`, run by `pnpm dev:branch-check` (B110): two members exchange notes, pin and remove, with the refusals above, the rate limit and a late joiner reading the notes from history.

## Out of scope
- Reading the encrypted text or refs (the relay cannot).
- The client's board and its digests (client lanes).
- Erasing a removed note's frame from history (the frame is ciphertext; removal is a display rule).

## Acceptance criteria
1. A host or editor `board.note` is sequenced and fanned out to every member including viewers; a viewer's is `forbidden`.
2. The 21st note by one member within an hour is refused `frame_rate_exceeded` and not sequenced; the 501st live note of a session likewise.
3. `board.pin` naming an unknown note is `invalid_frame`; by a viewer `forbidden`; by a host or editor it is sequenced.
4. `board.remove` by the author or the host is sequenced; by another editor `forbidden`; naming a removed note `invalid_frame`.
5. A late joiner receives the board events from history in order; the board rows are gone after the session's purge.
6. A frame whose `p` fails the schema is `invalid_frame`; the relay never logs or stores `ct`.

## Tests required
- board.stage.test.ts (roles, validation, unknown and removed notes).
- board.limits.test.ts (per member per hour and per session).
- board.store.test.ts (the document, the mutex, purge).
- dev:branch-check board steps.

## Guardrails (MUST / MUST NOT)
- MUST read only `p`, never `ct`.
- MUST NOT put note text, refs or paths in logs, metrics labels or the table.
- MUST keep sequencing unchanged: refusals happen before sequencing and consume no sequence number.

## Failure modes
- Redis down -> the rate limit fails closed for `board.note` (503) while `board.pin` and `board.remove` go on.
- The note table cannot be read -> pin and remove are refused `service_unavailable` rather than accepted blind.
