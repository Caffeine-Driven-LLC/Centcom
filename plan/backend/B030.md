## Goal
Count workspace seats and enforce the `max_seats` entitlement atomically when members are invited or accepted, and expose seat usage for the entitlements `usage.seats` value.

## In scope
- `SeatService.usage(wspId)` = active memberships + pending, unexpired invites (reserved seats).
- `seatGate` Fastify decorator implementing `assertCanAdd(trx, wspId)`: takes a per-workspace advisory lock, reads `limits.max_seats` through the B069 entitlements reader, rejects when usage >= limit (null = unlimited).
- Read-only seat summary helper for B073/B069 (`getSeatUsage`).
- Downgrade behaviour: when usage > new limit, no membership is removed; only new adds are blocked.
- Metrics `seat_gate_rejections_total{reason}`.

## Out of scope
- Entitlement computation and caching (B069).
- Stripe seat quantity sync and proration (B073); PATCH /v1/workspaces/{id}/seats (B073).
- Invite and accept endpoints (B029) - they call this gate.
- Removing members on downgrade (CT-ENTITLEMENTS section 7 is a product process, not this lane).

## Build against (no counterpart needed)
The B069 entitlements reader replaced by a stub returning fixtures from contracts/fixtures/entitlements/ (free: max_seats 1, team: 5, unlimited: null); Postgres via the B010 harness for the lock tests; no Stripe.

## Deliverables
- `apps/api/src/modules/seats/`
- `packages/db/migrations/0030_seat_indexes.sql`

## Interfaces (the only surface other lanes may use)
- TS: `interface SeatService { usage(wspId: string, trx?: Trx): Promise<{ members: number; pending_invites: number; total: number }>; }`
- TS: `interface SeatGate { assertCanAdd(trx: Trx, wspId: string): Promise<void> }` registered as Fastify decorator `seatGate`.
- Error: throws the registry `entitlement_*` error (HTTP 403) with `detail` naming the limit but no other workspace data.
- DB: index `memberships(workspace_id)` and partial index `invites(workspace_id) WHERE accepted_at IS NULL AND revoked_at IS NULL`.

## Acceptance criteria
1. With max_seats 5 and 4 members + 1 pending invite, `assertCanAdd` throws; with 3 members + 1 pending it passes.
2. 20 concurrent `assertCanAdd` + insert transactions against 1 free seat yield exactly 1 success and 19 rejections (advisory lock `pg_advisory_xact_lock(hashtext(wspId))`).
3. `max_seats: null` never rejects; `max_seats: 0` always rejects.
4. Expired and revoked invites do not count; they stop counting at the instant of expiry (+-1 s).
5. When the entitlements reader is unavailable the gate throws 503 (retryable) and does not allow the add.
6. `usage()` returns in < 20 ms p95 for a workspace with 50 members and 100 invites.

## Tests required
- seats.gate.test.ts: boundary cases, null/0 limits, expiry boundary with a fake clock.
- seats.concurrency.test.ts: 20 parallel adds, 1 seat.
- seats.downgrade.test.ts: usage 8 with new limit 5 blocks adds, removes nobody.
- seats.dependency-failure.test.ts: entitlements reader error -> 503 fail closed.

## Guardrails (MUST / MUST NOT)
- The gate MUST fail closed when entitlements cannot be read; never default to unlimited.
- The count and the insert MUST share one transaction and one advisory lock, or the limit can be exceeded under concurrency.
- The error `detail` MUST NOT include other members' data or Stripe/plan internals.
- MUST NOT read plan names or Stripe state to decide; only `limits.max_seats` (CT-ENTITLEMENTS section 1).
- Whether `guest` and `billing` roles consume a seat MUST be a single config constant (`SEAT_COUNTED_ROLES`, default all roles), not scattered conditions.

## Failure modes
- Lock wait exceeds 5 s -> 503 retryable with `Retry-After`, no partial state.
- Entitlements cache stale by <= 30 s -> accepted per CT-ENTITLEMENTS section 6; the DB count is always live.
- Pending invites referencing deleted workspaces -> ignored by the count query.
