## Goal
Maintain the in-memory registry of session rooms and enforce who may be in a room and who may send which kind of frame, using the live membership record rather than ticket claims.

## In scope
- `RoomRegistry`: create room on first join, track connections per member/device, evict a room 60 s after the last leave.
- Join authorisation: live membership + session state + `max_session_members` entitlement (hard cap 50), producing the 4403/4404 outcomes and populating `SessionAccess` (port consumed by B038) with a Postgres implementation.
- Authorise stage (order 20): per-kind minimum role table taken from the CT-WS-SESSION-EVENTS catalogue ('Who may send') and CT-RBAC session matrix; server-only kinds from clients are rejected; muted state is consulted via `MuteState` port.
- Live membership cache <= 2 s (CT-RBAC rule 2) plus subscription to `centcom:membership` events for immediate revocation (close 4403).
- Audit of denied privileged frames through B036 `emitDetached`.

## Out of scope
- Business rules of control and queue frames (kick, approve, caps - B051, B052).
- Slot assignment (B031), ticket verification (B038), fan-out (B044).
- Session lifecycle states (B053), join-token minting (B054).

## Build against (no counterpart needed)
The mock client simulator from B011 (scripted fake clients speaking the WS protocol), the in-memory B009 KV/pub-sub implementations, and the frame fixtures in contracts/fixtures/events/; no real client is needed. `SessionAccess` and `MuteState` in-memory doubles; membership changes are injected by publishing on the in-memory `centcom:membership` channel.

## Interfaces (the only surface other lanes may use)
- TS: `interface Room { sid: string; join(conn: RelayConnection, m: MemberView): void; leave(conn: RelayConnection): void; members(): MemberView[]; connections(): Iterable<RelayConnection>; connectionsOf(memberId: string): RelayConnection[]; closeMember(memberId: string, code: number): void }`
- TS: `interface RoomRegistry { get(sid: string): Room | undefined; getOrCreate(sid: string): Room; count(): number }`
- TS: `authorizeFrame(m: MemberView, frame: InboundFrame, mute: MuteState): { ok: true } | { ok: false; error: 'forbidden' }`
- TS: `export default relayModule: RelayModule` (order 20).
- Table `KIND_MIN_ROLE: Record<string, Array<'host'|'editor'|'viewer'>>` in `apps/relay/src/rooms/kind-policy.ts`; a test asserts it covers every kind in `events.schema.json`.
- Pub/sub input: `centcom:membership` `{type:'role_changed'|'removed'|'left', wsp, mem, user, role?, at}`.

## Acceptance criteria
1. A viewer sending `message.user` or `queue.submit` gets `sys.error` `forbidden` and the frame is not sequenced; a viewer sending `reaction` and `comment.add` passes; an editor sending `queue.approve` or any `control.*` is rejected; the host passes all host-allowed kinds.
2. Clients sending server-only kinds (`control.member_joined`, `control.roster`, `control.host_changed`, `control.session_state`, `control.rotate_key`, `queue.state`) are rejected `forbidden` for every role including host.
3. A muted member's `event`/`queue` frames are dropped (not an error close) while `presence` still passes.
4. Changing a member's role to `viewer` in the DB takes effect for their next privileged frame within 2 s even with no pub/sub message; with the pub/sub message it takes effect within 200 ms.
5. A `removed` membership event closes that member's connections with 4403 within 500 ms and `RoomRegistry` drops them.
6. The 51st distinct member joining a session is refused (4403); with `max_session_members` 4 the 5th is refused; reconnecting devices of an existing member are not counted twice.
7. Role comes from the live record: a ticket claiming `host` for a member now `viewer` joins as `viewer`.
8. A room with no connections is evicted 60 s (+-1 s) after the last leave; 10 000 join/leave cycles leave `RoomRegistry.count()` at 0 after the eviction timer.
9. Each denied privileged frame writes one audit event with outcome `denied` (no frame content in `meta`).

## Guardrails (MUST / MUST NOT)
- Authorisation MUST use the live membership/role, never the ticket's `role` or any client-sent field (CT-RBAC rule 1, 3).
- Default deny: a kind missing from `KIND_MIN_ROLE` that is not an unknown-future kind is rejected; unknown kinds from newer clients are forwarded only for roles `host` and `editor`.
- The relay MUST NOT decide content-level permissions it cannot see (e.g. which agent a message targets); only role/kind checks.
- A member removed from the workspace MUST lose access on the next frame; never rely on the connection staying authorised until reconnect.
- Rejected frames MUST NOT be logged with payload; log kind, sid, member id and result only.
- Room state is per node and in memory; nothing here may be treated as global truth (cross-node is B045).

## Failure modes
- Membership DB read fails -> deny privileged frames with `sys.error` 503-class (fail closed), keep the connection.
- Pub/sub subscription lost -> fall back to the 2 s polling re-check and log; resubscribe with backoff.
- Room evicted while a late join races -> `getOrCreate` is atomic; the joiner gets a fresh room.
