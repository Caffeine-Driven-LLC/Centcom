## Goal
Let a user delete their account (30-day grace, then irreversible purge) and request a downloadable export of their own data, exactly as CT-API-ACCOUNTS describes, without ever exporting or retaining other people's data or session ciphertext content.

## In scope
- DELETE /v1/me: validate no blocking state, mark the user `deletion_scheduled_at = now + 30 d`, revoke all refresh tokens and devices, write audit, return 202 with `Location` pointing at `/v1/me` (CONTRACT GAP below).
- POST /v1/me/export (Idempotency-Key accepted) and GET /v1/me/export/{id}: enqueue an export job, report status `pending|running|ready|failed|expired`, return a signed download URL (TTL 15 min per request) when ready.
- BullMQ job `account-export`: builds one JSON document of the user's own records (profile, preferences, devices with public-key fingerprints, memberships, API-key metadata without secrets, own notification preferences, own audit events) and stores it in the blob store as `exports/<usr>/<exp>.json`.
- BullMQ job `account-purge`: scheduled for the grace deadline; hard-deletes the user's rows and pseudonymises audit rows; idempotent and resumable.
- Service function `cancelDeletion(userId)` that clears the schedule (to be called by login flows; no HTTP endpoint).
- Migration adding `users.deletion_scheduled_at`, `users.deleted_at` and table `account_exports`.

## Out of scope
- GET /v1/me and PATCH /v1/me (B022).
- The audit emitter library itself (B036); this lane only calls it.
- Workspace deletion and workspace purge hooks (B027).
- Retention/purge of session history and snapshots (B090, B055); no session ciphertext is exported.
- Sending emails (B032 templates are not a dependency of this lane).

## Build against (no counterpart needed)
Fastify app built with the B006 error handler and the B010 test harness (Postgres/Redis containers, factories). Call routes with app.inject() and an HMAC-free test access token minted by the B017 test signer; authorisation uses the B021 RBAC engine; no client is involved. The blob store is the in-memory/MinIO S3 stub from B010; time is advanced with a fake clock to cross the 30-day boundary.

## Interfaces (the only surface other lanes may use)
- HTTP: DELETE /v1/me -> 202; POST /v1/me/export -> 202 `{id, status}`; GET /v1/me/export/{id} -> 200 `{id, status, created_at, expires_at, download_url?, size?}`.
- TS: `interface AccountLifecycleService { requestDeletion(userId: string, ctx: RequestCtx): Promise<{ scheduledFor: string }>; cancelDeletion(userId: string): Promise<void>; requestExport(userId: string, ctx: RequestCtx): Promise<{ id: string; status: ExportStatus }>; getExport(userId: string, exportId: string): Promise<ExportView>; }`
- TS: `purgeUser(deps: PurgeDeps, userId: string): Promise<void>` used by the `account-purge` job.
- DB: `users.deletion_scheduled_at timestamptz null`, `users.deleted_at timestamptz null`; table `account_exports(id text pk, user_id, status, blob_key, size_bytes, created_at, expires_at, error_code)`.
- BullMQ queues `account-export` (attempts 5) and `account-purge` (delayed job, jobId `purge:<usr>` so it is unique).

## Acceptance criteria
1. DELETE /v1/me returns 202; `users.deletion_scheduled_at` equals now + 30 d (+-1 s); all of the user's refresh tokens are revoked and a request using an old access token's device gets 401 `device_revoked` within 1 s of the call.
2. DELETE /v1/me twice returns 202 both times and keeps the original schedule (no extension).
3. A user who is the only owner of a workspace that still has other members gets 409 and nothing is scheduled; a user who is sole member of a workspace has that workspace queued for deletion with the account.
4. POST /v1/me/export with the same Idempotency-Key and body returns the same export id with `Idempotency-Replayed: true`; a second export requested within 24 h with a different key returns 429 with `Retry-After`.
5. GET /v1/me/export/{id} for another user's export returns 404 (not 403); a `ready` export returns a `download_url` that expires in 900 s (+-5 s) and the file is valid JSON that contains no other user's email, no token, no key secret, no `ct` value.
6. An export in `ready` status becomes `expired` after 7 days and its blob is deleted by the same job family; polling then returns status `expired` without a URL.
7. `account-purge` run after the grace deadline deletes the user row, devices, tokens, memberships, API keys, notifications, preferences and exports; audit rows keep the `aud_` id but `actor_id` becomes the constant `usr_deleted`; running the job twice is a no-op.
8. If the user calls `cancelDeletion` before the deadline, the delayed purge job is removed and the purge job, if it still fires, exits without deleting anything.

## Tests required
- account-lifecycle.routes.test.ts: delete, repeat delete, blocked by sole-owner rule, export create/poll/replay, cross-user 404.
- account-export.job.test.ts: golden export for a seeded user; negative grep for other users' emails, `refresh`, `secret`, `sha256(`.
- account-purge.job.test.ts: fake clock +30 d, full purge, idempotent re-run, cancel-before-deadline, audit pseudonymisation.

- Contract: responses validate against the generated CT-API-ACCOUNTS validators from B003.

## Guardrails (MUST / MUST NOT)
- MUST NOT export or retain anything belonging to another user (member lists show only the caller's own membership rows); this is a GDPR access-request surface.
- MUST NOT put the export in the API response body or in logs; only a short-lived signed URL, and the URL itself MUST NOT be logged.
- Purge MUST be a hard delete of personal fields (name, email, avatar, locale, preferences); audit rows are pseudonymised, never deleted here (retention is B090).
- MUST NOT allow API-key principals to call DELETE /v1/me or POST /v1/me/export.
- Revocation of tokens/devices MUST happen in the same DB transaction that sets the schedule, so a crash cannot leave a scheduled-but-active account.
- Deletion MUST NOT silently orphan a workspace that has other members; it fails with 409 instead.

## Failure modes
- Export job crashes mid-build -> BullMQ retries up to 5 times with exponential backoff and jitter; after the last attempt status `failed` with `error_code` set and no partial blob left behind.
- Blob store unavailable at upload -> job retries; the API keeps returning `running`, never a URL.
- Purge job fails halfway (e.g. FK) -> transaction rolls back per entity group, job retries, pager metric `account_purge_failed_total` increments; user stays in scheduled state.
- Export requested for a user already scheduled for deletion -> still allowed during grace (data-portability right).
## Notes
CONTRACT GAP: contract says DELETE /v1/me returns a `Location` of status but defines no deletion-status endpoint nor a way to cancel; this card points `Location` at /v1/me and offers `cancelDeletion` as a service function only.
