## Goal
The in-app notification inbox REST API: list with unread filter and pagination, mark one read, mark all read, with strict per-user isolation.

## In scope
- GET /v1/notifications?unread=true&limit&cursor returning CT-NOTIF-PAYLOAD objects ordered newest first.
- POST /v1/notifications/{id}/read and POST /v1/notifications/read-all (idempotent).
- Unread count header or field for fast badges (X-Unread-Count response header; additive).
- Retention-aware query (hide rows older than 90 days even before purge) and a 500-row cap on read-all per call batch loop.
- ETag/conditional behaviour is not used; rate limits per CT-PAGE.

## Out of scope
- Creating notifications: B063. Preferences: B066. Push: B064.
- Deleting/purging notifications: B090.
- Real-time delivery of new notifications over the relay (not in contracts).

## Build against (no counterpart needed)
Postgres container with notifications seeded by factories (B010) matching the B063 table definition; Fastify inject with test tokens; generated notification types for response validation.

## Interfaces (the only surface other lanes may use)
- GET /v1/notifications?unread=true|false&limit=1..200&cursor -> {data: Notification[], next_cursor, has_more}  (header X-Unread-Count)
- POST /v1/notifications/{id}/read -> 200 Notification (read_at set)
- POST /v1/notifications/read-all -> 200 {updated: number}
- InboxService.list(userId, q) / markRead(userId, id, now) / markAllRead(userId, now)

## Acceptance criteria
1. A user with 120 notifications (30 unread) gets 50 per page by default, 3 pages total, newest first with stable cursor ordering; unread=true returns exactly 30.
2. Reading user B's notification id as user A returns 404 on read and never appears in list; same for read-all affecting only the caller's rows.
3. POST read twice leaves read_at at the first timestamp (idempotent) and both calls return 200.
4. read-all marks all unread rows (tested with 1 200) and returns the exact updated count; a second call returns updated: 0.
5. limit=201 returns 422; an expired or foreign cursor returns 400 with a stable code in the pagination family.
6. Response items validate against the generated notification type and contain no extra fields; read_at is null for unread.
7. Requests need scope profile; an API key without profile gets 403; unauthenticated gets 401 token_invalid or token_expired.
8. Rows older than 90 days are not returned.

## Tests required
- inbox.list.test.ts: pagination, unread filter, ordering, retention window
- inbox.isolation.test.ts: cross-user access
- inbox.read.test.ts: idempotent read and read-all
- inbox.contract.test.ts: schema validation
- inbox.perf.test.ts: list of 200 within 50 ms on 100 000 rows (index use)

## Guardrails (MUST / MUST NOT)
- MUST filter by the authenticated user id in SQL on every query; the id comes from the token only.
- MUST NOT expose params or fields beyond CT-NOTIF-PAYLOAD.
- read-all MUST run in bounded batches (<= 500 rows per statement) to avoid long locks.
- Cursors MUST be opaque, bound to the filter set and expire after 24 h (CT-PAGE).

## Failure modes
- Database timeout -> 503 with retry_after_s; no partial read-all state is reported as complete (response only after all batches).
- Invalid UUID/ULID in path -> 404 (not 400) to avoid probing.
## Notes
Uses the pagination library from B025 through its public interface only.
