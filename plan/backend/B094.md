## Goal
Turn SLOs and failure signals into actionable alerts with severity, ownership and a written runbook for every page, so an on-call person who has never seen the system can triage and mitigate.

## In scope
- Alert rule files in `infra/alerts/` (Prometheus/Grafana rule YAML): SLO multi-window burn rates (fast: 14.4x over 1 h and 5 m = page; slow: 6x over 6 h and 30 m = page; 3x over 3 d = ticket) for each SLO defined in B093.
- Cause-based alerts: relay 4503 close rate > 1 % for 5 m, relay connections drop > 30 % in 5 m, Stripe webhook queue oldest age > 10 m or backlog > 100, any DLQ non-empty for 15 m, Postgres replication lag > 30 s, connection pool > 90 % for 5 m, Redis memory > 80 %, certificate expiry < 14 d, backup age > 26 h (metric from B099), retention job failed or aborted, webhook delivery failure ratio > 50 % for 15 m, `readyz` failing on > 1 instance.
- Routing config: severities `page`, `ticket`, `info`; escalation primary -> secondary after 15 min without ack; contact points by env variable (PagerDuty/Opsgenie/Slack abstraction in Grafana provisioning).
- One runbook per alert in `infra/runbooks/alerts/<alert-name>.md` using a fixed template (Symptoms, Impact, Dashboards, Triage commands, Mitigation, Escalation, Verification, Post-incident).
- Lint script `infra/alerts/lint.mjs` ensuring every alert has `severity`, `owner`, `runbook` label that resolves to an existing file, and an `expr` that references catalogue metrics only.
- On-call handbook `docs/ops/oncall.md` (rotation rules, handover, severity definitions, incident roles, status page update procedure using the status service).

## Out of scope
- Defining metrics and SLOs (B093) and implementing exporters.
- Disaster recovery runbooks (B099 owns `infra/runbooks/dr/`).
- Terraform for Grafana (B091 provides contact point endpoints as secrets).
- Customer-facing communications beyond updating `/v1/status` incidents.

## Build against (no counterpart needed)
`promtool check rules` and `promtool test rules` with synthetic time series; a local Alertmanager/Grafana container for routing tests; no live pager provider is needed (webhook receiver stub).

## Deliverables
- `infra/alerts/`
- `infra/runbooks/alerts/`
- `docs/ops/oncall.md`

## Interfaces (the only surface other lanes may use)
- Alert names (stable): `ApiAvailabilityFastBurn`, `ApiAvailabilitySlowBurn`, `ApiLatencyBurn`, `RelayConnectBurn`, `RelayFanoutBurn`, `ResumeFailureBurn`, `StripeWebhookLag`, `DeadLetterNonEmpty`, `PostgresReplicationLag`, `DbPoolSaturation`, `RedisMemoryHigh`, `CertExpirySoon`, `BackupStale`, `RetentionJobFailed`, `WebhookDeliveryFailing`, `ReadyzFailing`, `RelayOverloaded`, `RelayConnectionDrop`.
- Required labels on every alert: `severity`, `service`, `owner`, `runbook` (repo-relative path).
- Commands: `pnpm alerts:lint`, `pnpm alerts:test` (promtool).
- Runbook template `infra/runbooks/alerts/_template.md`.

## Acceptance criteria
1. `pnpm alerts:lint` passes: all 18 alerts listed above exist, each with `severity`, `service`, `owner` and a `runbook` that resolves to a non-empty file containing all template sections.
2. `promtool test rules` proves: a 1.44 % error rate for 1 h fires `ApiAvailabilityFastBurn`; 0.2 % for 1 h does not; a DLQ with 1 job for 14 min does not fire and 16 min fires `DeadLetterNonEmpty`.
3. Page-level alerts are limited to user-impacting conditions: a test asserts there are <= 10 `page` alerts and every `page` alert has an SLO or an explicit user-impact statement in its annotation.
4. Each alert has annotations `summary`, `impact`, `dashboard` (URL template to a B093 dashboard) and no annotation contains customer data or label values such as user/workspace ids.
5. Routing test: a firing `page` alert reaches the stub receiver once, repeats no more often than every 4 h, escalates to the secondary contact after 15 min unacknowledged, and `ticket`/`info` never page.
6. Every runbook has at least one concrete command or dashboard link per triage step and a 'how to verify recovery' section; a reviewer drill (tabletop) on 3 randomly chosen alerts is recorded in `docs/ops/oncall.md`.
7. Inhibition: `RelayConnectionDrop` is suppressed during an active deploy window (label `deploy_in_progress`) from B092; a test covers it.

## Tests required
- promtool rule syntax and unit tests for each SLO burn alert and 5 cause-based alerts.
- lint script tests with intentionally broken fixtures (missing runbook, unknown metric).
- Alertmanager routing tests with amtool.
- docs link check for runbook cross references.
- tabletop exercise checklist test (file exists and is dated within the release).

## Guardrails (MUST / MUST NOT)
- MUST NOT include user, workspace or session identifiers, emails or message content in alert labels/annotations; alerts are service-level.
- MUST NOT create an alert without a runbook and an owner; no 'noisy but informational' alerts at `page` severity.
- MUST NOT put secrets or pager keys in repo files; contact points reference environment variables.
- MUST ensure every page alert corresponds to a symptom a customer can notice or imminent data-loss risk (backup stale, DLQ).
- MUST keep alert thresholds in one file per service so changes are reviewable.

## Failure modes
- Metrics pipeline down -> `ObservabilityDown` meta-alert (absent-metric check) pages via a separate channel; documented in the runbook.
- Alert storm during a regional outage -> grouping by `service` and inhibition rules keep the page count <= 3.
- Paging provider unreachable -> fallback Slack/email contact point fires after 5 min.
## Notes
Alerts `BackupStale`, `RetentionJobFailed` depend on metrics exported by B099 and B090; until those land the lint script allows `pending_metric: true` annotations only in non-prod rule files. The named alert list may grow, never shrink, without updating the runbooks.
