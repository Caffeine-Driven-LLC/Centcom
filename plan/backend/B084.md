## Goal
Publish and serve the release manifest per channel so installers and the auto-updater can find the latest signed build for a platform and architecture.

## In scope
- `GET /v1/releases/{channel}/latest?platform=&arch=` and `GET /v1/releases/{channel}/manifest.json` (public, no auth) for channels `stable`, `beta`, `nightly`.
- Release ingest: an internal `publishRelease(manifest)` function and a CLI `pnpm release:publish <manifest.json>` used by the release pipeline; verifies the manifest's Ed25519 signature against the configured release public key(s) before storing.
- Storage: `releases` and `release_artifacts` tables; artifacts are CDN URLs only (never proxied); only the newest N=20 manifests per channel are kept active, older marked `superseded`.
- Per-channel `min_client_version` published to Redis key `status:min_client_version` for the status feed (B086) and returned in manifests.
- Yank support: `yankRelease(version, channel, reason)` removes a version from `latest` without deleting it.
- HTTP caching: `ETag`, `Cache-Control: public, max-age=60` for latest, `max-age=300` for the full manifest.

## Out of scope
- Building, signing and uploading artifacts to the CDN (release tooling of the client side; only the manifest crosses the contract).
- Auto-update client logic and installer scripts.
- Status feed assembly (B086) and client-too-old enforcement on WS/REST (B038, API middleware use `min_client_version`).
- Staged percentage rollouts.

## Build against (no counterpart needed)
Generate manifests and Ed25519 keypairs in tests; use the sample manifest(s) in `contracts/fixtures/` when present, otherwise the schema in `schemas/release-manifest.schema.json` via the generated validators from B003.

## Interfaces (the only surface other lanes may use)
- `GET /v1/releases/{channel}/latest?platform=<p>&arch=<a>` -> the platform-specific manifest entry (version, channel, released_at, artifact url, sha256, size, signature, min_client_version) per `schemas/release-manifest.schema.json`.
- `GET /v1/releases/{channel}/manifest.json` -> the complete manifest, all platforms.
- `publishRelease(manifest: ReleaseManifest, actor: Actor): Promise<{version: string; channel: string}>`; `yankRelease(...)`.
- CLI: `pnpm release:publish <manifest.json> --channel stable|beta|nightly [--dry-run]`.
- Redis key `status:min_client_version` (semver string); config `RELEASE_PUBKEYS` (comma-separated Ed25519 public keys, base64url), `RELEASE_KEEP_ACTIVE=20`.

## Acceptance criteria
1. `latest` for an existing channel/platform/arch returns 200 with the highest non-yanked semver (prerelease ordering per semver; `nightly` ordered by `released_at`); missing platform or arch returns 400 with pointers `/platform` or `/arch`; unknown channel returns 404.
2. `publishRelease` rejects a manifest with an invalid or unknown-key signature, a sha256 not matching `sha256:<64 hex>`, a non-HTTPS artifact URL, or a lower version than the current latest of the same channel (unless `--allow-downgrade` set by an admin).
3. Yanking the latest version makes `latest` return the previous version within 60 s (cache TTL), without data loss.
4. Responses carry `ETag`; `If-None-Match` returns 304; `Cache-Control` as stated; p95 <= 30 ms (served from memory cache refreshed every 30 s).
5. A published manifest is byte-stable: the stored manifest is served verbatim (no re-serialisation changing signature verification).
6. `status:min_client_version` equals the stable channel's `min_client_version` after publish, and unchanged when only beta/nightly publish.
7. The endpoint serves with no authentication, and rate limit anonymous 30/min/IP applies with `RateLimit-*` headers.

## Tests required
- unit: semver ordering incl. prerelease; platform/arch matching.
- integration: publish -> latest -> yank -> latest.
- signature tests with valid, tampered and wrong-key manifests.
- contract: manifest vs schema; headers.
- failure-path: Redis down on publish -> manifest stored, key update retried by a job; DB down -> 503 with `retry_after_s`.
- abuse: requests with huge query strings or invalid channel path -> 4xx, no stack traces.

## Guardrails (MUST / MUST NOT)
- MUST verify the Ed25519 signature before a manifest becomes visible; MUST NOT accept unsigned manifests in stage or prod.
- MUST serve only HTTPS CDN URLs and never fetch or proxy artifacts.
- MUST NOT allow publishing through a public endpoint; publish is CLI/CI-only with an `admin` scope credential or a deploy-time DB role.
- MUST keep release public keys in config, never in code, and support two keys at once for rotation.
- MUST NOT leak internal build metadata (CI URLs, commit authors, internal hostnames) into the manifest response.

## Failure modes
- No release exists for a channel -> 404 problem+json (not 200 with null).
- Corrupt stored manifest -> that row is skipped, error metric incremented, previous version served.
- CDN URL later unreachable -> not detected here; update client verifies hash, so no integrity impact.
