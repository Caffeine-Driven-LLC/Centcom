## Goal
A person can run the API and the relay on their laptop and watch two brand-new accounts sign up, share a session through the relay and read each other's encrypted messages, so the clients can be built and tried against a real backend.

## In scope
- Serve the session, workspace, member, entitlement, invite and share-link routes from `apps/api/src/modules.ts` (each skipped with one log line when its dependency is not configured), with the plugins they need (idempotency, RBAC, audit).
- `pnpm dev:relay` (`tools/dev/relay.ts`): runs `apps/relay` against the dev stack with the API's JWKS and plain `ws://` for local use.
- A development-only default plan for new accounts (`DEV_DEFAULT_PLAN`), written in the sign-up transaction, refused in production, and the seeded workspace on a plan with `relay_access`.
- The relay announces a member's first connection (`control.member_joined`) so the host grants keys; guests without a device are admitted as viewers.
- `pnpm dev:two-clients` and `pnpm dev:two-accounts` (`tools/dev/`): scripts that play two people with the client's real libraries, and `docs/api-service.md` 'Two sessions on your machine'.

## Out of scope
- Production deployment, a real mail provider, billing and metering (B106).
- A viewer guest's sender checks (B104) and session-level invites (B105).

## Acceptance criteria
1. With the stack, API and relay running, `pnpm dev:two-accounts` ends OK: a new e-mail signs up (user, personal workspace, owner membership, plan), invites a second new e-mail, both join one session through the relay and each reads the other's message.
2. A production configuration refuses `DEV_DEFAULT_PLAN` and a production sign-up gets the free plan (test).
3. The relay announces `control.member_joined` once for a member's first connection and the host grants keys (relay test).
4. A viewer guest ticket with no `dev` claim is admitted only as a viewer with no caps; a bad or missing `dev` for any other role is refused (relay tests).
5. A module whose configuration is missing is skipped with one log line and the rest boots (test).

## Guardrails (MUST / MUST NOT)
- MUST NOT put tokens, tickets, invite or link secrets, key material or e-mail addresses in logs.
- MUST keep contracts/ as it is: this lane builds against the contract text and fails closed where the contract is silent.
- MUST NOT let a development default (plan, rate limits, plain ws) take effect in production.

## Failure modes
- Redis, Postgres or the relay down while a script runs -> the script prints which step failed and exits 1.
- A second sign-in of the same e-mail -> the same user and workspace (no duplicate).
