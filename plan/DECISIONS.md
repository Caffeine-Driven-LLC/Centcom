## Provider design (contracts 1.2.0)

| Question | Decision |
|---|---|
| Use the Claude Agent SDK / OpenAI Agents SDK, or call model APIs directly? | **No.** Centcom drives the user's own `claude` and `codex` CLIs as child processes (stream-json / app-server JSON-RPC). Adding an SDK or API path needs an ADR (CT-PROVIDER). |
| Who handles login and credentials? | The vendors' own tools. Centcom only launches their login (`claude auth login`, `codex login`) in the user's terminal and asks `claude auth status` / `codex login status`. It never reads or stores credentials; the backend never sees any (B101 enforces). |
| "Sign in with Claude" inside Centcom? | Not permitted by Anthropic, not implemented. |
| Native "Sign in with ChatGPT" plan-token client? | Out of scope for v1 (needs an OpenAI-issued client ID); the `codex` engine covers ChatGPT sign-in via the user's own Codex. Revisit by ADR. |
| Who pays in a command post? | The host's CLI/account. Subscription-backed engines are blocked in shared command posts by default (kill switch `provider.command_post.subscription`, off); API-key/cloud logins are allowed. Branch mode: each owner pays. |
| Do we meter or sell model usage? | No. Entitlement `hosted_minutes_month` meters relay time (server-side); client-reported tokens/agent minutes are informational only. |
| How are approvals routed? | Engines call the injected `PermissionGate` (C015); Claude Code via `--permission-prompt-tool` served by a small stdio MCP server, Codex via app-server approvals. |
| What still needs a human? | Written confirmation from Anthropic (and OpenAI for shared use) before enabling subscription-backed command posts; re-verification of CT-PROVIDER §2 before launch (see its risk register §8). |
