# 05 · End-to-end encryption

Contract in this file: **CT-CRYPTO**

Goal: the relay, the database, backups and our staff cannot read work content. Only devices of current (or entitled past) session members can.

Primitives (libsodium names): **X25519** (key agreement), **Ed25519** (signatures), **XChaCha20-Poly1305-IETF** (AEAD), **BLAKE2b** (hashing/MAC/KDF), **crypto_box_seal** (sealed boxes), **Argon2id** (only for optional passphrase wrapping, not on the wire). No other algorithms in v1. `alg` values: `xchacha20poly1305`.

---

## 1. Keys

| Key | Type | Lives | Notes |
|---|---|---|---|
| **Device identity** `D_x` | X25519 keypair | Device, OS keychain | Public half registered with the backend at device-flow login |
| **Device signing** `D_s` | Ed25519 keypair | Device, OS keychain | Public half registered; signs every encrypted frame |
| **Session key** `K[e]` | 32 random bytes per **epoch** `e` | Held by member devices only | Generated by the host at session creation (`kid = "k1"`) |
| **Path MAC key** `K_p[e]` | `BLAKE2b-256(key = K[e], data = "centcom.pathmac.v1")` | derived | For `file.lock.path_hmac` = `base64url(BLAKE2b-256(key = K_p[e], data = utf8(normalised_path)))`; paths are NFC, `/`-separated, relative to the project root, no leading `./` |
| **Snapshot key** | same as `K[e]` | | Snapshots are AEAD under the epoch key |

`kid` = `"k" + epoch`. Epoch starts at 1.

Public keys are fetched from the backend: `GET /v1/devices/{id}/keys` and `GET /v1/sessions/{id}/members` (includes each member's device public keys). Keys are **trust-on-first-use** with a visible fingerprint: `fp` = first 12 characters of `base32_rfc4648(BLAKE2b-256(D_x ‖ D_s))`, shown as `ABCD-EFGH-IJKL` (users can compare out-of-band; the UI offers "verify" for high-trust teams). A changed key for a known device raises a warning, never a silent accept.

## 2. Encrypting a frame

Plaintext = UTF-8 JSON of the secret payload (see CT-WS-SESSION-EVENTS). Output `ct = {alg, kid, n, c}`.

```
n   = 24 random bytes (XChaCha nonce)               -> base64url
aad = canonical_json({"v","t","id","sid","from_dev","k","kid"})   // from_dev: sender device id
c   = XChaCha20-Poly1305-Encrypt(key = K[kid], nonce = n, aad = aad, plaintext)   -> base64url
```
`canonical_json` = RFC 8785 (JCS). `from` (member id) is stamped by the server, so the AAD uses the **device** id which the sender knows and which cannot be spoofed without the sender's signing key.

Nonces are random 192-bit; no counter state is needed. A device MUST NOT reuse a nonce with the same key (random 192-bit makes collision negligible; implementations MUST use the platform CSPRNG).

## 3. Signing

Every frame with a `ct` carries `sig`:
```
sig = Ed25519-Sign(D_s, canonical_json({"v","t","id","sid","from_dev","k","kid","n","c","p"}))
```
(`p` included only for hybrid frames; absent otherwise.) Receivers MUST verify `sig` against the sender device's registered Ed25519 key (looked up via the roster; the roster carries `device` ids and the public keys are cached) and drop invalid frames.

The relay does **not** verify content signatures (it cannot read `from_dev` semantics beyond the header) but MAY verify them as an abuse filter since it knows the public keys; verification is optional in v1 and never a reason to reject valid traffic.

## 4. Giving a member the key (joining)

Invites are for people; keys are for devices. Flow when device `M` joins session `S`:

1. `M` obtains a relay ticket and connects. The relay emits `control.member_joined` (with `device`).
2. The **host** (or any editor who holds all epochs and is online) sees the new device and sends a **key grant** event: a `queue`-free, `t:"event"`, `k:"key.grant"` frame (hybrid: `p` = `{to_device, kids:[…]}`, `ct` = for each kid, `crypto_box_seal(K[kid], D_x[M])` list). Because the grant is sealed to `M`'s public key, only `M` can open it.
3. `M` decrypts the grants, stores the keys in memory (and optionally in the keychain for fast resume), verifies the host's signature, then can decrypt history frames and everything after.
4. If no key holder is online, `M` stays in `waiting_for_key` state: it receives ciphertext it cannot read and shows "Waiting for the host to let you in".

> `key.grant` is added to the catalogue as part of this contract (hybrid, sender: host or editor holding keys). Its `p`: `{to_device: dev_…, kids: [short]}`; its secret: `{grants: [{kid, sealed: b64}]}`.

**Share history off** (`control.policy.share_history=false`, or an invite flag): the grant contains only the current and future epochs, never earlier ones.

**Hosted offline grants** (so joining works when the host sleeps): the host can pre-publish a *sealed key bundle* for a specific invite: `PUT /v1/invites/{id}/key-bundle` (an `crypto_box_seal` of `K[*]` to a one-time invite public key `I_x` whose private half is carried in the invite link fragment `#k=…`, never sent to the server). The accepting device opens it using the fragment. The server stores only ciphertext, deletes it on acceptance/expiry.

## 5. Removing a member / rotating

When a member is kicked, leaves permanently, or a device is revoked:
1. The host (or the relay on the host's behalf **only for `control.kick`, never choosing keys**) triggers a new epoch: the host generates `K[e+1]`, seals it to every remaining device, publishes `key.grant`s, and the relay emits `control.rotate_key {kid:"k{e+1}"}`.
2. Frames sent after `rotate_key` MUST use `K[e+1]`. Removed members keep access to history they already hold (cryptography cannot revoke knowledge), but cannot read anything after the rotation.
3. If the host is unreachable when a rotation is needed, the session is `paused` until a key holder rotates.
4. Scheduled rotation: every 7 days or 100 000 frames (whichever first) the host rotates (reason `scheduled`).

## 6. What the relay may see (the contract)

| Visible to relay | Never visible |
|---|---|
| Frame header fields, sizes, timing, `kid` | Message text, code, diffs, file paths, branch names, commands |
| Queue/approval metadata (CT-WS-SESSION-EVENTS clear parts) | Session keys, device private keys |
| `path_hmac` (keyed hash, unlinkable across sessions) | Plaintext paths |
| Member public keys (it distributes them) | Anything inside `ct` |

Traffic analysis (who talks when, how much) is **not** hidden in v1. This is stated in the privacy policy.

## 7. Storage rules

- Private keys: OS keychain (`@napi-rs/keyring`), never in config files, never logged, never in crash reports.
- Session keys: in memory; persisted only encrypted by a key held in the OS keychain.
- Snapshots and durable history on the server are ciphertext under `K[e]`.
- Telemetry and crash reports MUST NOT include `ct`, keys, or decrypted payload text.

## 8. Conformance vectors

`fixtures/crypto/vectors.json` holds known-answer tests (fixed keys/nonces → expected `c`, `sig`, `path_hmac`, sealed-box *structure* checks). Both sides' libraries (client lane `C056`, backend lane `B050` for the "relay cannot decrypt" tests) run them in CI. Vectors are generated by `tools/plan/gen_crypto_vectors.py` with libsodium and reviewed in the Contract PR.

## 9. Not in v1

Forward secrecy per message (ratchet), post-compromise security beyond epoch rotation, metadata hiding, key backup/recovery (a lost device means asking the host for a new grant), multi-host sessions.
