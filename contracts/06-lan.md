# 06 · LAN direct mode

Contract in this file: **CT-LAN**

Two machines on the same network collaborate with **no backend and no account**. A *host* client runs a small WebSocket server that speaks the same protocol as the relay (CT-WS-ENVELOPE, CT-WS-SESSION-EVENTS, CT-WS-QUEUE, CT-WS-CONTROL), with the host client playing the "server" role.

## 1. Discovery (mDNS / DNS-SD)

- Service type: `_centcom._tcp.local.`
- Instance name: `<session-name>-<4 hex>` (unique on the network).
- Port: host chooses (default 7070, falls back to a random free port).
- TXT records (all ≤ 255 bytes, lowercase keys):

| Key | Meaning |
|---|---|
| `v` | LAN contract version, `1` |
| `p` | Protocol list, `1` |
| `sid` | Session id (`ses_…`, generated by the host locally in LAN mode) |
| `name` | Session display name (≤ 40 chars, **not secret**) |
| `host` | Host display name |
| `fp` | Host device fingerprint (CT-CRYPTO §1) |
| `n` | Current member count |
| `pair` | `1` if a pairing code is required (always `1` in v1) |

- Advertising can be disabled (`--no-announce`), in which case guests join by `centcom join ip:port` + the pairing code.
- Discovery never leaks anything secret: no key material, no content.

## 2. Pairing and trust (no backend)

A guest must prove it knows a short **pairing code** shown on the host screen (8 chars `[A-Z2-9]` without ambiguous glyphs, valid 5 minutes, one use per guest, rate-limited 5 attempts per code).

Protocol: **CPace** (balanced PAKE; draft-irtf-cfrg-cpace) over ristretto255 using libsodium, with the host's session id and both device fingerprints as the channel identifiers. Output: a shared secret `ISK` used to
1. authenticate both sides (key confirmation MACs exchanged), and
2. wrap the session key grant: the host sends `key.grant` sealed to the guest's X25519 key **after** confirmation.

Wire form: before `sys.hello`, the WebSocket carries `lan.pair.1` … `lan.pair.4` text frames (a mini-handshake, defined in `schemas/lan-pair.schema.json`):
```
G → H  lan.pair.1  { cpace_msg, device:{id,x25519,ed25519,name}, fp }
H → G  lan.pair.2  { cpace_msg, device:{…}, fp }
G → H  lan.pair.3  { confirm }          // MAC over transcript with ISK
H → G  lan.pair.4  { confirm, ok:true, member:{…}, session:{sid,name,policy} }
```
On success both sides **remember** each other's device keys (TOFU) so reconnects skip pairing within the session's lifetime (a per-session reconnect token, 256-bit, issued in `lan.pair.4` and stored in memory + keychain).

Failure modes: wrong code → `lan.pair.err {code:"bad_code"}` and close 4403; too many tries → ban the source IP for 10 min.

## 3. After pairing

The guest sends `sys.hello` as with the relay, but `ticket` is the **LAN reconnect token** (opaque string, not a JWT). The host validates it locally. Everything else (welcome, sequencing, ack, resume from the host's in-memory log, queue, control, presence) is identical. The host is both the relay and the host member.

Differences to the relay:
| Topic | Relay | LAN host |
|---|---|---|
| Ticket | JWT from backend | Local reconnect token |
| Replay buffer | Redis + durable log | Host memory + local transcript file |
| Snapshots | Server blob store | Host's local disk; fetched over a `lan.snapshot.get` frame |
| Rate limits | Server-enforced | Host-enforced with the same defaults |
| Billing/entitlements | Enforced | Never; LAN is free |
| Audit | Server | Local log only |
| Host loss | Failover possible | Session ends (no failover) |

## 4. Network rules

- Bind: all interfaces by default, with `--bind <ip>` to restrict. Never bind publicly unless the user passes `--allow-wan` (and then warn).
- Plain `ws://`. Payloads are end-to-end encrypted under the session key (CT-CRYPTO), so LAN is as confidential as relay for content. Pairing messages carry only public values and PAKE messages.
- Firewall hints: if no guest can connect within 30 s the host UI shows how to open the port.
- IPv4 and IPv6 both supported; mDNS on `224.0.0.251` / `ff02::fb`.
- Max members in LAN mode: 8.

## 5. Moving from LAN to relay

A LAN session can be **upgraded** to a hosted session (Pro): the host calls `POST /v1/sessions` with `adopt: {lan_sid, key_epoch, last_seq}`; the transcript so far stays local on the host and is offered to joiners as a snapshot. The session id is re-minted by the server; members reconnect via the relay with a new ticket. This is a v1 *capability* (`lan.upgrade`) but may ship after launch; clients check the cap.
